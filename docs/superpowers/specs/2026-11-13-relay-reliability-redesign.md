# 预设中转稳定性整改设计

日期：2026-11-13

状态：独立技术复审、独立用户视角复审及修订复核完成；第一批确定性修复已实施并完成本地检查，详细范围见第 15 节。整体设计尚未全部实现，未通过真实模型与客户端上线验收。

代码基线：`ecf50e471`；文档基线：`dc4820365`。线上状态未在本轮重新核验。

范围：预设、请求/回复脚本、世界书、客户端交付、故障处理、配置生命周期和正文审计的完整链路。

## 1. 目标与边界

用户要的是：配置好一个渠道后，日常聊天、变量更新、结构化输出和客户端工具调用都可以稳定使用；预设及其必要脚本真正生效；不用每次请求都猜测该开哪个开关，也不用靠反复试错恢复配置。

本设计不是“让所有请求都显示成功”。成功必须同时包括：

1. 客户端收到符合其显式协议和格式要求的完整结果。
2. 该请求应执行的预设核心功能确实执行，没有偷偷切换为裸模型。
3. 不丢失客户端工具、工具历史、必要数据或关键输出处理。
4. 可选功能失败时，不毁掉已经可以安全交付的结果。
5. 用户能知道当前配置是否可用、发生了什么以及怎样恢复，而不是只收到通用报错。

不能承诺模型永不输出错误、网络永不中断、任意酒馆浏览器脚本都能在中转站运行。可以承诺的工程目标是：支持边界明确、已支持流程有可重复的验收证据、异常处理一致、配置变更可回退、故障不产生静默损坏。

设计审查轮只编辑本文。用户随后授权开发，并明确要求推送到现有云端自动部署链路，部署后暂停，真实模型与客户端验证另行安排。下文所有“必须”均为验收要求，不因代码已部署而视为完成。

## 2. 取舍：保留核心能力，减少互相矛盾的规则

- 保留必要请求脚本、工具绑定、回复还原脚本和必要清理。不能通过删除它们获得“兼容”。
- 中转站接收完整消息历史；脚本处理请求内上下文，不建立跨请求酒馆会话，不自行获取别人的聊天。
- 管理员可以维护适合中转站的预设派生版：明确改中性任务措辞、上下文接口和输出边界，保留原始文件及变更说明。通用运行时不按预设名称写特殊分支，不自动改写任意第三方预设。
- 浏览器美化、按钮、DOM、聊天持久化等不在本模块目标内。导入时说明这些能力未运行；依赖这些能力的核心脚本不得伪装为可用。
- 客户端业务工具归客户端；中转站不执行业务工具、不伪造工具结果，不为适配随意改名或删除历史。
- `tool_choice:none` 限制客户端可见工具调用，不禁止中转站使用内部承载回复的工具。
- 不通过静默增加模型调用、重试或修改客户任务来修复格式。
- 优先修复已有实现的职责边界；不另建一套并行工作流框架，不为每个故障新增开关。

## 4. 唯一处理模型与不可变约束

一个请求只确定一次执行计划，冻结渠道配置版本、客户端约束、预设/脚本版本、世界书和规则版本。后续阶段不得各自重新猜测客户端意图。

处理顺序：

1. 保存原始请求审计引用，解析客户端显式约束及工具所有权，确定渠道快照。
2. 做支持范围、配置有效性及预算检查；明显不能处理的请求必须在调用上游前明确失败。
3. 按既有发送规则处理客户历史，保留不可变原文和稳定历史 ID；冻结世界书扫描快照及候选条目。扫描不包含随后由预设生成的文字。
4. 预设组装建立锚点后，在同一世界书事务内完成宏展开、匹配/递归、预算、排序、插入及 `wi_format`；随后系统消息合并、预设后处理和请求脚本各执行一次，形成最终上游请求。世界书不能在全部脚本执行后才补进去。
5. 依据最终有效计划验证上游请求边界，调用上游一次；现有重试必须遵守第 9 节边界。
6. 聚合响应，识别内部回复来源/客户端业务工具，完成必要解包和 formatter。
7. 执行必要回复处理和可选处理，按声明的依赖及顺序逐项提交。
8. 验证最终客户端交付协议及格式，提交响应，记录结果。

原始输入不可变；阶段在私有工作副本上操作。失败时仅丢弃该阶段未提交修改。消息、工具、宏变量和阶段诊断一起提交/回退，不允许正文回退而宏状态残留。阶段不能靠重新执行已运行脚本恢复；脚本的非事务外部副作用不在允许能力中。

此事务承诺不等于能快照任意 JavaScript 虚拟机。`tavern-v1` 共享 realm 的闭包、事件监听器和 once 状态不能靠复制消息或 host 变量回滚。只有隔离的纯输入输出步骤、明确可快照的 host state 可逐步继续；共享 realm 的依赖钩子组成原子组，失败销毁 realm，绝不复用或重跑。后续必要处理仍依赖该 realm 时不能继续；不依赖它的宿主规则可在完整有效检查点上继续。候选检查必须拒绝无法兑现的“继续”选项。

“检查点”只表示已完成哪些处理，不意味着任何中间结果都能交付。可交付结果必须同时满足：

- 所有必需阶段完成，或使用已验证、等价的替代还原方法；
- 无未消费的内部工具、半截 arguments 或未完成 SSE；
- 客户端显式格式、工具选择和历史约束成立；
- 不遗漏被定义为必要的数据和清理。

阶段执行记录至少包含：版本、阶段、成功/跳过/失败、是否使用退路、最终交付分支、错误码和耗时。不要将“执行过脚本”当作“脚本效果符合任务”的证明。

## 5. 配置一次可用：导入、升级、审批与回退

### 5.1 一个完整配置单元

预设内容、脚本及依赖的固定版本、启用项覆盖、世界书关联及覆盖、回复来源、格式还原约定、必要/可选规则、失败处理共同组成一个版本。渠道凭据、地址、分组等不进入可导出的预设包，也不能被导入覆盖。

新导入和更新已有预设必须分开处理：

- 新导入：发现脚本和声明能力，生成候选配置；未支持能力用人话说明；必要能力缺失不能标为可用。
- 更新：在旧版本之上做字段级差异和依赖分析，保留与本次变更无关的渠道选择；新增/删除/变更必须展示。不能靠“全部继承旧审批”绕过检查，也不能重建对象丢掉原配置。
- 导出/重新导入：支持无凭据完整适配包。只导入原始酒馆 JSON 时明确“这是预设原文件，不含本渠道的适配设置”，提供保留现有设置的更新入口。
- 保存草稿不影响运行版本。激活必须是完整配置原子切换；配置有误时旧版继续服务。
- 带版本号比较写入，阻止两个浏览器窗口互相覆盖；缓存跨实例失效和读取必须保持整版本一致。
- 保留可恢复的上一完整版本和变更说明。回退还原整套配置，不仅还原提示词文本。

以现有渠道存储和缓存为基础实现版本单元，不先造一个配置平台。若需要新增持久化字段/事务，必须补真实 SQLite/MySQL/PostgreSQL 验证，不以模拟测试替代。

### 5.2 激活界面

默认页面只展示：

- 正在使用：版本、必要脚本状态、世界书状态、支持的请求类型。
- 本次更改：哪些功能改变、哪些设置保留、哪些需要重新确认。
- 验证结果：“本地检查通过”与“该渠道真实请求验证通过”分开，不写笼统“已准备=完全可用”。
- 操作：保存草稿、检查、启用此版本、恢复上一版本。

未变化的配置不要求反复审批；普通用户不手填 JSONPath、指纹或内部工具名。技术详情折叠。所有有效默认值由后端返回，前端不得另算一套规则。

### 5.3 发现与授权分离

新回复来源的发现使用候选快照，不受旧来源固定指纹阻挡；发现本身不授权新代码执行或启用。发现必要的受限脚本运行遵守相同隔离和资源限制。

激活检查才验证候选来源、脚本代码、依赖版本和输出约定是否一致。需要重新确认时展示实际变更，不要求用户先删除旧来源才能修复。审批绑定稳定配置依赖，不绑定每次客户端 schema 或动态业务参数。

远程脚本/依赖只在准备候选时取回、锁定摘要、验证；请求路径不重新下载“最新脚本”。升级失败不影响当前版本；旧版回退不能依赖远端文件还存在。脚本名称相同不代表代码可信或兼容。

### 5.4 一次请求一个版本

激活期间，已有请求继续使用原快照，新请求使用完整新快照。重试只选择满足同一已确定交付约定和核心处理要求的渠道；不得为了换渠道删除预设或脚本。是否等价由稳定的计划字段判定，不由渠道名推测。无合适渠道时返回明确失败，不降格为裸转发。

运行版本与验证记录分开：验证记录绑定配置 revision、编译器/运行时 revision、端点/模型/协议、关键参数、请求类型及客户端交付方式。换模型等只使相应验证证据过期，不自动清除所有信任授权或让旧配置停止工作；已知不兼容的修改仍须阻止激活。缓存按不可变 revision 读取，激活切换活动版本，已有请求继续持有旧快照。配置可移植不代表跨模型验证结论可移植。

### 5.5 多轮更新与已知可用恢复点

单次请求冻结版本不能保证连续会话跨版本兼容。升级和回退都须检查客户可见工具定义、变量格式、历史解析规则及脚本的数据约定：

- 与旧历史兼容的升级，可原位切换；必须以“旧版产生第一轮、新版接续”的案例验证，回退方向也要验证。
- 破坏性变更不能直接替换正在使用的入口。保留旧固定版本渠道/模型别名，新入口用于新会话或明确完成迁移的客户端；用户在切换时操作一次，不需要每个请求传版本。旧入口必须实际固定旧配置及兼容重试池，不能只有名字没变、背后仍切换活动版本。
- 不知道历史兼容性时视为尚未证实，不猜测客户会话结束。中转站不新增聊天会话服务器，不擅自改写变量状态。
- 至少保留一个明确已验证可用的恢复点，而不只是“上一次保存”。恢复前显示可否继续现有会话；配置回退不能撤销已执行的业务工具或客户已接收的变量变化。

新增模型/端点组合先在候选入口验证，不直接覆盖已验证的正常入口。客户端变化不能总被服务端自动识别；支持清单提供一次性的接入配置和验证操作，不依赖 User-Agent 猜客户端功能。

P0 确认主用客户端能否给既有会话保留原入口；若其全局模型设置会切换全部会话，保持原入口直到用户明确完成迁移，不宣传可以自动“新旧会话各用一版”。

### 5.6 本次必须交付能直接用的适配包

开发/维护者负责交付当前主用预设及普通/变量两个现有用途的完整适配包，不把写 formatter、判断脚本依赖、填写来源指纹的工作转嫁给普通管理员。包内必须包含：

- 核心功能清单及与原预设的对应关系：请求处理、工具绑定、回复还原、必要输出内容；删除/中性化的只是明确列出的任务偏向或浏览器职责。
- 必要性与依赖声明、完整输出映射、可行的失败退路、固定依赖和经验证默认值。
- 当前客户任务样本、长历史和续轮验收证据；同一配置不逐轮切换开关。
- 兼容升级/回退说明、保留原文件及可阅读的修改摘要。

普通用户的工作是确认来源可信、选择所需功能、关联世界书并启用；不是编程。未知第三方原文件可以作为待适配草稿，但“发现不支持”不算完成当前主用预设的交付目标。通用运行时提供声明接口，当前派生包提供具体实现，两者分开。

## 6. 出错如何处理：把“继续”做成真实能力

### 6.1 必要与可选由功能决定

必要：让预设工作所需的请求脚本、内部工具还原、客户工具保护、最终格式验证，以及管理员标为必需的数据处理/清理。

可选：不改变客户交付含义的装饰、非必需补充信息等；世界书是否必需由管理员明确选择。普通小说增强世界书可允许失败跳过，承载任务关键规则的世界书不能默认为可忽略。

无法证明脚本仅作装饰时，不自动认定它可选。通用系统无法推断任意程序的语义；由适配包声明并经过验收，界面显示其作用。现有渠道升级不得悄悄重新分类。

本次主用包必须在准备阶段把可选装饰移出核心共享 realm 依赖组，改为可隔离的纯处理或默认不启用不必要装饰；不能只在运行时说“虽然是装饰，但它坏了只能整条失败”。确实不可隔离的组整体标为必要，不宣传其局部可无害跳过。任何改造都要证明核心请求/回复脚本的实际作用仍保留，而不是再次删除脚本。

依赖分组须形成明确清单，以同一输入比较请求处理、工具绑定、回复还原和必要变量的行为；再注入可选装饰故障验证核心不受影响。不能通过把所有失败步骤都改标“必要”来规避可用性要求。

### 6.2 有效行为表

| 阶段 | 配置“继续”后的有效行为 | 仍不能继续的情况 |
| --- | --- | --- |
| 世界书 | 回滚世界书整个阶段，继续原预设和请求脚本；标记世界书未使用 | 该世界书被设为必要，或原请求/配置本身无效 |
| 请求预设/脚本 | 只有显式允许“不使用此预设也可服务”的渠道，且未发上游，才能回到原始客户请求走正常中转 | 核心预设必须存在的渠道不提供此选择；不把这种退化记为预设成功 |
| 回复来源还原/formatter | 使用事先验证等价的还原退路，仍得到完整的客户端结果 | 内部工具无法完整解析，必需字段缺失，无法证明退路保留必要数据 |
| 可选回复脚本 | 丢弃失败步骤修改，继续执行后续仍适用的规则，最终检查再交付 | 失败步骤是必要转换，或者剩余结果不满足交付约定 |
| 可选接收正则 | 同上，保留此前有效正文，不返回被替换到一半的内容 | 必要清理失败、必须命中的规则未命中，或最终格式无效 |
| 最终交付验证 | 只从已完整执行必要步骤的候选中选择合法结果 | 没有合法完整结果时失败；不把 JSON 改成纯文本冒充成功 |

“原样请求”指恢复原始客户端请求语义，然后经过正常鉴权、路由、协议转换等；不是绕过网关的字节直通。上游调用后不得借此再次发一遍裸请求。

formatter 出错不再躲在用户看不到的策略之外。界面用“从预设回复中取出结果”解释该阶段，与“可选的回复加工”分开。内部工具不能直接透传给不认识它的客户端。

### 6.3 关键改动：生成退路，而不是到处截获异常

准备配置时生成一份有效失败计划：每阶段的作用、是否必需、可用退路、原因。前端只允许选择真正有效的选项；若旧配置写了不可能执行的“原样继续”，明确提示冲突并在候选中修正，不静默覆盖运行版本。

运行时所有异常出口使用同一阶段处理规则，包括超限、超时、解析、宏展开和插入错误。未知内部错误默认不能绕过必要步骤，但要提供定位信息，避免所有错误压缩为 `preset script processing failed`。

可选失败不应短路跳过后面的必要正则。若其下游依赖失败输出，则同组回滚或停止，依赖在配置检查时确定。禁止无限尝试历史中间字符串，禁止重复运行有状态脚本。

“失败”还包括程序正常返回但违反该步骤的输出约定，例如把合法 JSON 加工成非法 JSON。可选步骤在私有副本中完成后，须先验证该步骤承诺保持的约束，再提交。没有明确步骤边界、只能在整段结束时验证的转换组合，作为一个事务组处理：必需组失败不得绕过；纯可选组可回到其入口的合法结果。不能在最终验证失败后任意倒找一个字符串，也不能以“没有抛异常”证明加工成功。

等价 formatter 退路只适用于已声明“某字段就是完整最终正文”的来源；存在重排、多字段合并、必要变量等逻辑时不能擅自退回取一个字段。先验证、后启用，不以名称猜测。

### 6.4 用户应看到什么

配置页显示一句有效总结，例如：

> 世界书异常时继续；预设核心脚本必须正常运行；装饰处理异常时保留完整回复。不会把内部工具直接发给客户端。

请求结果分三类，分开统计：

- 完整完成：核心及要求的功能完成，客户结果有效。
- 降级完成：客户结果有效，但明确允许的可选功能没运行；控制台说明失去什么，不能算完整成功。
- 提交前失败：没有合法完整结果或在提交前取消；连接仍可写时，客户端得到稳定错误码和请求编号，不包含私人内容。

另列“发送中断/接收未知”：处理成功不证明客户端已收到。开始写出后的断连不能算完整交付，也不能再返回另一份 JSON 错误或重试。服务端只记录自己的写入事实；无应用层确认时不宣称客户端完整接收。上面三类处理结果与发送状态分开存储，界面组合显示，避免一列“成功/失败”掩盖区别。

默认不往 JSON 正文、工具参数或剧情正文塞提示语。降级提示放控制台；响应头可作为辅助但不能假设所有客户端显示。频繁降级在渠道页聚合提醒，单次可选故障不要求用户立刻操作。

失败详情必须给出恢复决策：当前运行配置是否改变、是否有兼容的已知可用版本、是否值得重试、是否可能重复客户业务动作。确定性配置错误不提供误导的“再试一次”；不把“恢复上一版”当作模型拒绝、网络故障或客户状态变化的通用解药。无合法结果时明确告知，不拿上游 HTTP 200 安慰用户。

## 7. 世界书：触发、位置、顺序和可解释性

世界书分两步：先冻结发送规则处理后的客户历史扫描快照和候选，再在预设组装的正确位置完成匹配与物化；随后让请求脚本读取已经包含世界书的消息。不能为了“预设之前处理”把所有位置粗暴变成一个最前 system。预算依赖展开后长度、递归依赖已纳入内容，必须在同一宏上下文单次执行，不能提前匹配一次、插入时再算一次。

当前实现的配置值应按以下契约整理，不凭记忆扩大酒馆兼容范围：

| 位置 | 解释与边界 |
| --- | --- |
| `follow_global` | 条目继承本书/配置明确的全局位置，不是又一个物理位置 |
| `inherit` | 使用预设的世界书锚点；具体优先锚点及无锚点时批准的兼容位置在候选检查中展示 |
| `before_definition` / `after_definition` | 分别对应预设的 `worldInfoBefore` / `worldInfoAfter`，不靠任意 system 文本猜定义 |
| `system_prelude` | 前导 system/developer 消息之后、首个会话消息之前的系统补充位置 |
| `before_last_user` | 有效客户历史的最后一条 user 之前，不是预设临时生成的 user 之前 |
| `at_depth` | 在有效历史 user/assistant/tool/function 消息坐标中从尾部数；0 为最后历史消息后，1 为最后历史消息前。预设临时消息不计入；不越过其后的预设尾部指令 |

工具调用及关联结果组成不可拆的片段；落在片段内部的插入点移到片段起点，并记录请求位置与实际位置。缺失定义锚点、没有 user、深度超界不能静默退到 system：候选配置可明确批准一种兼容映射，否则运行时按世界书必要性跳过/失败。不得把现有隐式回退悄悄当成新契约。

预算优先纳入较高 Priority；同一插入块内最终按 Priority 从低到高排列；同值保持书的配置顺序、条目顺序，不能因 map 遍历改变。界面分别解释“预算优先级”和“实际顺序”，不误称高优先级一定最先出现。超预算完整排除条目、不截断必要内容，记录原因。沿用已通过测试的匹配算法，不为本次整改重写所有关键词/递归规则。导入默认值和真正启用的高级约束分开；不能仅因为存在一个默认字段就判定整本世界书不兼容。

必要性也是预算义务：在固定扫描范围和既有有限递归规则内，必要世界书中已命中且符合条件的内容不能被当作普通可选超额项丢弃。每一轮已经发现的候选集合内，预算准入先保护必要内容，再给可选内容；同一必要性级别沿用上述 Priority 及稳定顺序。已参与宏/递归工作态的选择不事后撤销重算，不承诺全局最优分配。后续递归发现必要内容无法容纳、或工作限额使必要判断未完成时，整个世界书事务不能记为完整完成；按必要性停止而不是悄悄继续。没有命中的条目不等于失败。

这不能只新增一个报错出口：主用包激活前须证明代表长历史、实际宏展开、必要条目和客户输出空间能容纳于模型有效上下文和服务预算，预览显示预算占用。发现无法容纳的常用任务就是配置/方案阻断；不能让用户每次通过手动关条目碰运气。调整预算算法只限新增必要性义务，既有递归和宏不可为预算重跑。

每条条目有稳定来源 ID，记录是否启用、是否命中、是否被预算排除、逻辑位置和实际阶段位置。预设合并等已知变换维护映射；任意脚本重写后无法追踪时显示“脚本已重组，无法精确定位”，不可将旧索引标为最终位置，不用文本搜索假装证明。

条目总览保留开关、触发方式、位置、顺序、必要性/跳过策略归属及搜索筛选；点开才编辑详细内容。空条目、没命中、没启用、出错跳过是不同状态。导入说明默认汇总可用条目和需处理问题，技术字段折叠；每个问题有具体影响和可执行操作。

整个世界书阶段使用第 4、6 节事务规则，覆盖匹配、宏、预算、格式模板及插入。在进入此事务前保存组装消息及完整宏工作状态，失败恢复后接续后处理；不重跑已经执行的预设前缀。没有该世界书时预算变化或递归依赖也不能留下残留决策。

## 8. 客户端格式与预设工具：支持边界及必要实验

### 8.1 先确定客户交付，再决定内部运输方式

使用请求的显式字段建立约束，不通过提示词关键字猜“变量渠道”“剧情请求”。自然语言格式要求仍传给模型，但没有明确可验证规范时不宣称能机械证明语义正确。

没有 `response_format` 的真实客户端同样是主用范围，而不是无关边缘情况：

- 普通渠道保持客户原始任务约束和中性预设；请求只在提示词里要求变量标签、JSON 或不续写剧情时，预设不能强制改回剧情、增加开场白或装饰段。这类任务必须进入 E2 真实验收。
- 变量专用入口可在适配包中预先绑定明确的默认交付约定，例如既有变量块及其中可解析的更新列表；管理员一次启用，之后不逐轮选择。该约定来自客户已知协议，不是从正文猜测的分类器。
- 请求有显式约束时按其决定交付；与渠道不可变的必要功能矛盾时预检诊断，不偷偷忽略任何一方。没有显式约束则使用明确的渠道默认值；也没有默认值时保持正文，不增加未经请求的包装。
- 同一入口中混入无法区分的不同隐式格式要求，不能承诺机械全自动识别。优先保留任务语义；若需要强格式保证，使用已配置的稳定入口/客户明确标识，不增设逐轮人工切换。

P0 必须核对实际客户端发送的是显式字段、约定标签还是纯提示词，并据此记录支持和验证方式。“验证 JSON 语法通过”不能证明变量更新业务正确；主用变量样本还须验证更新操作与任务要求相符。

由第 4 节唯一执行计划冻结“有效交付约定及来源”，请求组装、formatter、失败退路和最终验证共同读取。渠道默认值不能只加进提示词，却不进入后续验证。纯业务工具中间轮仍遵循第 8.2 节分支，不因渠道默认 JSON 就被强迫产生正文。

内部回复工具是预设输出的运输方式，不是客户端业务工具。脚本可修改其负责的上游组装，但最终边界检查不能被脚本覆盖：客户端工具 schema、选择限制和历史不能被悄悄丢弃；名字冲突不能按顺序覆盖，必须在上游前给出可操作诊断。

| 客户端请求 | 正常交付 | 核心脚本/内部工具规则 |
| --- | --- | --- |
| 无业务工具或 `none` | content；若要求 JSON/schema 则正文满足它 | 必要请求脚本生效，可用内部工具承载并还原；不泄露 tool_calls |
| `auto` | 合法正文，或合法客户端工具调用；允许的协议下也可同时有 content 和业务调用 | 请求脚本运行；有最终正文时执行其必要还原；纯业务调用是合法中间步骤，不凭空补剧情 |
| `required` / 指定业务工具 | 符合选择约束的真实业务调用 | 请求脚本仍运行，但不能用内部回复工具替代客户要求；最终文本轮再走正文还原 |
| 工具结果续轮 | 保留工具 ID、参数和结果关系，继续真实任务 | 不伪造历史，不把客户工具结果当内部回复；不得重复执行业务工具 |

“核心脚本生效”不等于每一轮必须出现内部工具调用：客户要求业务工具的那一轮有其协议职责。必须展示真实执行和交付分支；不能用这条解释长期绕过最终回复脚本。

### 8.2 混合输出必须先实验，不能用一句 prompt 当保证

现有“上游允许混合、本地一律拒绝”需要整改。目标是接受协议允许、且能无损还原的输出，不是禁止所有客户端并行工具。

候选实现边界：

- 内部工具与普通 content 同时出现：只有来源约定明确两者如何组成结果时才组合；不默认拼接思考、说明或重复正文。正文权威来源在配置中确定，附带文字保留在审计中。
- 同一 choice 内部工具与业务工具同时出现：内部部分还原为 content，业务调用保留原 ID/name/arguments；仅在客户允许 content+业务调用、来源无歧义、最终验证通过时交付。不丢掉其中一侧。
- 多内部回复、未知工具、调用未结束、同名冲突，不猜测取第一个。
- 客户端 `parallel_tool_calls` 不被全局关掉来避免内部问题。上游原生能力不能表达所需约束时，必须记录能力边界。
- `auto` 下不能用“强制任意工具”代替“回答正文时使用内部容器”的条件需求。

接受模型必须落实到每一个 choice，而不只是解除原有拒绝：

1. 纯业务中间轮：保持业务工具，正文钩子按“无最终正文”不适用记录；不要求它凭空生成最终 JSON。客户端明确禁止工具时此分支无效。
2. 纯最终正文：执行 formatter、必要正文钩子和清理，再验证客户正文格式。
3. 正文＋业务混合轮：正文执行与纯正文一样的必要处理；业务参数不得进入正文脚本或正则。非空正文若受 `response_format` 约束，必须满足该约束。不能沿用“只要有工具就跳过整个 choice 的处理”。

经已验证的运输及协议映射后，最终上游请求仍无法表达所需约束，或最终客户端结果无法保持原约束时，在上游前明确拒绝。不要求客户约束字段字面透传：例如 JSON 约束可由内部工具承载、formatter 和最终验证共同兑现，但禁止丢弃其语义；未经验证的映射不能作为兼容保证。初始稳定范围必须覆盖 `n` 未设置或为 1；多 choice 在完成逐 choice 独立处理和整响应提交验收前明确不支持此适配组合，不能只返回第一个来伪装满足 n。该限制不应影响未开启适配的普通渠道。

SSE 输出契约：保留业务工具的 ID、name、arguments、相对顺序；删除内部工具后，若重建可见工具 index，整个输出流须使用同一连续映射，不影响后续 tool_call_id。内部参数不能作为片段泄露。结束原因在已完整还原且无业务工具时才可由 tool_calls 转为 stop；仍有业务工具则保持工具结束语义。length/content_filter、拒绝及中断不能改写为成功 stop。终止帧不重复，usage 不累加重建次数；原有扩展元数据保留或明确标记无法无损转换。客户端最终 JSON 和流式解析出的结果必须等价。

供应商拒绝是独立状态：仅在客户协议支持对应拒绝表达时按协议交付，否则明确失败；不能从推理或零散文字中编一个“符合 schema 的答案”。截断的内部参数不允许容错补齐后当完整成功。

实验 E1 必须在目标上游用低成本无敏感任务覆盖：纯内部、纯业务、内部+文字、内部+业务、多个业务、none、named、required、续轮，以及流式分片。检验上游实际接受何种约束和本地可无损接受哪些结果。

通过则实现上述接受模型；若供应商或现有脚本不能保留两类职责，禁止宣称该组合已支持，也不默认启用这条新路径。保留已验证组合；由渠道能力页说明限制和可选兼容渠道。绝不暗中追加模型一跳来拆任务。实验未通过的高频组合是发布阻断项，而非上线后让用户碰运气。

### 8.3 formatter 不应破坏客户正文

运行时向适配脚本提供只读的客户端交付约束，并区别最终正文、必要结构数据和可选展示段。由显式声明的 formatter 接口消费这些字段，不给通用运行时增加预设名称判断。

- JSON/schema：完整正文作为一个结构化值验证；不能附加 summary/选项标签、包一层引号或重复序列化。
- 普通文字：允许预设既有组织和风格，不自动删除变量、时间锚点等客户真正要求的数据。
- 多字段被定义为必要数据时，必须有明确的客户结果映射；不能为了 JSON 合法就把字段扔掉。
- 纯提取脚本与任意转换脚本区分；后者不能假装存在通用安全回退。
- 若需要修改预设派生版接口，明确版本及差异，原版保留。确认核心能力案例通过后才能替换线上配置。

实验 E2 验证普通文本、严格 JSON、schema、包含反斜杠/Unicode/代码的大字符串、附加段启用时的数据保留，及原始 OutputPreprocessing 的实际职责。不可把原本空操作脚本当作已验证了复杂转换能力。

## 9. 流式、并发、取消、重试与费用

必要的完整回复处理继续使用有界缓存，不把未验证片段先发出去。需要完整结果的渠道在界面说明“此预设需等待完整回复”，不能称为实时逐 token 输出。

基线交付方式：验证前不提交响应头和业务正文，因此仍能返回正确 HTTP 错误。可用客户端须在实际等待预算内接受这种方式。心跳会提交响应头，不能当作无成本补丁；若以后增加心跳模式，须单独证明 SSE 错误语义、断线及客户端行为，不能先开再说。

实验 E3 在实际部署规格和代表客户端测量首字节/总等待、取消传播、并发资源与内存。记录网络代理的空闲超时、客户端绝对超时，以及请求预算的最小值；超过已支持预算的组合明确标识，不谎称延长网关超时就能解决全部问题。

交付支持清单必须包含主用客户端的一次性超时/流式设置，以及常见长度和较长历史下的实测等待。若客户现有版本无法配置到足以完成必要处理的等待范围，这就是当前主要目标未解决，不能仅在说明中加一句“请耐心等待”就通过发布。心跳、异步任务或第二次生成不是默认退路。

容量设计：

- 区分长时间在途额度和短时间脚本 CPU 执行额度。采用有上限的准入/短等待，不允许无限排队；额度按实例预算配置，并有客户/渠道公平性。
- 并发上限、单响应上限、解析后的内存开销与队列长度一起测量。不得只把 16 或 8MiB 改大。
- 超过响应限额、取消、超时应及时取消上游并释放槽位，不读完整个无用大回复；有界记录诊断。
- 超载在上游前拒绝，给出稳定错误类型和合理重试提示。不能显示预设脚本坏了。
- 断开连接后不继续做无价值格式化，已开始上游的费用是否产生按现有实际用量与计费规则处理。

重试仅适用现有允许重试的失败类型、有剩余总预算、兼容执行计划，且客户端响应未提交。上游已经返回完整但不合法的结果，不能默认重试多次来粉饰成功率。脚本已执行副作用或客户端已收到业务内容时禁止重放。客户端在断线后自行重试可能重复业务工具建议，中转站不能承诺跨请求 exactly-once。

取消信号必须贯穿准入等待、上游连接/读取、脚本执行、格式化、最终写出，而非只在 Finish 前检查一次。响应头或正文首次提交后不重试、不再追加另一份错误正文；发送中断只记录已知状态。上游错误响应、上游成功但适配失败、下游写入失败分别记录，不用一律 HTTP 200 或一律“脚本失败”掩盖来源。

不新增收费规则。本模块必须保证预扣/结算/释放沿既有规则执行且每次上游尝试可核对：上游产生用量但本地未交付不能伪造为没调用，也不能重复结算；错误诊断不混淆“客户端交付失败”与“上游未产生费用”。涉及账务修改时遵循 `.agents/rules/billing.md` 并补相应测试。

## 10. 日志：默认看懂，需要时能还原事实

默认比较“上游内容”和“发往客户端的内容”，两侧采用同一种可读模式，并标明上游内容来自哪个工具/字段。旁边清楚显示“从工具参数取出正文”等实际步骤。没有可读正文时显示工具调用，而不是一片空白；发生写入中断时明确右侧是计划发送的完整内容及已知发送状态，不声称客户端全部收到。

提供一个明确的“查看原始协议”入口，保留原始请求/上游响应/客户端响应及各自 HTTP 状态；复制原文复制真实捕获数据，复制正文只复制解码后的所选文本，两者不能同名混淆。

解析规则：

- 只在协议定义的字符串字段或用户展开的完整嵌套 JSON 上逐层解析；限制深度、大小和计算时间。
- 语法上合法的反斜杠、Windows 路径、代码和字符串 `\\n` 不全局替换；不在中转传输链路为“好看”修改它们。
- 大整数、未知类型保持精度；无法安全解析时保留原文并说明，不重新序列化损坏数据。
- 未完成 SSE、截断捕获、非 JSON、二进制或超大正文有明确状态；不能显示“空回复”掩盖捕获不完整。
- 未知工具只显示调用及参数，不标作已执行结果。不执行 HTML、链接脚本或日志中的指令。

布局采用内容区单一主滚动、可用的固定操作栏、适度宽度的目录或可折叠目录；长正文正常换行，代码可横向滚动。避免大空白键名列、每个叶子重复 JSONPath、嵌套滚动互相抢滚轮。宽屏和窄屏分别截图验收，复制、搜索、键盘操作、超长数据必须可用。

截图中的左右编码差异应能用“协议层不同，正文已提取”解释，但只有真实解析结果一致时才能显示一致；不能为了消除用户疑虑硬标“无问题”。

## 11. 用户体验与可观测性

普通操作路径：

1. 导入预设：看到它提供哪些核心能力，哪些浏览器功能不支持。
2. 关联世界书：总览启用项及位置，保留已有选择。
3. 检查并激活：本地检查失败有具体修复入口；真实验证未做则如实显示，不假装通过。
4. 客户端日常请求：同一配置按显式请求约束处理，无需每轮切模式。
5. 更新：查看差异、检查候选、启用；不必重新配置无关选项。
6. 出问题：请求号能看到在哪阶段、上游是否成功、客户为何没收到、有没有可用退路；可恢复上一完整版本。

渠道页展示近一段时间的完整完成、降级完成、提交前失败、发送中断、上游失败和超载；处理结果与发送状态按第 6.4 节分别统计。统计分母及版本必须明确；不能只看 HTTP 200，也不能把上游失败算成脚本缺陷。未测试类型标“未验证”，已知不支持标“不支持”，本地通过标“本地检查通过”。

日志保留配置版本、上游/客户端状态、处理阶段、预算和重试信息。默认不展示脚本堆栈；管理员可展开脱敏技术详情。审计大小和保留时间有界，不保存凭据，导出的复现包清除私人正文和可执行凭据。

配置页不增加一排新的工程术语。每个开关旁边回答：控制什么、关闭会失去什么、何时需要调整。错误提示附“当前配置未变/已恢复/需要修正哪项”，不让用户自己猜保存是否生效。

### 12.2 真模型与发布门槛

实验 E1/E2/E3 必须先给出事实结果及支持矩阵，才能开启依赖这些结论的大范围实现。对当前主用渠道及变量渠道验证完整任务，不只验证最简单的 `{"ok":true}`。使用无敏感、可判定结果的样本，不外传私人角色内容。

每种声明支持的关键任务至少有：确定性回归、真实目标模型代表样本、客户端实际接收验证。实测预算、轮数、结果和失败样本在运行前确定并记录，不能事后删掉失败样本。有限样本只能说明该版本在该组合通过，不证明无限可靠。

“日常无需干预”单列为产品门槛：P0 固定实际客户端、普通/变量用途、工具续轮、代表历史长度、可接受等待范围、必要功能清单及允许的人工干预条件。验收人员使用交付包一次配置后连续完成这些任务，经历兼容更新和兼容回退，过程中不得改内部来源、格式开关或临时关闭核心脚本。自然语言格式样本、关键变量结果和长历史都不能在失败后从矩阵删除。允许人工操作的条件限于主动升级/切换用途、明确的破坏性迁移和真实异常恢复，不包括正常每轮请求。

发布硬门槛：

- A–G 必须项无未解决失败；未支持组合明确列出且不误导入口。
- 核心脚本被跳过、内部工具泄露、客户工具丢失、结构化输出被污染、配置半更新、重复结算，任一出现立即阻断发布。
- 每个可选阶段的“继续”都完成故障注入验证；正常可交付结果必须继续成功。
- 代表负载内无资源持续增长；取消/超时释放在已设定预算内完成，预算及峰值实测记录。
- 保存配置本地验证与远程准备分离；不能保存一次就隐式下载/编译所有大脚本阻塞很久。延迟目标在 P0 建立基线后明确，不能本轮凭空许诺数字。
- 灰度期间分别看完整率、降级率、客户交付失败率、上游错误率及 p95 等待；不得用降级挤高完整率。没有连续观测证据不称“稳定版已验收”。

已知限制不等于可以把主要使用场景划出支持范围来过关。若主用模型无法同时满足预设核心功能与实际客户工具/格式需求，产品目标尚未达成，必须保留该阻断结论，而不是让用户自行接受裸转发。

| 阶段 | 交付物 | 开始下一阶段的条件 |

虽然当前管理员只有一人，不必建设长期兼容平台，但当前运行配置和回滚能力必须保全。旧文档归档、旧字段的迁移说明和当前唯一规则不可含糊。

发布必须可回退代码及对应完整配置；新代码写入的配置版本不能让旧代码误读。部署前准备兼容恢复包，失败由管理员/受控发布流程回退，不在单个请求中静默换预设版本。故障统计与证据保留，不能靠清日志改善观感。
