## 0. 实现状态（2026-11-08）

本文件是目标规格，实现按第 20 节的阶段顺序推进。当前分支已落地的部分：

- 工具协议只做显式投影：删除按工具字段名和 JSON 形状自动猜客户端的路径（`presetProtocolAutoJSONArgument`、`presetProtocolAutoJSONProjection`、`presetProtocolClientJSONObject` 等已移除）。
- 非 `tool` 契约只有在存在显式 `response_argument` 或启用的 `toolCallFormatter` 时才会激活；参数无法解析时明确报错，不输出半转换结果。
- 新增渠道级阶段策略 `tool_policy.phase_policy`：`request`（默认）、`always_auxiliary`、`always_final`、`disabled`。
- 新增显式工具角色列表 `action`、`content`，与既有 `client_final`、`preset_final`、`auxiliary` 一起由渠道保存，不再靠推断。
- 世界书导入高风险字段（`probability < 100`、生效的 `characterFilter`、`group`/`groupWeight`/`groupScoring`、`sticky`/`cooldown`/`delay`、`role`、酒馆原始位置字段）标记为 `risk`，条目导入后自动停用，原始 JSON 保留在 `source`，由用户一次性确认后简化启用。
- 世界书条目总览和详情页提供可见的“需要确认”状态与“确认并启用”操作，不出现灰色死开关。
- 世界书条目存在未解决 `issues` 时不能启用或“确认”，开关保持可点击并说明原因（第 9.5、9.6 节）。
- 下拉框统一使用项目 `Select`/`Combobox`，`NativeSelect` 已退役并由 oxlint `no-restricted-imports` 拦截。
- 渠道级 `AdaptationProfile`、`AdaptationBasePlan` 与冻结的 `AdaptationResolvedPlan` 数据模型（第 4、5.3 节）。
- 每个工具角色的可见性策略对象 `visibility_policy`：审计中输出 `auxiliary/action/content` 的生效可见性，指纹包含可见性摘要，网关内部工具集合参与响应侧泄露检查（第 5.2、7 节）。
- 分阶段 `failure_policy` 的实际执行：响应恢复、响应校验、输出预处理和接收正则各自按阶段取值，`safe_raw` 仅在无网关内部工具时可回退，接收正则支持 `preserve`/`empty`/`fail`（第 12 节）。
- 跨渠道重试的计划一致性校验：每个冻结计划额外保存“仅出站请求”的指纹，比较时覆盖预设、世界书、发送规则和工具协议；仅接收侧规则被排除，因为选中渠道会重建响应过滤器且不会改变已发送的上游请求。重试继续复用 `initialPresetAudit`，不再重新推断协议（第 4.2、12 节）。
- 预设能力报告：渠道编辑器内提供“能力报告”按钮，调用 `POST /api/channel/sillytavern/inspect`，展示探测到的工具、能力、警告和条目运行状态（第 10.1、14.2 节）。
- 能力报告和适配诊断对用户显示中文摘要，原始后端字符串仅保留在折叠的“技术细节”中，避免界面直接暴露英文内部字段。
- 适配概览：渠道编辑器顶部展示运行时、工具协调开关、最终回复模式和参与协调的工具数量（第 14.1 节）。
- 阶段级失败策略控件和可见性说明（第 5.3、14.4 节）。
- 第三层实时请求诊断 trace：`PresetCompileTrace.Diagnostics` 记录预检、世界书、预设、工具协调、请求计划、响应校验/恢复/输出处理/接收正则和客户端写回；审计工作台的执行详情新增“适配诊断”视图（第 14.3、17 节）。
- 能力报告使用有界内存指纹缓存；冻结计划使用“只缓存不可变策略元数据”的有界内存缓存，绝不跨请求复用包含原始消息的 `RequestPlan` 对象（第 10.2、13 节）。

截至本版本，第 20 节的交付项已全部落地。后续修改必须保持本节的诊断字段、缓存边界和审计不变量。

## 1. 最终目标

New API 的首要职责始终是中转站：

- 接收客户端请求。
- 完成鉴权、限流、路由、渠道选择、计费、日志和上游协议转换。
- 只在渠道明确配置了世界书、预设或脚本时，启用请求适配。
- 不把 New API 改造成 SillyTavern 客户端。
- 不保存会话状态、工具阶段、sticky、cooldown 或客户端身份。

最终目标是：

> 渠道保存明确策略；每次请求只根据当前请求契约生成一份不可变计划；世界书、预设、脚本、正则和工具协议按固定顺序执行；能够确定时自动处理，不能确定时安全回退；客户端收到它实际要求的结构，预设内部工具不泄漏。

必须同时满足：

- 没有配置适配的渠道保持纯中转，行为不变。
- 客户端身份不进入核心设计，不维护客户端列表。
- 请求行为由当前请求契约和渠道策略决定，而不是由客户端名称、UA、IP 或请求指纹决定。
- 语义角色由用户一次性确认，执行阶段由系统完全确定。
- 无法安全判断时不猜、不伪造、不半处理。
- 用户不需要理解脚本、工具 schema、世界书内部结构或正则实现。

## 2. 非目标

以下内容明确不做：

- 不完整复刻 SillyTavern 状态机。
- 不保存每个客户端的能力配置或历史覆盖项。
- 不根据工具名、参数数量、工具位置或 JSON 字段形状猜工具角色。
- 不根据提示词正文猜客户端要求的 JSON 或工具格式。
- 不自动执行客户端工具、预设工具或动作工具。
- 不把预设终止工具改名为客户端工具来伪造兼容。
- 不把动作工具结果吞掉后返回空正文。
- 不删除客户端工具定义、工具调用 ID、工具结果或工具历史。
- 不改变路由、模型选择、渠道亲和、计费、鉴权、日志和重试次数。
- 不为适配功能增加全局客户端管理页面或会话管理页面。

## 3. 核心原则

### 3.1 请求契约驱动

每次请求只根据可验证的结构判断处理方式：

- 现代工具契约：`tools`、函数级 `tool_choice`、工具调用历史。
- JSON 契约：`response_format.type` 为 `json_object`。
- 纯文本契约：没有现代工具契约，也没有 JSON 契约。
- 旧式函数契约：`functions`、`function_call`。

提示词中的自然语言要求不构成结构化契约。

### 3.2 语义角色只确认一次

机器可以识别工具所有权和已有调用结果，但不能自动理解语义。以下语义必须来自显式声明、结构唯一可证明或用户一次性确认：

- 预设终止工具。
- 动作工具。
- 内容容器工具。
- 响应字段映射。

客户端最终协议可以由客户端结构化契约唯一确定，不需要用户再次确认。

确认结果保存在渠道策略中，不保存在客户端身份中。

### 3.3 执行阶段不再推断

请求计划生成后，执行层只执行计划：

- 不重新推断工具角色。
- 不重新判断当前阶段。
- 不因为响应内容不同就临时切换协议。
- 不根据上游响应反向改变客户端契约。

### 3.4 失败时保持数据中心转

系统不伪造成功：

- 世界书解析失败，可以跳过世界书并记录诊断。
- 预设或脚本失败，按渠道策略严格失败或安全回退。
- 工具角色不唯一，不修改请求。
- 响应无法安全恢复，不输出半转换结果。
- 跨渠道重试计划不一致，拒绝换渠道重试。

## 4. 三层架构

### 4.1 渠道策略层

每个渠道最多有一个可选的 `AdaptationProfile`。

它只保存用户意图：

- 是否启用适配。
- 使用哪个预设。
- 使用哪个世界书。
- 发送侧文本规则。
- 接收侧文本规则。
- 工具契约默认策略。
- 预设终止工具的显式角色和响应字段映射。
- 世界书简化决策。
- 严格失败或安全回退策略。

它不保存：

- 客户端身份。
- 会话状态。
- 工具执行结果。
- 临时请求计划。
- sticky、cooldown 或递归状态。

### 4.2 请求计划层

每次请求进入后，根据当前请求和渠道策略生成一份 `RequestPlan`。

计划至少包含：

- 原始请求快照。
- 请求契约分类。
- 客户端最终工具或最终格式。
- 预设工具所有权。
- 工具角色。
- 当前阶段。
- 世界书匹配源和扫描结果。
- 世界书注入点和顺序。
- 预设脚本执行边界。
- 响应恢复目标。
- 失败回退策略。
- 计划指纹。

计划分为两个确定阶段：

- `BasePlan`：在预设脚本执行前生成。冻结原始请求快照、请求契约、渠道策略、世界书匹配源和匹配结果。
- `ResolvedPlan`：在预设脚本执行并完成工具解析后生成。冻结最终工具角色、当前阶段、响应恢复目标和执行参数。

`ResolvedPlan` 生成后不可再推断或修改。`Normalize` 到 `Tool Resolution` 读取 `BasePlan`，之后的执行阶段读取 `ResolvedPlan`。同一请求的所有重试必须复用同一个 `ResolvedPlan`。计划不得写入长期存储。

服务端指纹缓存只允许保存与请求正文无关的确定性元数据，例如渠道策略指纹、契约分类、客户端最终工具和已冻结的协议指纹。缓存键必须包含完整策略与请求结构摘要，但缓存值不得保存原始消息、匹配消息、世界书命中文本或任何会话状态。每次请求仍必须创建自己的 `BasePlan` 与 `ResolvedPlan`；禁止复用包含 `Original` 或 `Matched` 的请求计划对象。

### 4.3 确定性执行层

执行层只做计划规定的事。`ResolvedPlan` 生成前读取 `BasePlan`，生成后读取 `ResolvedPlan`：

- 处理发送文本。
- 匹配世界书。
- 编译预设。
- 注入世界书。
- 执行消息后处理。
- 执行预设脚本。
- 投影当前阶段需要的工具。
- 发送上游请求。
- 校验并恢复响应。
- 执行输出处理和接收正则。
- 最终写回客户端。
- 记录安全诊断。

执行层不重新推断，不临场改协议，不按工具名特殊处理。

## 5. 核心数据模型

### 5.1 请求契约分类

`ContractClass` 只允许以下值：

- `tool`：客户端存在现代工具契约。
- `json`：客户端明确要求 JSON 对象。
- `text`：客户端没有结构化契约，只期待文本。
- `legacy`：只存在旧式函数字段。
- `unknown`：契约不完整或冲突。

契约优先级：

1. 同时存在现代 `tools` 和 `response_format` 时，`tools` 优先，合同为 `tool`。
2. 只有现代 `tools` 时，合同为 `tool`。
3. 没有现代 `tools`，只有 `response_format.type=json_object` 时，合同为 `json`。
4. 没有现代工具和 JSON 合同时，只有旧式 `functions` 或 `function_call`，合同为 `legacy`。
5. 没有结构化工具和 JSON 合同时，合同为 `text`。
6. 同时出现无法无损并列的字段组合时，合同为 `unknown`。

只有 `tool` 和 `json` 可以进入自动协议投影。`text` 只有在预设显式声明内容容器工具时才能恢复正文。`legacy` 和 `unknown` 默认保持中转原样。

### 5.2 工具角色

`ToolRole` 使用主角色加可见性描述：

- `final`：最终回复协议。
- `auxiliary`：中间辅助工具。
- `action`：需要客户端执行外部动作的工具。
- `content`：承载最终正文或 JSON 的内容容器工具。
- `unknown`：无法确定。

可见性只允许：

- `client_visible`：该工具调用需要返回客户端，由客户端处理。
- `gateway_internal`：该工具仅用于最终内容承载，不得泄漏给客户端。

允许的组合：

- `final + client_visible`：客户端最终工具。
- `final + content + gateway_internal`：预设终止内容工具，只能投影为客户端文本或 JSON。
- `auxiliary + client_visible`：预设辅助工具。
- `action + client_visible`：预设动作工具。
- `content + gateway_internal`：可投影为文本或 JSON 的预设内容容器工具。
- `unknown`：不激活协议协调。

一个工具可以同时具有 `final` 和 `content` 语义，但必须显式声明或由预设合同唯一证明。最终工具属于客户端时使用 `final + client_visible`；最终工具属于预设且需要投影时使用 `final + content + gateway_internal`。

角色优先级：

1. 预设或渠道显式声明。
2. 客户端函数级 `tool_choice`。
3. 客户端只有一个必需工具。
4. 最后一条 user 消息之后已有辅助工具结果。
5. 预设脚本执行后的函数级 `tool_choice` 指向预设自有工具。
6. 没有客户端工具，且当前请求只存在一个预设自有工具。

以上都无法成立时，角色为 `unknown`。

### 5.3 渠道适配方案

`AdaptationProfile` 的建议字段：

```yaml
enabled: bool
preset_id: string
worldbook_id: string
applies_to_models: []
send_rules: []
receive_rules: []
tool_policy:
  mode: auto | disabled
  client_final_override: string
  preset_final: string
  auxiliary: []
  action: []
  content: []
  response_target: auto | text | json
  response_argument: string
  phase_policy:
    mode: request | always_auxiliary | always_final | disabled
visibility_policy:
  auxiliary: client_visible
  action: client_visible
  content: gateway_internal
failure_policy:
  preflight: request_passthrough | fail
  worldbook: skip | fail
  precompile: request_passthrough | fail
  preset: request_passthrough | fail
  script: request_passthrough | fail
  tool_resolution: tool_protocol_passthrough | fail
  response_validation: safe_raw | fail
  response_restore: safe_raw | fail
  output_processing: preserve | fail
  regex: preserve | empty | fail
  cross_channel_retry: reject
  response_started: stop
```

`response_argument` 是 JSON 点路径，第一版只支持一个最终投影字段。需要组合多个字段时，使用预设已有的 `toolCallFormatter` 生成最终 JSON 或文本，不在网关中增加隐式合并。

`response_target=auto` 的选择规则：

1. 如果存在客户端最终工具，选择 `tool`。
2. 如果合同为 `json`，且存在明确的终止工具和 `response_argument`，选择 `json`。
3. 如果合同为 `text`，且存在明确的内容容器工具和 `response_argument`，选择 `text`。
4. 否则不进行响应投影，使用 `tool_protocol_passthrough`。

`phase_policy.mode=request` 表示按当前请求消息判断。其余值只用于明确不重发辅助结果的请求，且保存在渠道策略中。

UI 可以提供一个“严格模式”快捷开关。保存时它必须展开为上面的阶段级失败策略，运行时不使用额外全局优先级。

`safe_raw` 表示：只有原始上游响应不包含 `gateway_internal` 工具、没有违反当前客户端合同、且尚未向客户端写出任何字节时，才允许发送原始响应并记录诊断。否则必须返回明确错误。

### 5.4 客户端身份

客户端身份不是核心模型。

系统不保存客户端名称、UA、IP、设备标识或客户端级覆盖项。需要区分策略时，只允许使用用户可控且稳定的路由边界：

- 不同模型名。
- 不同渠道。

API Key 可以继续用于 New API 的鉴权、限流和路由，但不参与适配方案选择。不同请求结构需要不同策略，而请求本身无法区分时，应拆分渠道，而不是维护客户端身份。

每个渠道只有一个 `AdaptationProfile`。`applies_to_models` 只决定该方案是否适用于当前模型，不产生第二套隐藏策略。

## 6. 固定请求流水线

### 1. Preflight

检查：

- 渠道是否启用适配。
- 模型是否匹配。
- 是否 Passthrough。
- 预设和世界书是否可解析。
- 脚本运行时是否可用。
- 当前请求契约是否可分类。

输出只有三种：

- 激活适配。
- 安全回退到纯中转。
- 明确失败，并给出原因。

不得出现“看起来启用了，实际部分生效”的中间状态。

### 2. Normalize

把客户端请求规范化为内部结构，同时保存只读的原始客户端快照。

### 3. Send Rules

只处理客户端输入文本。不得修改工具、图片、reasoning 或工具历史。

发送规则执行后的文本称为 `matched_messages`。发送规则执行前的只读副本称为 `client_snapshot`。

### 4. Worldbook Match

唯一一次世界书匹配。扫描源必须是 `matched_messages`，也就是发送规则已经处理、但尚未经过预设编译的客户端消息。

`client_snapshot` 只用于审计和契约判断，不用于直接注入。

该阶段完成：

- 角色范围。
- 扫描深度。
- 关键词和正则匹配。
- 大小写和全词。
- 优先级和预算。
- 递归控制。

### 5. Preset Skeleton

构建预设提示词骨架和命名插槽，包括 system 区、世界书标记、聊天历史标记和对话示例标记。

### 6. Worldbook Inject

把世界书注入骨架。该动作必须发生在系统合并、严格后处理和预设脚本之前。

### 7. Message Post-Process

执行系统消息 squash、merge、strict 和 single-user 等后处理。

### 8. Preset Scripts

执行预设服务端脚本、工具绑定和 `FinalRequestProcessing`。

脚本权限边界：

- 只能新增自己的工具。
- 不能删除客户端工具。
- 不能修改客户端工具定义。
- 不能修改客户端工具历史。
- 不能修改路由、计费、流式设置或上游私有字段。

### 9. Tool Resolution

判断客户端最终协议、预设辅助工具、预设终止工具、动作工具和内容容器工具。

只有唯一安全时，才允许激活协议协调。

工具解析完成后，`BasePlan` 被冻结为 `ResolvedPlan`。从此执行层不再重新推断工具角色或当前阶段。

### 10. Upstream Projection

当前阶段只暴露一种协议：

- 辅助阶段只暴露辅助工具。
- 最终阶段只暴露唯一最终工具或唯一终止工具。

请求投影只允许修改：

- `tools`
- `tool_choice`

投影只作用于即将发送给上游的请求副本。`client_snapshot`、客户端历史、工具调用 ID、工具结果和原始工具定义保持不变。

其他字段保持不变。

### 11. Provider Conversion

执行模型映射、系统提示、参数覆盖、字段裁剪和上游协议转换。

协议协调不得影响这一阶段的既有行为。

### 12. Upstream Request

发送上游请求，同时保存上游原始请求。

### 13. Response Validation

校验模型响应是否符合当前计划：

- 最终阶段是否只调用计划中的工具。
- 工具参数是否完整且可解析。
- 是否出现多个终止工具调用。
- 是否出现动作工具调用。
- 是否出现空正文或半转换内容。

### 14. Response Restore

恢复顺序固定：

1. 恢复被文本化包装的工具调用。
2. 恢复预设内部工具。
3. 按显式合同投影为客户端文本、JSON 或客户端工具调用。
4. 保留工具调用 ID、`finish_reason`、usage、reasoning 和未知字段。

响应投影必须原子完成：先在内存中生成并校验完整结果，再一次性写出。不得在流式输出中途完成一半后切换到另一套语义。

禁止：

- 向客户端泄漏预设内部工具。
- 吞掉动作工具。
- 在无法证明安全时把工具参数转成正文。
- 输出半个 JSON 或半个正文。

### 15. Output Processing

执行预设输出预处理、旧式提取和接收正则。

接收正则必须在协议恢复之后执行，且只处理客户端最终可见文本。

### 16. Final Emit

最后写回客户端。

必须保留：

- choice 索引。
- usage。
- reasoning。
- `finish_reason`。
- 工具 ID。
- SSE 元数据和未知字段。

### 17. Audit

记录阶段结论，不默认记录完整正文。

审计至少包含：

- 计划指纹。
- 契约分类。
- 工具角色。
- 当前阶段。
- 世界书命中结论。
- 响应恢复目标。
- 回退原因。
- 诊断代码。

## 7. 工具协议协调

### 7.1 激活条件

只有同时满足以下条件才激活：

- 端点为 Chat Completions。
- 渠道启用了适配。
- 预设模型匹配。
- 脚本运行时已启用并成功。
- 非 Passthrough。
- 客户端声明现代工具契约或安全的 JSON 契约。
- 工具角色唯一可判断。
- 当前阶段唯一可判断。

### 7.2 客户端最终工具

客户端最终工具按以下顺序确定：

1. 渠道显式 `client_final_override`。
2. 原始请求的函数级 `tool_choice`。
3. 原始请求只有一个工具且 `tool_choice=required`。
4. 有辅助工具结果，且排除已完成工具后只剩一个候选。
5. 否则未知。

不能因为预设脚本追加工具，就否定客户端原本唯一明确的最终工具。

### 7.3 预设终止工具

预设终止工具按以下顺序确定：

1. 渠道或预设显式 `preset_final`。
2. 无客户端最终工具时，脚本编译后的函数级 `tool_choice` 指向预设自有工具。
3. 无客户端工具，且脚本编译后只有一个预设自有工具。
4. 显式辅助列表中排除后，只剩一个预设自有工具。
5. 否则未知。

如果客户端已有最终工具，预设终止工具不能替换它。

### 7.4 辅助工具和动作工具

- 客户端最终工具确定后，其余预设自有工具默认为辅助或动作候选。
- 已有辅助工具结果的工具不能再作为当前阶段辅助工具重复暴露。
- 动作工具永远不能被响应投影吞掉。
- `action + client_visible` 是预期的客户端可见工具调用，不属于内部工具泄漏。
- `content + gateway_internal` 只能用于最终内容投影，不得直接返回客户端。
- 无法区分辅助工具、动作工具和内容容器工具时，角色保持未知。

### 7.5 当前阶段

阶段不保存到服务端，只根据当前消息序列判断。

当前周期边界是最后一条有效 user 消息。

辅助阶段：

- 存在辅助工具。
- 最后一条 user 消息之后没有已完成的辅助工具结果。

最终阶段：

- 最后一条 user 消息之后存在已完成的辅助工具结果。
- 或没有辅助工具。

如果客户端不重发辅助工具结果，渠道策略必须显式选择：

- 始终最终阶段。
- 始终辅助阶段。
- 关闭协调。

对应字段是 `tool_policy.phase_policy.mode`。默认值为 `request`，即按当前请求判断。

### 7.6 请求投影

辅助阶段：

- 只暴露辅助工具。
- 只有一个辅助工具时使用函数级 `tool_choice`。
- 多个已验证辅助工具时使用集合和 `required`。
- 客户端最终工具不得出现。
- `auxiliary + client_visible` 和 `action + client_visible` 可以进入辅助阶段，因为客户端需要执行并回传结果。

最终阶段：

- 只暴露唯一最终工具。
- 使用函数级 `tool_choice` 强制该工具。
- `content + gateway_internal` 不得作为可见工具返回客户端。

### 7.7 响应恢复

客户端最终工具：

- 保持上游 `tool_calls` 原样。
- 不转换为文本或 JSON。

客户端要求 JSON：

- 只在 `response_format.type=json_object` 且角色明确时恢复。
- 必须有显式 `preset_final` 和单个 `response_argument` 点路径，或使用 `toolCallFormatter` 生成完整输出。
- 参数必须是合法 JSON。
- 无法解析时不输出半转换结果。

客户端要求文本：

- 只在预设显式声明内容容器工具时恢复。
- 正文来源必须通过单个 `response_argument` 点路径或 `toolCallFormatter` 确定。
- 标签清理通过接收正则执行。

动作工具：

- 保留工具调用。
- 不转换正文。
- 不修改 `finish_reason`。
- 只允许 `client_visible` 动作工具进入客户端响应；`gateway_internal` 工具不得泄漏。

## 8. 典型场景

### 8.1 客户端最终工具与预设辅助工具冲突

输入：

- 客户端工具：`soliumbra_reply`
- 客户端函数级选择：`soliumbra_reply`
- 预设脚本新增工具：`context`

计划：

- `soliumbra_reply` 为客户端最终工具。
- `context` 为预设辅助工具。
- 第一条请求只暴露 `context`。
- 最后一条 user 消息之后已有 `context` 结果时，只暴露 `soliumbra_reply`。

结果：

- 客户端不会收到 `context`。
- 模型不会同时看到两个最终协议。
- 预设辅助能力保留。

### 8.2 预设终止工具同时包含信封和正文

示例结构：

```json
{
  "extra": "{\"emotion\":\"smile\",\"opts\":[\"...\"]}",
  "game_content": "<game>正文...</game>",
  "think_nya": "..."
}
```

可靠处理必须来自显式配置：

- 终止工具：该工具。
- 结构化字段：`extra`。
- 正文字段：`game_content`。
- 忽略字段：`think_nya`。
- 标签处理：接收正则去除 `<game>`。

第一版网关只支持单一路径投影。需要将 `extra` 和 `game_content` 合并为一个客户端 JSON 时，必须使用预设的 `toolCallFormatter`，由它输出最终 JSON。

配置后可以稳定输出客户端需要的 JSON 或正文。未配置时保持中转原样。

### 8.3 纯文本客户端

如果客户端没有工具，也没有 JSON 契约：

- 默认纯中转。
- 只有预设显式声明内容容器工具时，才允许恢复正文。
- 动作工具不能转换。
- 无法确定时不伪造正文。

### 8.4 多工具或提示词要求格式

如果客户端有多个工具且没有函数级选择：

- 工具角色未知。
- 不激活协议协调。
- 保持中转原样。
- 用户可以在渠道策略中显式指定最终工具。

如果客户端只在提示词中要求 JSON：

- 不视为结构化契约。
- 不自动推断。
- 可以配置接收正则或显式响应策略。

### 8.5 客户端不发送历史工具结果

如果无法判断辅助结果：

- 不猜测阶段。
- 使用渠道级策略。
- 不保存客户端身份。
- 不保存会话状态。

## 9. 世界书最终设计

### 9.1 两条硬边界

- 匹配必须在预设组装之前。
- 注入必须在预设骨架之后、后处理和脚本之前。

### 9.2 条目字段

保留真正影响运行的字段：

- 启用状态。
- 常驻或关键词触发。
- 主关键词和次级关键词。
- 正则、大小写和全词。
- 优先级。
- `prevent_recursion`。
- 条目级注入模式和深度。

### 9.3 插入位置

只支持四种确定语义：

- `inherit`：优先进入预设世界书标记，否则回退 system 前置区。
- `system_prelude`：插入开头 system 或 developer 之后。
- `before_last_user`：插入最后一条 user 消息之前。
- `at_depth`：按固定深度插入，深度限制在 0 到 20。

`at_depth` 的锚点固定为消息序列尾部：

- 深度 0 表示插入到现有消息之后。
- 深度 1 表示插入到最后一条消息之前。
- 深度 N 表示从尾部向前移动 N 条消息。
- 深度超过当前消息数量时，回退到 system 前置区。

不实现 per-entry AN、EM、outlet、role 和完整酒馆位置系统。

### 9.4 顺序

- 选择时高优先级先参与预算。
- 最终文本按优先级从低到高排列。
- 高优先级内容更靠近区块末尾。
- 预览必须显示真实顺序。

### 9.5 导入状态

每个条目导入后只能处于：

- 完全支持。
- 自动归一化后支持。
- 忽略展示字段后支持。
- 简化后支持，并明确说明触发范围变化。
- 无法安全简化，保持停用并说明原因。

风险字段：

- `probability < 100`
- `characterFilter`
- `sticky`
- `cooldown`
- `delay`
- 顶层 `depth`
- 不支持的酒馆位置字段，包括角色定义前后、AN、EM、outlet 和 role override

上述字段会改变触发范围或时机，不能默认绿色自动启用。用户确认一次后保存渠道决策。

本文支持的位置只有 9.3 节列出的四种模式。除此之外的位置字段均视为不支持，不得静默映射成支持的四种模式。

### 9.6 禁止状态

不得出现：

- 条目开关灰色不可点。
- 条目显示已启用但实际不会运行。
- 未支持字段被静默删除后自动启用。
- 世界书总开关关闭时误解条目状态。

## 10. 预设最终设计

### 10.1 能力报告

导入预设后生成能力报告：

- 提示词顺序。
- 启用条目。
- 宏和上下文需求。
- 聊天历史插槽。
- 对话示例。
- 服务端脚本。
- 工具绑定。
- 输出预处理。
- 响应正则。
- 可运行、部分运行、不可运行和未知能力。

脚本动态生成工具时，报告必须标记为：

- 已观察到的工具。
- 样本执行时新增的工具。
- 依赖请求上下文、当前无法确定的工具。

不能把样本结果伪装成永久事实。

### 10.2 失效规则

以下任一变化必须使能力报告和缓存计划元数据失效：

- 预设内容。
- 脚本运行时。
- 工具绑定。
- 工具协议配置。
- 世界书内容或简化决策。
- 发送和接收规则。
- 模型映射。
- 渠道适配策略。

### 10.3 保留边界

必须保留：

- 预设提示词和消息注入顺序。
- `ChatSquash`。
- `FinalRequestProcessing`。
- 预设辅助工具和动作工具。
- `OutputPreprocessing`。
- `toolCallFormatter`。
- 响应正则既有职责。

禁止：

- 修改客户端工具定义。
- 删除客户端工具历史。
- 静默吞掉无法识别的脚本能力。
- 在保存后才暴露不可运行能力。

## 11. 正则最终设计

职责收窄：

- 发送正则只处理客户端输入文本。
- 接收正则只处理客户端最终可见文本。
- 接收正则必须在工具恢复和协议投影之后执行。
- 接收正则不能先看到内部工具 JSON。
- 接收正则只负责正文提取、标签清理和格式清理。
- 接收正则不负责猜客户端协议。
- 默认匹配失败时保留原文。
- 只有用户显式选择时才清空。

固定响应顺序：

1. 文本化工具恢复。
2. 预设内部工具恢复。
3. 协议投影为文本、JSON 或客户端工具。
4. 输出预处理。
5. 接收正则。
6. 最终写出。

## 12. 失败与回退

阶段级策略：

| 阶段 | 默认行为 | 严格模式行为 |
| --- | --- | --- |
| Preflight | `request_passthrough` | 返回明确错误 |
| 世界书解析 | 跳过世界书并诊断 | 返回明确错误 |
| 预编译校验 | `request_passthrough` | 返回明确错误 |
| 预设编译 | `request_passthrough` | 返回明确错误 |
| 脚本执行 | `request_passthrough` | 返回明确错误 |
| 工具角色判断 | `tool_protocol_passthrough` | 返回明确错误 |
| 响应校验 | `safe_raw`，否则明确错误 | 返回明确错误 |
| 响应投影 | `safe_raw`，否则明确错误 | 返回明确错误 |
| 输出预处理 | 保留原文 | 返回明确错误 |
| 接收正则 | 默认保留原文 | 按规则失败或清空 |
| 跨渠道重试 | 计划指纹不一致时拒绝换渠道 | 拒绝换渠道并诊断 |
| 已开始写响应 | `stop`，不再重试 | `stop`，不再重试 |

`failure_policy` 的每个阶段字段是运行时唯一权威。UI 的“严格模式”只是一个保存快捷方式，保存时必须展开成具体阶段值。

“passthrough” 在本文中有两个明确含义：

- `request_passthrough`：整个适配层不启用，世界书、预设、脚本、协议和响应处理都不执行。
- `tool_protocol_passthrough`：世界书和预设按渠道配置继续执行，但工具协议不修改 `tools`、`tool_choice`，响应投影也不执行。

工具解析默认使用 `tool_protocol_passthrough`。响应校验和响应投影默认使用 `safe_raw`。Preflight 失败使用 `request_passthrough`。

当响应投影已经开始时，必须原子构建完整结果。若失败且尚未向客户端写出任何字节：

- 非严格策略只有在 `safe_raw` 条件满足时，才可以发送原始上游响应并记录诊断。
- 严格策略返回明确错误。

若已经向客户端写出字节，不得回退或切换语义，只能结束当前响应并记录诊断。

协议投影需要的流式缓冲必须按 choice 独立组装完整工具参数。缓冲超限时按阶段策略处理，且不得释放半个工具调用。

原则：

> 能确定才处理，不能确定就回退，不能回退就明确失败。

## 13. 性能与稳定性

- 没有适配方案的渠道走零额外处理路径。
- 没有世界书、没有预设、没有接收规则的请求不进入响应缓冲。
- 只有需要工具投影或接收规则时才缓冲响应。
- 所有宏展开、脚本、正则和缓冲都有固定上限。
- 重试复用同一计划，不重新推断阶段。
- 不保存会话级状态。
- 能力报告和计划按指纹缓存，配置变化立即失效。
- 审计默认记录结论，完整正文按需开启。

## 14. 管理界面

### 14.1 第一层：适配概览

只展示：

- 当前渠道是否启用适配。
- 使用哪个世界书和预设。
- 当前是否会实际运行。
- 最终回复模式：文本、JSON 或工具。
- 需要处理的问题数量。
- 一键切换回纯中转。

### 14.2 第二层：能力与条目

世界书显示条目总览：

- 条目名称。
- 启用状态。
- 触发方式。
- 插入位置。
- 是否被简化。
- 当前是否可运行。

预设显示能力报告：

- 哪些条目会执行。
- 哪些脚本会执行。
- 哪些能力只保留、不执行。
- 哪些工具会被识别。
- 哪些客户端契约存在冲突。

### 14.3 第三层：诊断与预览

显示：

- 每个阶段的输入输出摘要。
- 世界书命中原因。
- 注入的实际消息索引和顺序。
- 工具角色判断过程。
- 响应投影过程。
- 原始技术字段。
- 安全审计内容。

### 14.4 交互统一

- 固定短列表使用项目统一 `Select`。
- 长列表使用可搜索的 `Combobox`。
- 不使用 `NativeSelect`。
- 下拉弹层统一行为，不因选中项自动跳到上方。
- 不支持的控制显示原因。
- 不使用灰色死开关。
- 所有页面使用同一套状态、警告和确认交互。

### 14.5 状态颜色

- 绿色：确定支持，自动运行。
- 黄色：需要一次确认，确认后长期保存。
- 红色：无法安全支持，保持停用或纯中转。
- 灰色：未配置或未启用。

## 15. 旧路径退役

以下路径必须退役或合并：

- 按工具名关键字猜最终工具。
- 从提示词正文猜 JSON 协议。
- 响应阶段任意解析 JSON 再打补丁。
- 多个最终工具同时暴露给上游。
- 世界书“开着但不会运行”的状态。
- 分散在多个入口的同类配置。
- 同一功能的两套世界书注入实现。
- 预设脚本、`tool_text` 和工具协议同时处理同一响应。
- 灰色不可点击功能按钮。
- 项目内不同风格的 `NativeSelect`。
- 自动 JSON 形状投影默认路径。

当前代码中仍然存在的自动投影和字段形状猜测路径，必须在正式实现时删除或默认关闭，否则本文承诺的稳定性不成立。

## 16. 用户使用链路

### 16.1 第一阶段：导入预设

用户操作：

- 导入一个陌生预设。

系统自动：

- 解析名称、提示词顺序和启用条目。
- 识别脚本运行方式。
- 识别脚本新增工具。
- 识别输出预处理和响应正则。
- 检查不支持能力。
- 生成中文能力报告。

用户看到：

- 可以运行。
- 部分运行。
- 只能保留不能执行。
- 需要确认的工具角色。
- 需要确认的响应格式。

### 16.2 第二阶段：预检确认

系统生成预览：

- 客户端请求进入后先做什么。
- 世界书何时匹配。
- 世界书插到哪条消息前。
- 预设何时组装。
- 脚本何时运行。
- 工具何时暴露给上游。
- 最终返回文本、JSON 还是工具调用。

如果唯一安全，显示绿色。

如果存在歧义，只问一次：

- 哪个预设工具是终止工具。
- 哪个工具是动作工具。
- 哪个工具是内容容器。
- 客户端最终格式是什么。
- 响应字段从哪里取。

用户不需要填写工具名、schema 或内部参数，除非确认界面明确展示这些选项。

### 16.3 第三阶段：导入世界书

系统自动分类：

- 完全支持。
- 归一化后支持。
- 简化后支持。
- 无法安全简化。

条目总览显示：

- 条目名称。
- 是否启用。
- 常驻或关键词。
- 插入位置。
- 是否简化。
- 当前是否可运行。

风险项一次性确认，确认后长期保存。

### 16.4 第四阶段：配置渠道策略

用户在渠道中确认：

- 预设。
- 世界书。
- 发送处理。
- 接收处理。
- 工具协调策略。
- 失败策略。

保存的是渠道配置，不是客户端配置，也不是对话状态。

### 16.5 第五阶段：接入任意客户端

用户不需要登记客户端。

系统按当前请求契约执行：

| 请求情况 | 系统行为 |
| --- | --- |
| 唯一最终工具 | 自动协调辅助阶段和最终阶段 |
| `json_object` 且映射明确 | 自动恢复为 JSON |
| 只有纯文本 | 只有内容容器明确时恢复正文，否则纯中转 |
| 多工具或角色不明 | 不猜，保持中转或按渠道显式覆盖 |
| 历史不完整 | 按渠道阶段策略处理 |
| 旧式函数字段 | 默认不自动投影 |

五款客户端依次接入时，预设、世界书和渠道策略只配置一次。只有请求契约无法确定时，用户才做一次渠道级选择。

### 16.6 第六阶段：日常使用

用户不需要：

- 每次请求选择模式。
- 每次重新导入预设。
- 每次手动处理工具冲突。
- 维护客户端列表。
- 保存会话状态。

系统：

- 根据请求契约自动执行。
- 无法判断时标记需要处理。
- 不静默改变行为。

### 16.7 第七阶段：更换预设或世界书

更换预设：

- 重新预检。
- 对比新旧工具和能力。
- 能力报告和计划指纹失效。
- 原有渠道策略尽可能复用。
- 新增歧义只确认一次。

只更换世界书：

- 不重新配置客户端。
- 重新检查条目总览。
- 预设和工具协议保持不变。

## 17. 预期体验

完成后，用户应当能够：

- 在渠道里选择预设和世界书。
- 看到系统是否会实际生效以及为什么。
- 看到世界书命中条目、插入位置和顺序。
- 看到客户端最终收到文本、JSON 还是工具调用。
- 看到预设内部工具不会泄漏。
- 看到哪些条目被简化。
- 看到哪些请求被安全回退。
- 一键切回纯中转。
- 不维护客户端身份或客户端列表。

预期工作量：

- 导入预设：一次。
- 确认能力报告：一次。
- 处理工具角色歧义：最多一次。
- 导入世界书：一次。
- 处理世界书风险条目：最多一次。
- 配置渠道策略：一次。
- 日常使用：零配置。

## 18. 最终成品能够解决的问题

可以解决：

- 客户端最终工具和预设辅助工具冲突。
- 两个最终工具同时暴露。
- 预设内部工具泄漏。
- 世界书匹配顺序错误。
- 世界书插入位置错误。
- 响应投影后正文丢失。
- 工具角色不唯一时的乱猜。
- JSON、文本和工具三种最终格式的确定处理。
- 灰色死开关和同类配置分散。
- 下拉框风格与弹层行为不统一。

条件性解决：

- 预设终止工具包含信封和正文，需要显式字段映射。
- 纯文本客户端恢复，需要显式内容容器角色。
- 客户端不重发历史，需要渠道阶段策略。
- `<game>` 标签清理，需要接收正则位置正确。

无法保证：

- 模型不遵守 `tool_choice`。
- 客户端只在提示词中要求格式。
- 客户端和预设要求不同且不可转换的最终工具。
- 同一个请求结构需要两套不同策略且没有稳定路由边界。

## 19. 验收标准

### 19.1 不变量

- 未配置适配的渠道行为不变。
- Passthrough 行为不变。
- 鉴权、路由、渠道选择、计费、日志和重试次数不变。
- 客户端工具定义和工具历史不被修改。
- 世界书在预设前匹配、后处理前注入。
- 响应写回保留 choice、usage、reasoning、`finish_reason` 和未知字段。

### 19.2 工具协议

- 开关关闭时请求和响应不变。
- 客户端唯一最终工具被正确识别。
- 预设工具不进入最终阶段。
- 辅助阶段只暴露辅助工具。
- 最终阶段只暴露最终工具。
- 客户端最终工具响应保持工具调用。
- JSON 和文本恢复只在显式合同下发生。
- 角色不唯一时不激活。

### 19.3 世界书

- 匹配源是 `matched_messages`，即发送规则处理后、预设编译前的客户端消息。
- 注入发生在预设骨架之后、后处理和脚本之前。
- 四种插入模式行为确定。
- 顺序按低优先级到高优先级输出。
- 风险条目不会被默认自动启用。
- 不出现“开着但不会运行”。

### 19.4 响应链

- 工具恢复在协议投影之前。
- 协议投影在输出处理和接收正则之前。
- 接收正则看不到内部工具 JSON。
- 无法恢复时不输出半转换结果。
- 流式和非流式语义一致。
- 多 choice 不串组。

### 19.5 UI

- 短列表使用 `Select`。
- 长列表使用 `Combobox`。
- 下拉弹层不自动跳到上方。
- 绿色、黄色、红色和灰色状态含义一致。
- 不支持控制显示原因。
- 迁移后不再新增 `NativeSelect`。

### 19.6 回退

- 世界书失败可以跳过并诊断。
- 脚本失败不静默吞掉。
- 工具角色不唯一保持中转。
- 响应投影失败不输出半转换结果。
- 只有满足 `safe_raw` 时才允许回退到原始上游响应。
- 跨渠道重试计划不一致时拒绝。

## 20. 实施顺序

### 阶段一：冻结不变量

交付：

- 纯中转不变测试。
- 世界书顺序测试。
- 客户端工具保留测试。
- 响应字段保留测试。

### 阶段二：建立渠道策略和请求计划

交付：

- `AdaptationProfile`。
- `RequestPlan`。
- `ContractClass`。
- 计划指纹。
- 预检结果。
- 只生成、不改变响应行为。

### 阶段三：重构世界书和预设

交付：

- 统一世界书匹配和注入。
- 条目状态。
- 导入风险分级。
- 预设能力报告。
- 单一世界书注入实现。

### 阶段四：接入工具协议

交付：

- 显式工具角色。
- 客户端最终工具识别。
- 预设最终工具识别。
- 阶段判定。
- 请求投影。
- 响应恢复。
- 无法判断时不修改。

### 阶段五：重构响应链

交付：

- 单一响应处理顺序。
- 工具恢复、协议投影、输出处理和接收正则。
- 旧自动 JSON 猜测退役。
- 双重处理路径合并。

### 阶段六：统一 UI

交付：

- 适配概览。
- 能力报告。
- 世界书条目总览。
- 诊断与预览。
- `Select` 和 `Combobox` 统一。
- 旧 `NativeSelect` 退役。

### 阶段七：审计、性能和清理

交付：

- 阶段 trace。
- 安全审计。
- 快速路径。
- 缓冲边界。
- 旧路径删除。
- 全量回归测试。

## 21. 固定决策

以下决策不再反复讨论：

- 不保存客户端身份。
- 不维护客户端列表。
- 不保存会话状态。
- 请求契约驱动执行。
- 语义角色由用户、预设显式声明，或由结构唯一证明。
- 工具角色不唯一时保持中转。
- 世界书高风险简化需要一次确认。
- 纯提示词格式不自动推断。
- 响应投影必须有显式合同。
- 一个渠道只有一个适配方案，`applies_to_models` 只控制适用范围。
- 同一个请求结构需要不同策略时，用模型或渠道拆分边界。
- New API 保持中转站属性，适配只做加法，不改变主链路职责。

## 22. 最终原则

> 渠道策略清晰，请求计划冻结，执行顺序固定，自动处理只在唯一安全时发生，失败明确回退，用户永远能看到最终会发生什么。

这条原则高于单个功能是否“全自动”。任何会重新引入猜测、上下文状态或客户端身份绑定的设计，都不属于最终方案。
