入口提示词的目标措辞先固定，实施时以原内容指纹和条目 ID 核对，不做全文件“剧情→任务”的盲替换：

- 初始化：保留角色身份与内部回复机制，表达为“按照本次请求的规则、上下文和输出要求完成任务；最终结果由预设内部回复工具承载，并由中转站还原后交付”。不得写成“不使用预设工具”。
- 上下文衔接：说明下方是完整客户端对话与有效背景，不要求用户开始游戏；保留预设组装需要的边界，不能先删掉脚本依赖的标记。
- 末尾任务：表达为“根据完整上下文完成本次请求，遵守当前输出要求；只有本次任务需要创作时才续写剧情”。不拿最后一句用户话代替完整任务。
- 文风、选项、场记、游戏标签：按作者声明的创作/展示职责限定适用场景；保留实际规则内容和启用状态。客户端明确要求数据结构时不强插展示段落；不能给所有普通条目笼统加“可选”来弱化全部功能。
- 源码中的开场消息、工具描述、同步状态也要同样审查。只改可见 prompt 而遗留动态的“开始游戏”指令不算完成。

#### R3. 工具选择和结果交付的确定规则

客户端“允许工具”与内部“使用工具承载文字”是两个不同约定。客户端不能看到、也不用执行预设容器。网关不执行任何客户端业务动作。

为确实强依赖容器的预设，在现有 `ReplyAdapter` 增加最小能力字段 `require_container`，含义仅为“完成文字/JSON 回复必须经过已声明容器”。它不是一个普通用户每轮切换的开关；由这个已审查的副本及对应配置明确声明。未声明的其它预设不自动改变行为，不按名称识别。

格式边界使用独立的 `formatted_output:client_format` 声明，表示 formatter/输出处理完成后已经是客户端目标正文，结构化结果不能再进入旧的全文包装提取路径。该元数据自身不批准 JSON 转换；实际结构化请求仍须独立确认 `structured_output`，否则发送前拒绝。关闭 JSON 转换时保留格式边界，便于再次开启时不丢失原配置；缺省值仍保留旧版 text 提取行为。不能用 require_container 同时暗示格式类型，也不能通过尝试解析正文猜测走哪种处理。

请求钩子增加只读 `preset` 数据视图，与现有只读 `client` 并列；内容来自当前渠道快照，并已合入条目启用覆盖，不是浏览器或聊天存档。副本从原始静态条目预先提取 registerPart 声明，在请求时按实际启用顺序构造工具参数；不扫描客户端消息寻找控制标记。最终参数始终含必需的完整结果字段，辅助字段可空。JSON Schema 不直接写入该动态工具定义的指纹，否则不同客户端 Schema 会使同一来源绑定每轮失效；格式要求仍通过现有转换约定传递。

实施保留这些可观察的数据职责：有效声明解析、动态参数构造、原生消息/世界书保留、组件稳定排序、正文与辅助字段分离、必要输出钩子执行。不保留旧的半截 JSON 恢复为成功、强制 game 包装和浏览器账本。新的脚本代码属于这个明确授权的预设副本，网关只提供通用数据视图与协议协调，不能按名称自动替换其它导入预设源码。

| 本轮客户端要求 | 上游实际可调用集合 | 内部生成选择 | 最终允许交付 |
| --- | --- | --- | --- |
| 无本轮业务工具，或显式 none | 已确认的内部回复容器 | 单个容器指定名称；多个已声明容器时 required，禁止历史用途工具参与 | formatter/输出处理完成后的文字或合格数据，无 tool_calls |
| auto / 缺省，且有业务工具 | 客户端原业务工具 + 已声明内部回复容器 | 对 require_container 副本使用 required：业务动作或内部完成结果必须二选一 | 真实业务调用，或者还原后的最终正文；不能绕过容器直接输出普通文字 |
| required | 只有客户端业务工具 | 保持 required | 至少一个合法业务调用，不用内部容器抵充 |
| 指定客户端工具 | 只有原客户端允许的业务集合 | 保持指定工具 | 指定业务调用；关联字段不变 |
| 携带业务工具结果续传 | 根据本轮工具要求重新决定，不能根据历史猜阶段 | 依上面规则 | 历史完整保留；最终回复时仍运行预设容器链 |

auto→内部 required 是经声明的生成方式转换，不是改变客户端可见业务语义：客户端本来可以得到业务调用或完成文字，两种结果仍然都有。此能力必须由现有协调层在脚本之后、冻结之前决定；不让脚本伪装原始 client.tool_choice，也不通过晚期 param_override 偷改。若 provider 无法表达该候选集合，模型调用前报告具体能力缺口，不能降成裸模型。N 节原生 auto/none/required 回归必须新增这组已声明转换，同时保留未声明脚本改变选择会失败的保护。

客户端与内部工具同名、混合内部/业务调用、未知调用、多个不可合并容器继续拒绝歧义，不覆盖定义、不丢弃其中一半。业务调用分支没有内部结果时，该容器 formatter 不适用是正常行为；不等于关闭整个脚本。普通 content 与一个内部容器同时出现时保留已核验的“容器结果为权威来源”行为，旁白留在上游审计，不与任务结果乱拼。

首轮范围继续是现代 Chat Completions 的文字/SSE 及 tools。旧式 functions 的混合内部传输必须另行验证，不能因 modern tools 通过就宣传完全支持；现有无适配和已验证的旧式 none 行为不改变。

#### R4. 从导入到结果交付的一条数据链

1. **准备副本**：从原版和当前完整渠道设置构建候选，不从已经删去核心的 relay-native-1 倒推丢失源码。保留两个渠道各自的世界书、规则、模型、条目选择和其它设置；对来源版本不符、缺少审查过的核心块直接停止生成，原文件不覆盖。
2. **请求冻结**：原客户端约束与生效配置分别只读保存。有效历史、发送规则、世界书触发和插入、预设骨架组装沿用现有顺序；脚本只能加工本次明确来源的数据。
3. **数据脚本**：保留工具绑定、有效控制声明解析、动态工具参数、预设背景与规则加工。原生历史不压成伪 JSON、不反转义、不抽出工具消息前置、不只取 lastUserMessage。世界书位置不因脚本重新拼接而悄悄变成统一背景；需要保留来源时扩展最小通用数据视图，不能按字符串相等猜来源。
4. **生成约定**：协调层验证实际动态工具、所有权、formatter、客户端协议和 R3 转换；冻结上游约定。实际参数覆盖之后再检查，覆盖破坏约定则在发送前失败。
5. **回复还原**：只对确认的完整内部调用运行 formatter；不让 partial JSON 提取器把截断当成功。客户端业务调用不进入这个 formatter。消费后移除内部调用，并把结束原因改为正常完成；拒绝/过滤/截断保留真实状态。
6. **格式边界**：改造副本的最终正文字段原样承载任务结果，formatter 不无条件添加 game 标签或混入思考。保留确实启用且适用的其它结果组件及稳定顺序，输出钩子仍执行。formatter 的数据职责、辅助字段过滤与展示包装分别有测试，不能退成 noop。
7. **特殊结构**：显式 JSON/Schema 要求传入生成侧；内部传输是工具时，不能谎称仍受 provider 原生 response_format 强约束。使用“生成提示约束 + 确定性本地验证”，并且保留这一局限的测试证据。副本结果已是目标 JSON 时，不再做旧式全文标签清理；按 I 节仅处理明确的 JSON 字符串路径，最后验证 Schema。自然语言要求 XML/Markdown/JSON 时不另起分类模型；正文加工必须不破坏字面反斜线、引号和用户要求保留的标签。
8. **错误检查点**：可选处理失败，仅保留已完成必要还原且满足交付约定的结果。内部工具原文不是给客户端的有效检查点。不能通过 request_passthrough 关闭本次必要脚本却显示完整预设成功。
9. **流式**：本轮容器必须完整处理后交付，沿用有界缓冲和取消传播。不承诺真实逐 token 正文；验证前不发送半个容器，也不额外启动修复模型调用。

用户的日常操作仍是导入可信副本、保留需要的条目/世界书、做一次代表性检查后保存。无需为聊天、变量和业务工具续传来回关脚本。日志要能分清“请求脚本已执行”“业务工具交付”与“内部回复工具已还原”；这些是实际不同分支，不再用一个成功标志掩盖必要步骤缺失。普通用户不需要认识 think_nya 或自己重配字段名。

### A. 用户最终应该得到什么

用户导入一个可信预设，选择需要的世界书、文字清理和默认结果要求，在草稿中准备依赖并做代表性样本检查后启用。之后客户端继续提交完整请求；在已验证的支持范围内，不需要每轮决定是否运行脚本，不需要为了 JSON、工具续传等正常调用反复切换预设开关。

成立的支持承诺必须同时满足：

1. 本次任务所需的预设请求加工、回复生成方式、回复还原和必要清理实际工作，没有偷偷退回裸模型。
2. 客户端得到本次声明的文字、JSON 或业务工具调用；内部回复工具不会泄漏为客户端待执行动作。
3. 历史、当前任务、图片、工具关联和有效世界书不被网关重复、串会话或错误重排。
4. 无法兼容、上游拒绝、生成截断和格式不合格分别可见；不伪造正常结果，不无提示增加模型调用。
5. 换客户端或预设通常只需重新检查输出约定，不新增按客户端品牌、预设名、工具名写死的代码。

**中转适配的基本边界（本轮用户已明确）：客户端约束首先约束客户端可见的行为和交付结果，不要求内部生成请求与客户端请求逐字段相同。** 在已启用预设适配的渠道，客户端 `tool_choice:none` 表示不能返回供客户端执行的工具调用；中转站仍可使用已确认的预设内部回复容器，并在内部完整还原后交付文字/JSON。内部容器只承担内容生成和还原，不因此取得执行客户端业务工具或外部业务动作的权限。未启用适配的原生中转行为不变。

“核心功能保留”是功能约定，不是“脚本函数被调用过”。例如某预设必须通过回复工具和 formatter 生成完整结果，只运行它的请求钩子不能算完整支持。

不承诺任意 JavaScript、任意预设、任意自然语言格式要求或任意上游都可无配置地完整兼容。模型的语义正确率无法由网关确定性保证；能够确定性保证的是已声明的处理步骤、字段保护、结果校验和失败边界。浏览器界面、聊天存档写回、模型业务工具执行、跨轮状态服务、自动二次生成不纳入本方案。

| --- | --- | --- |
| 客户端本次需要什么 | 未加工请求的显式协议字段，加上仅补缺省项的渠道结果约定 | 不可变的客户端业务工具约束、文字格式、历史协议和交付要求 |
| 预设要怎样才能正常工作 | 有效条目、已声明的数据钩子、明确回复来源、依赖能力 | 必须运行的步骤、可选修饰、可用生成方式及还原规则 |
| 两者怎样组合 | 上述两项与真实 provider 能力 | 单次请求的内部生成约定、客户端交付约定、两者之间明确的还原步骤和允许分支 |

这三个决定扩展现有 `ClientRequirements`、预设回复约定及 `PreparedAdaptation`，不建立新的中转服务、通用工作流框架或与旧 Plan 并存的第二套控制器。诊断对象只描述决定及执行事实，不参与推断。

“适用范围”仍可让管理员显式选择某些请求不使用预设，但它不是推荐的冲突修复方式。用户选择完整预设时，已可确定的必要步骤不兼容必须在发送前指出，不能自动退化为仅请求脚本模式；只有实际响应到达后才能发现的问题，按 K 节返回运行期错误，不能声称所有失败都可提前识别。可选的“只用提示词和消息整理”必须被明确命名为功能减少，不能称为完整兼容。

### D. 必需步骤与能力声明

1. 已启用的数据请求钩子默认对本次适配请求必需；被确认的回复来源及其 formatter 默认对该来源的回复必需。必要性必须包含适用对象，不能把所有 formatter 当成每种响应都必须调用，也不能遇到冲突再将它标为可选。
2. 菜单、样式、UI 组件等只有在能与数据功能独立分开时可略过。混合脚本不能通过删除代码、吞异常或伪造浏览器 API 来裁剪。
3. 识别现有 SPreset/helper 声明，沿用已有受限运行时。可识别的插件契约用于生成配置建议，不按某一预设名称建立适配器。
4. **只有脚本接口明确支持原生输出，或存在管理员确认且实际验证的通用转换约定，才允许改变预设的回复生成方式。** 只有 `reply_adapter`、一个工具或一次成功返回，不构成这一证明。
5. 运行证据记录具体步骤的 executed/skipped/failed 和不适用原因。业务工具调用没有内部容器时，对该容器的 formatter 不适用是正常行为；但前提是已确认预设允许这条业务分支。若脚本另有覆盖所有回复的数据逻辑，必须保留，不能借“不适用”绕过。
6. 保留只读的客户端格式信息供受支持脚本主动调整。旧脚本不读取这个接口时，不声称它已自动适应新格式；不得重写其源码去伪装兼容。

SPreset 请求钩子可读取可选的 `client` 参数：`messages` 是发送规则处理后、预设组装前选定的唯一有效历史（显式 `chat_history` 优先）；`tools`、`tool_choice`、`functions`、`function_call`、`parallel_tool_calls`、`response_format` 是本轮原始客户端约束。它与可修改的 `request` 分开序列化，进入隔离运行时后递归只读，不提供持久状态、网络或工具执行权限。内部生成为 none/Schema 转换移除的控制字段仍可在该视图中读取。旧的 `({request})` 钩子保持兼容，但不会自动获得保留历史的能力。

用户已授权为本机输入资产制作可回退的协议升级副本。副本可以主动读取上述通用接口：存在原生业务工具历史时，从一开始就使用完整原生对话分支，保留顺序、调用 ID、参数、工具结果与媒体；不先压缩再追加一份原文。预设背景加工、内部回复工具、formatter 和输出处理继续运行。网关不按预设名称修改源码，不自动修补旧脚本，也不覆盖用户原文件；输入资产升级与通用网关功能分别记录证据。

界面能力结论分为“已识别”“本地处理通过”“该场景模型测试通过”“缺少能力/存在冲突”。能力声明、样本证据和未知项不可合并为一个“已准备”。

#### D1. 能力从哪里来，不把补声明的负担全部交给用户

| 依据 | 系统能确定什么 | 不能由此直接推出什么 |
| --- | --- | --- |
| 已支持的 SPreset/helper 接口、注册信息及有效配置 | 钩子位置、工具注册、参数定义、显式格式化入口和可解析设置 | 脚本允许任意改写工具选择，或支持任意客户端格式 |
| 通用接口适配器的固定输入输出约定及回归 | 该接口如何接收完整消息、保留关联、还原对应结果 | 同名但行为不同的脚本也兼容 |
| 管理员确认的来源/用途绑定与实际版本样本 | 哪个对象是内部容器、对哪些定义和场景有效 | 任意源码分支都已验证，或单次模型成功等于完整兼容 |
| 工具名称、字段叫 content、源码文本搜索 | 仅用于展示候选和诊断 | 自动所有权认领、必需步骤豁免或能力通过 |

旧脚本无需为了导入而先编写新 manifest。能够由已有接口确定的信息自动生成；未知用途只要求一次必要确认。确实缺少接口能力的，由 V0/V1 确认能否扩展通用宿主接口或适配器；只增加宿主接口而旧脚本不使用，不算解决。不得通过改预设名称判断、正则修改 JavaScript 源码或提示词补丁实现“通用兼容”。

能力记录最少包含：来源接口/版本、适用输入、允许的输出分支、各分支必需步骤、结果来源/类型、保护字段、依赖指纹和验证证据。沿用现有配置和编译结果承载，不增加自由编排语言。

#### D2. 分支执行表

| 本次分支 | 请求加工 | 容器 formatter | 输出脚本与规则 | 客户端交付 |
| --- | --- | --- | --- | --- |
| 内部容器完成文字回复 | 必需钩子执行一次 | 对实际来源执行一次 | 运行适用的必需处理和文字规则 | 普通 assistant 文字 |
| 内部容器完成结构化回复 | 同上，带明确结果约定 | 不跳过；结果进入声明的提取/转换 | 按 I 节明确的数据类型处理 | 验证后的 JSON 文本等约定形式 |
| 客户端业务工具调用 | 必需钩子执行一次，保留工具协议 | 没有内部容器则不适用 | 不处理业务参数；伴随正文按已声明范围处理 | 原业务调用及允许的伴随正文 |
| 预设支持的原生文字/结构化回复 | 必需钩子执行一次 | 仅在已证明不需要容器的分支不适用 | 保留该分支必要处理 | 原生格式或经声明转换的结果 |

这是一次响应的技术分支，不是让网关推断业务“阶段”。分支及允许集合在发送前确定，根据真实响应的协议类型选择已允许分支；不按正文措辞猜测。未声明的混合结果按 E/K 处理。脚本在分支外仍有不可分离的数据副作用时，先解决接口兼容，不能用本表删除它。

### E. 工具所有权与生成方式

工具分为客户端业务工具、已确认的预设回复容器、脚本创建的历史记录用途、未声明用途四类。工具用途来自声明和本次来源，不来自名称、数量或字段叫 content。

**默认普通请求：完整沿用预设回复链。** 不需要本轮客户端业务调用时（包括显式 none），预设可通过已确认内部回复工具返回，由原 formatter 还原，再运行必需输出处理和文字规则。客户端只收到文字，不负责执行内部回复工具；存在特殊格式要求时继续按下列格式转换规则处理。

**结构化输出：先保留预设，再检查可验证的转换。**

- 当已有明确 formatter 或字段来源能产出目标 JSON 时，内部工具可以作为上游传输方式，最终结果再按客户端 Schema 验证。客户端的 Schema 要求保存在交付约定中，不因为内部传输使用 tools 就丢失。
- 此路径可能不使用 provider 的原生 `response_format` 字段；必须是渠道已确认的格式转换能力，原始客户端约束仍保留，日志显示“转换后校验”，不能谎称上游原生 Schema 约束仍在工作。未确认转换时不自行移除该字段。只将格式约束传给生成侧，不重新追加原始业务消息。
- formatter 输出固定故事/标签且没有合法结果提取方式时，不能通用地“猜 JSON”。应显示缺少结果来源，不静默关 formatter。
- 转换不能证明模型将始终生成正确 JSON；不合格结果被明确阻止，且不自动补写或二次生成。

**客户端业务工具：不执行、不冒充、不改变调用语义。**

- `required`/指定名称只允许满足客户端要求的业务调用；预设容器不能冒充 required 调用。
- **本期确定：显式 `none` 禁止客户端业务调用，不禁止适配链内部回复容器。** 本轮不向生成侧提供可调用的客户端业务工具；需要回复容器的预设继续使用它，由原 formatter、必需脚本和适用规则还原。最终只能交付符合约定的文字/JSON，不携带 `tool_calls` 或旧式 `function_call`。客户端工具定义和历史仍保留在只读原请求/有效历史中，不因本轮不可调用而删除历史。
- 缺省/`auto` 允许业务调用或完成回复。只有预设声明允许业务工具分支，且 provider 能表达所需候选集合时，才可同时提供业务工具与内部回复容器。内部容器代表“完成回复”，不是客户端业务动作；恢复完成后按文字/JSON 要求交付。对 R3 中明确声明 `require_container` 的副本，由协调层把内部生成选择转换成联合集合的 required，避免最终正文绕过必需容器；未声明预设不改变。
- 预设脚本强制其唯一回复工具而不支持协商时，不能擅自改成 auto 来宣称完整保留。候选集合转换必须有副本能力声明、最终发送 guard 和正向实测，不能靠工具注册或一次碰巧调用证明。
- 同一 choice 混合业务调用与内部回复容器、多个未声明可合并的回复容器时，不丢弃一半结果；默认返回明确不兼容响应。普通 content+业务调用按原协议保留，文字清理不碰业务参数。

**同名来源必须按本轮候选集合处理。** 客户端与预设的同名定义在输入侧仍各有来源，不能仅按名字认领。如果本轮要同时提供两个不同用途的同名工具，准备时指出歧义，不任意覆盖或改名。客户端 none 时其业务定义不在可调用集合中，不能仅因它与内部容器同名就报冲突；本轮实际生成的调用按冻结的内部定义还原，但原客户端历史不能据此被消费或改写。若要将客户端自己携带的定义当成回复容器消费，仍需确认用途并绑定作用范围、定义版本、结果来源和 formatter。定义变化需重新检查，不隐式补充它未声明的正文字段。

这解决的是工具职责，不建立“辅助阶段/最终阶段”业务编排，也不让网关自动调用模型返回的工具。

**客户端边界与内部传输的统一规则：**本期批准两类通用适配：内部容器还原为最终回复；在明确可转换的结果来源上实现客户端格式约定。客户端 none 与内部容器可以共存；客户端 required 则不能由隐藏容器冒充业务调用。这是同一条“交付语义不变、内部传输可适配”的规则，不增加按客户端品牌判断的例外，也不新增一个让用户逐轮选择的 none 开关。

内部上游的工具选择可按已确认预设能力使用指定容器或 required，与原客户端 none 不同属于预先计划的转换，不是晚期覆盖。最终 guard 必须分别检查内部工具集合/选择和客户端交付结果。仅因工具调用被隐藏不代表合法：未知工具、客户端业务工具、具有外部业务动作的工具不能认定为回复容器；不能执行它们后删除记录来伪装 none 合规。none 消除了本轮业务工具候选冲突，但不自动解决 JSON 格式、上下文、同名来源或脚本本身的不兼容。

#### E1. 结构化输出的生成路线，不只设计事后校验

选择顺序由已确认能力决定，不靠一次模型回复猜测：

1. 能保留必要预设功能，且实际 provider 支持客户端原生格式约束时，优先保留原生约束。
2. 预设必须使用容器时，确认输出数据在原 formatter 后仍可获得；明确最终 Schema/格式通过哪个已有接口、受支持宿主上下文或结构化输入传入生成侧。若只允许文本提示，记录“提示约束 + 本地校验”，不等同原生强约束。
3. 容器字段是对象、JSON 字符串还是普通正文必须确定；不擅自修改客户端工具 Schema，不给预设容器增加未经接口支持的字段。
4. formatter、必要输出脚本和规则的输入输出类型串联必须成立；声明 Pointer 不代表可以跳过原 formatter 的必要作用。
5. 原生和转换路径均不成立时，在模型调用前报告具体缺失能力。数据实际生成不合格则属于运行期失败，不切换另一条路线重新请求模型。

V2 必须验证生成侧确实收到格式要求、最终结果确实保留预设作用，以及成功样本比例；“错误结果被拦住”另行统计。不新增通用 JSON 修补器，不自动删除正文/思考段去碰运气提取结构。

### F. 常见情况的确定行为

| 请求情况 | 完整保留预设的实现方式 | 无法满足时 |
| --- | --- | --- |
| 普通文字 | 原请求钩子、内部回复工具、formatter、必要清理 | 显示实际缺失步骤 |
| 提示词要求 Markdown/XML/JSON，但无协议字段 | 仍运行完整预设；渠道可预先声明默认结果检查 | 未配置检查则只能说文字已交付，不能声称符合自然语言要求 |
| `json_object`/Schema，无工具冲突 | 已确认的容器结果转换并验证，或预设明确支持的原生结构化模式 | 未知转换、必要 formatter 不可保留则发送前指出冲突 |
| `tools:auto` | 经声明和验收的业务工具+完成回复分支；require_container 副本按 R3 约束内部传输，或使用明确支持的原生模式 | 不擅自强迫客户端业务动作，不静默删除预设工具 |
| `required`/指定客户端工具 | 保留请求加工；只有预设声明允许该业务调用分支才可用 | 不用私有工具冒充，不为结果套另一个调用 |
| 显式 `none` | 保留内部回复容器和还原链，或使用预设支持的原生回复方式；最终不返回工具调用 | 内部来源/还原能力缺失时明确失败，不能仅因 none 判定冲突 |
| 工具历史续传，甚至不再声明 tools | 保留原历史顺序与关联，本次工具可用性另行判断 | 不凭有历史自动启用/停用预设或猜下一阶段 |
| 客户端携带仅思考字段工具，却希望获得独立任务结果 | 先确认这是业务工具还是已声明回复容器，并核对结果来源 | 无结果承载方式则明确指出定义不满足用途，不伪造结果字段 |
| 多 choice、混合多模态或其他 API 入口 | 仅在当前适配器声明支持并通过对应验收时处理 | 不将 Chat Completions 测试扩张为全部协议支持 |

首轮承诺范围为现有 Chat Completions 入口及其非流式/SSE。旧式 functions、各 provider 的原生入口和不透明签名分别验收；不能为跑通例子删除字段、改名或补造签名。

### G. 请求链与最后一道保护

固定顺序：

```text
原始请求只读快照 + 当前生效配置/依赖版本快照
  → 适用范围、客户端约束与可提前判定的冲突
  → 有效历史、发送规则
  → 世界书匹配、定位及预设组装
  → 请求脚本（一次）
  → 完整兼容性检查、冻结本次处理决定
  → 原生 provider 转换与渠道参数覆盖
  → 最终发送约束检查
  → 上游
```

渠道参数覆盖不得在已检查之后悄悄改变内部 tools、tool_choice、生成侧格式要求、历史协议或已冻结的消息内容。适配请求要在最终发送前检查实际生效字段；不只查看旧 DTO。校验基准是已冻结的内部生成约定，不是要求内部字段与原客户端字段相等；客户端约束另在交付侧验证。none→内部容器 required、Schema→已批准容器转换等差异必须有明确的转换记录。

- 在保存/预览阶段尽早指出可判定的冲突；条件覆盖仍需请求时检查。
- 不在计划阶段提前完整执行一次 override 再在发送阶段执行第二次，避免条件、副作用或数组追加重复。保留现有实际执行位置，使用执行后的语义结果核验。
- provider 字段映射通过现有适配器做语义比较，不拿不同协议的 JSON 字符串直接相等比较。没有可靠映射的组合不宣称支持。
- 仅适配请求受新增冻结约束；未配置适配的原生中转保留其行为。正常模型路由和非保护参数仍沿用原生逻辑，不顺带改计费或鉴权。
- 最终校验通过后不再有可修改受保护内容的处理阶段。参数覆盖违反内部方案地改成 none、删除必要容器、改生成约束或改消息等均要有对应回归；原客户端 none 被合法转换为内部容器生成不能误报。
- 客户端显式要求优先；渠道输出默认只填缺省项。不能用另一层默认覆盖客户端 auto，再称其为客户端要求。

请求脚本接收完整、来源明确的有效消息，以及受支持接口提供的只读客户端要求；不能先删除所有协议字段再假定脚本会正确整理工具历史。宿主可提供数据视图，但该视图和最终上游消息不是同一对象。动态工具定义和输出约定需在脚本执行后核对，再冻结；不能为探测动态行为重复执行脚本。必要字段比较使用规范化语义，不把 JSON 键顺序变化当冲突。

### H. 历史与当前任务不能靠补贴原文维护

原请求和显式替代历史选定后只有一个有效历史来源。不把两个来源拼在一起；不跨会话读取“最近一次请求”；本次状态结束即释放。

- 客户端工具调用与对应结果作为完整关联区块处理，保留原始顺序、ID、参数、结果及已支持的不透明字段。上下文可以被明确授权加工，但不能把所有工具历史抽出前置，随后再拼一份当前上下文。
- 脚本创建的合成历史与客户端真实工具历史分别标记来源。能在目标 provider 合法表达时保留其原语义；没有完整关联或无法承载时不能生成假的工具结果。
- 仅供数据脚本读取的视图与最终模型请求分开。内部序列化信封不默认作为完整 assistant 文本注入；若确需文字历史投影，必须由明确适配器按已声明字段生成，并在预览展示，不能把任意参数反复 stringify。
- 保留网关侧消息来源标记及世界书锚点。能维护标记的受支持脚本使用它们；任意旧脚本彻底重建 messages 且丢失关联时，不能伪称可恢复所有历史。该组合需要明确脚本接口或被标为不支持。
- 不通过“最后一条 assistant 后面的消息就是任务”判断业务，不用关键词发现“变量请求”。本轮任务来自客户端完整有效请求；格式要求来自显式协议或渠道预先配置。
- 脚本正常改变/压缩内容后，不再把原消息追加回去。对于把任务变成示例、遗失有效消息的缺陷，通过具体脚本接口和可复现样本修复，不用通用尾部提示词保证语义。

**多轮连续性必须单独成立。** 客户端下一轮只会带它实际收到的文字/业务调用，不一定携带上一轮被消费的内部容器、脚本临时变量或 provider 元数据。不能依靠网关保存“上次脚本状态”补齐。V3 要验证实际脚本能否由客户端完整请求继续工作；需要私有持久状态才能运行的能力本期不承诺。仅靠文字相等不能证明恢复了消息来源；对彻底重建消息的接口，必须有明确关联规则或受支持的接口改进，不引入按内容相似度猜测原消息的算法。

### I. 回复处理、JSON 和变量结果

统一执行 `完整协议解析 → 按来源还原 → 必需输出处理 → 适用清理 → 结果验证 → 一次交付`。原始上游、各检查点和最终结果分开保存，不原地改坏上一份有效结果。

1. 已声明内部容器只调用一次原 formatter/提取器；真实工具参数是完整合法对象才允许还原。工具协议的 arguments 是 JSON 字符串，解析一次；已得到字符串后不循环反转义。
2. 客户端业务工具的名字、ID、参数及不透明字段保持协议语义，不进入正文正则。若明确约定要处理某些工具参数，那是另一种转换能力，首轮不支持。
3. 普通文本继续执行原预设必需输出钩子及接收规则。结果原本是 JSON 文本时，可按预先声明的“文本清理后解析”路径处理，但必须最终验证；不能从大段回答中自动搜索第一个大括号。
4. 原生 JSON 或已恢复的结构化对象不交给整段字符串正则。需要处理其中字符串时只使用明确 Pointer；操作后再次验证。对于必需全文脚本不适用的情况，在发送前判定能力，不能事后静默跳过。
5. 增加标准 JSON Schema 本地校验能力用于已转换结果；使用成熟库，不手写子集解释器。V2 固定库版本、方言、支持的校验关键字、format 行为及引用范围后再实施。禁止运行时远程 `$ref` 获取；不支持的断言/引用形式在准备时明确报告；不把允许的注释或扩展元数据误当校验能力，也不忽略未知断言后声称完整验证。
6. 原生 Schema 路径与转换 Schema 路径分别报告 provider 约束是否启用、本地实际验证范围。类型、必填、额外字段、嵌套数组和组合 Schema 均须通过该支持范围的测试；不把“JSON 能解析”称为满足 Schema。
7. 对于变量更新，复用通用结果检查入口：用户可一次声明纯 JSON、指定标签中的 JSON/JSON Patch、或文字。标签/路径是配置，不硬编码某个预设的 UpdateVariable 名称；严格检查完整包装及内部 JSON，不生成不存在的补丁。
8. JSON Patch 只验证支持操作、字段和路径语法，不在网关修改客户端状态。验收客户端能否应用，使用测试客户端持有的已知初始状态；真实状态缺失时，日志只报告语法通过，不能保证路径存在或数值业务正确。
9. 未声明格式的普通文字不能可靠判定“是否答对”。不得通过匹配拒绝语、context_only 等词硬删正文；显式结果检查失败时报告不合格，未配置时明确显示“未检查业务格式”。

内部容器已成功消费时，交付信封也必须完成转换：不残留内部 `tool_calls`、`function_call` 或“等待工具执行”的结束原因；按对应客户端协议输出已完成文字/JSON。拒绝、过滤、截断不能借此转换成正常完成。SSE 的角色、正文、完成和终止事件由现有 writer 一致生成；非流式与流式解析后的交付语义相同。正文正确但结束原因仍要求客户端执行工具，同样判为失败。

客户端只在自然语言中说“必须 JSON”的兼容性，不能由网关永久保证。一次性渠道默认结果检查或客户端标准 response_format 是可靠的配置入口，不新增按自然语言动态猜测格式的模型调用。

### J. 世界书与规则继续共用现有机制

世界书匹配基于发送规则处理后的有效客户端历史；预设提示词不反过来触发世界书。命中内容在预设骨架中按目标位置插入，然后进入请求脚本，不在脚本后补插。

保留已实现的 v2 锚点：定义前/后、系统背景区、最新用户前、聊天深度；同位置稳定排序，工具关联区块不拆分。缺失插槽的明确回退及预算不足要显示实际原因。预览和实发使用相同配置、宏上下文与执行函数。脚本重排后的精确语义位置无法普遍追踪，不伪造逐条定位。

插入位置在界面和日志明确为**“预设组装时的位置，在请求脚本之前”**，不能无条件承诺是最终上游位置。脚本保持消息来源时可额外显示最终位置；重组/合并后只能展示可证明的保留情况。若用户要求严格最终位置而脚本不能保留，准备阶段报告该约束不支持，不在脚本后偷偷补一份世界书。

世界书诊断分别展示：未触发/已命中、已插入/因预算或禁用未插入、已交给脚本、最终位置可确认/脚本已重组无法精确定位。不能因为“命中”就表示最终模型使用了背景；语义参与由固定正常样本验收，不靠日志字符串搜索证明。V3 还需确认深度计数、同位置排序的比较键、完整工具区块边界和缺失锚点回退；记录当前规则并测试，不趁机重写整个匹配算法。

正则保留发送/接收方向、适用目标和来源身份；同源关联副本只运行一次，独立规则不按名称去重，关闭项不复活。可选展示美化不作为 API 正文生成步骤，必要提取与可选清理分开标识。

不重写已经验证的世界书匹配器、编辑器和受限正则引擎。新增验收要证明这些内容进入实际脚本并影响正常样本结果，而不是只证明“已命中”。

### K. 可用性、失败、流式与性能

可用性优先指“保留已验证且仍满足约定的结果”，不是失败就发送任意原文。

| 情况 | 默认决策 |
| --- | --- |
| 独立可选世界书失败 | 可跳过并明确记录；声明为必需背景时不能跳过 |
| 必需请求脚本或回复来源失败 | 不静默取消预设；发送前终止或返回明确适配错误 |
| 可选输出修饰/清理失败 | 保留此前已满足所有必要步骤及结果约定的检查点 |
| 容器恢复失败、必需清理失败、最终格式不合格 | 不泄漏内部调用、不返回半成品、不填空对象冒充成功 |
| 协议明确拒绝/过滤/截断 | 保留真实状态，不能改成成功；有内容也不能自动视为有效变量结果 |
| 普通文字表达拒绝而无协议标识 | 不靠关键词确定性分类；按已声明结果检查决定可否交付，不自动重试绕过 |

对于依赖完整容器、正则或 Schema 验证的回复，保持有界缓冲后再交付。无加工的原生流不新增完整缓冲；已写出数据后不切换策略、不重新发另一份答案。按 choice/tool index 组装 SSE，不按网络块解析；取消、超时、截断释放资源，不能为凑完整结果保留后台生成任务。

请求脚本每次逻辑请求执行一次；同配置上游网络重试复用冻结结果和独立响应缓冲。拒绝、格式错误、脚本错误不触发额外模型生成；跨渠道候选需要等价配置及能力，不在失败后改用裸模型。沿用原生次数和计费，不增加隐式成本。

保存只做本地必要解析校验；依赖准备和模型测试是独立动作。编译缓存限定于配置/源码等静态产物，不缓存可变聊天状态。保留执行时限、内存、并发准入和内容大小约束；在目标 VPS 测量必要并发下的 CPU、内存及首字延迟，不能只凭常量宣称容量达标。

#### K1. 流式不是把已完成的回复伪装成实时生成

- 发送前确定“原生实时转发”或“完整处理后交付”。后者仍可按客户端要求使用 SSE 信封，但用户可见首段正文要等完整处理结束；样本检查及日志明确显示这一点。
- 默认完整缓冲路径在验证成功前不提交响应头或正文，保留返回标准 HTTP 错误的能力。客户端、反向代理和上游的等待时限由 V4 核对；不得无限延长或向上游偷偷增加生成请求。
- 如果实际客户端必须靠保活维持连接，V4 单独验证 SSE 注释保活和提交响应后的错误信封。保活一旦提交响应，就不能再返回不同 HTTP 状态；错误必须走该客户端能识别的流内错误并终止，不发送伪造的成功完成事件。未验证前不默认启用，不用空正文事件骗取“首字已到达”指标。
- 不同时承诺“整份结果验证后才输出”和“即时输出未经验证的正文”。若客户端超时要求无法满足完整处理链，提前显示已知限制；不能默认关预设、关验证或漏出半个容器来假装解决。
- 取消和到期必须传播到脚本、HTTP 上游和缓冲读取；释放本地资源并终止本地后续处理，不承诺远端供应商一定停止已收到的生成任务。

#### K2. 错误类型、重复请求与可恢复性

复用现有错误信封，增加稳定的适配错误分类和请求 ID；具体序列化接口在 V4 对照现有 writer 确定，不另建错误系统。

| 情况 | 未提交响应时的目标行为 | 重试含义 |
| --- | --- | --- |
| 输入/静态能力不兼容 | 400，指出冲突来源及修改位置 | 同输入同配置不应自动重试 |
| 配置已失效、运行时代码异常 | 明确配置/执行错误，不冒充上游拒绝 | 不触发模型重试；管理员处理后重试 |
| 模型已返回但容器/结果校验失败 | 错误信封保留“交付不合格”的独立分类，不放进正常 assistant 正文 | 本网关不自动重生成；模型是否已调用必须可见 |
| 本地并发准入不足/等待到期 | 沿用原生资源繁忙/超时语义，并标明发生阶段 | 调用方可决定稍后重试；不为补偿自动生成 |
| 已提交 SSE 后失败 | 流内错误并结束；不能倒改 HTTP 状态或回到原文放行 | 不在同一响应中开始第二份答案 |

V4 必须落定运行期失败的具体 HTTP 状态、机器码及测试客户端行为；这是实施前必填项，不能临时把所有失败改成 200 或 400。可提供 `retryable` 等诊断，但不能声称任意客户端都遵守。客户端自行重试会产生新的入口请求；一次点击不等于一次 HTTP 请求。复用请求 ID/尝试关联区分入口次数与上游尝试次数，不按相同正文擅自去重，也不新建会话存储或端到端 exactly-once 承诺。

#### K3. 配置与依赖作为一个固定运行版本

1. 继续使用现有配置存储/缓存。一次运行版本由预设有效条目、脚本源码及依赖内容摘要、回复来源、规则、世界书和输出约定共同确定；请求开始后持有不可变快照。
2. 编辑和准备依赖发生在候选配置中。下载或编译失败不覆盖当前生效版本；本地保存草稿不代表已切换运行版本。若现有页面仅有保存/启用一体动作，启用前先完成必要准备，再原子替换，不能先换一半再下载另一半。
3. 外部网址脚本按已准备的内容版本运行，请求链不实时重新下载；更新依赖是明确动作，形成新候选版本和差异，不悄悄改变已验收版本。继续沿用现有获取限制和信任确认，不扩大脚本网络能力。
4. 一个请求不能使用旧预设配新规则/新依赖。更新只影响之后的新请求，进行中请求继续原快照；回退也回退完整适配配置及可用依赖，不只回退一个开关。
5. 同源模块可共享只读编译缓存，脚本变量、事件、消息及临时结果不共享。并发准备结果用配置版本核对，过期结果不得覆盖新候选。
6. 动态客户端工具 Schema 不导致渠道永久进入“待重新验收”；按已支持的结构范围逐请求验证。只有绑定为内部回复来源的定义发生语义变化，才使该绑定失效；仅 JSON 键顺序变化不算新能力。

#### K4. 性能验收先定界线再测

V4 先记录目标 VPS 资源、典型与最长正常请求、实际客户端超时、计划并发及现有基线，再固定准入上限、队列等待、脚本时限、单响应缓冲及总体内存预算。数字必须在测试前写入本节的执行记录；当前尚未测量，不填虚假的容量承诺。

至少区分：准备/保存耗时、不含模型等待的适配开销、上游生成时间、首段有效正文时间、完整交付时间、峰值内存和取消后资源释放。用少量代表性正常请求比较原路径与候选路径；完整缓冲路径不以网络保活作为首字。超出预定界线先定位瓶颈，不能靠无上限缓冲/并发或放宽全部超时通过。没有固定界线与实测证据，不允许标为性能验收通过。

### L. 用户界面与实际操作

主界面只保留四个已有入口：预设、世界书、回复处理、样本检查。现有二级编辑方式保留，不把脚本、规则和所有技术参数重新展开成超长渠道表单。

用户操作：

1. 导入预设，保留其有效条目和手动开关；确认可信的数据脚本。显示实际文件名、启用步骤、已略过界面功能及缺少能力。
2. 确认系统依据已声明 formatter 提出的回复来源；多来源或未知用途才要求选择，不让每次导入都手填工具名。
3. 可选世界书和文字规则。条目总览能看启用、触发方式、位置和顺序。
4. 回复要求默认跟随客户端；没有显式协议的固定用途，可在该渠道一次设置默认结果检查。它不禁用工具、不改业务工具定义、不隐式复制另一套预设。
5. 使用样本检查。免费本地预览和一次真实模型测试分开；报告请求加工、生成方式、还原/清理、最终格式及预期样本断言。检查只覆盖显示的版本和场景。
6. 保存后日常无需干预。换预设、关键脚本、结果来源、模型能力或格式约定时，仅让相关检查过期；迟到异步结果不能覆盖新配置。

用户默认只需理解：使用哪个预设、哪些世界书启用、回复需要怎样清理、客户端最终需要什么。内部容器选择、分支必要步骤、协议转换差异由识别结果和处理计划显示，不变成一排用户必须逐项理解的开关。none 时可以显示“客户端接收文字；预设回复工具在内部处理”，不能提示用户把客户端改成允许业务调用才能使用预设。

通用渠道默认不强制变量补丁格式。固定用途结果约定只作用于明确选择的范围；复用已有模型匹配/路由能力表达用途，必要时由不同模型别名选择，不按 User-Agent、提示词关键词或最近请求猜测。若现有配置不能共享预设且区分默认结果要求，先在 V5 评估最小扩展；不能无声复制多份可独立漂移的预设，也不为了此项新建配置平台。用途范围重叠/优先级不明确时保存前提示。客户端显式格式优先于缺省值，但不能绕过预设必要处理。

主要状态使用“请求整理已执行”“回复工具未启用”“回复还原未执行”“结果格式不符合要求”等实际事实。技术码、Schema 原文和兼容性细节放在详情。不能将所有步骤压成一个“成功”，也不能为每个步骤增加一个普通用户必须理解的技术开关。

界面显示失败时应指出冲突双方和可操作位置，例如“预设回复工具没有可用的还原方式，无法转换为客户端文字”，而不是笼统 `script-failed`。客户端 none 且内部容器可还原是正常支持场景，不能显示成冲突。不得把未支持、未检查和检查失败混在同一种状态。

#### M0. 2026-11-10 本地实施记录

本记录对应 `97dac7cad` 上的实施工作区。没有修改线上渠道，也没有提交私人预设源码。正常测试预设的真实模型正向验收与私人数据核心离线检查分别记录，二者不能拼接成“私人预设完整验收”。

**已实现的本地路径：**

- 客户端显式 `tool_choice:none` 或旧式 `function_call:"none"` 时，先保存客户端约定，仅从本轮可调用集合中分离客户端业务工具。预设仍运行原请求钩子、已确认回复容器、原 formatter、必需输出钩子和接收正则；不是 `nativeDelivery` 绕过。
- 客户端交付约定与脚本生成后的内部请求分别冻结。真实请求准备与最终请求预览共用 `SealClientRequirements`；两份约定必须与本次编译对应。
- 现有 relay 在字段过滤和参数覆盖之后检查内部生成关键字段。覆盖工具选择、定义或消息会在发送前终止，返回 400 且不跨渠道重试；普通温度覆盖不受影响。当前是对覆盖阶段的保护，不是对任意 provider 转换做完整语义认证。
- 补充流式/非流式、同名工具、保留工具历史的通用脚本、旧式 none、合法转义、缺失必需容器、标准拒绝与未知工具泄漏回归。原客户端请求不被修改，缺少内部容器不能当作完整预设回复成功。
- 完整回复校验拒绝单个信封/事件中重复的候选编号、单个流式事件中重复的工具编号、同一候选内重复的调用 ID，以及混用或擅自切换旧式/现代工具协议。不同事件中同一编号的合法分片仍正常累积，空 ID 分片不抹掉已有关联；不能通过把两个歧义项拼起来制造合法 JSON。结束标记与正文共用同一 SSE 解析结果，兼容 CR/LF/CRLF、注释和无空格的 `data:[DONE]`，仍拒绝终止后追加数据及未完成的流。
- 已删除 `compilePresetWithClientDelivery`、`presetClientContextMessages` 与 `nativeDelivery` 分支；原 `delivery_mode` 字段不能再覆盖工具来源、跳过 formatter 或前置历史。保留客户端选择及完整工具消息的通用请求钩子，可在 `auto` 下联合提供业务工具和已确认回复容器；`required`/指定名称只提供客户端业务工具。每轮仍独立处理完整客户端请求，无网关跨轮状态。
- `reply_adapter.structured_output` 是一次确认的格式转换能力，不是上游原生 Schema 保证。启用后只将客户端格式约定交给生成端，不补发业务原文；回复依次经过原 formatter、完整文本输出钩子、已声明文字清理，再进行最终 JSON/Schema 校验。输出钩子不再因 JSON 分支被跳过，也不按 JSON 字段重复调用。业务工具调用不进入正文清理；同时携带 tools 与 response_format 时，格式要求只约束最终文字分支。
- JSON Schema 使用固定依赖 `github.com/santhosh-tekuri/jsonschema/v6 v6.0.2`；默认方言 Draft 2020-12，明确声明的库内置方言按其规则处理。内联 `$defs`/`$ref` 可用，禁止加载外部 URL/本地文件/未知外部元 Schema，输入 Schema 最大 256 KiB。没有额外启用 `AssertFormat`，`format` 不应被宣传为统一强制断言；正则使用库默认的 Go 正则引擎，无法编译的表达式在准备阶段失败。保留 JSON 数字精度，不用浮点数近似来验证整数约束。未知扩展关键字不构成已验证的额外断言。
- 界面使用已有回复来源编辑器和开关组件，增加明确的 JSON 转换说明；编辑来源保留该确认，删除全部来源则清除确认。检查报告仍显示“未做模型验收”，不能以开关开启或本地通过宣称实际模型兼容。
- Responses 桥接和请求正文透传尚未接入内部约定保护，暂不允许使用该原型路径。

V0 后先走通 P1/P2，再做 P3/P4；不能从最复杂混合工具开始同时改所有层。V1–V3 的共同证据必须来自一套可以串起来的请求/回复链，不能拿互相不兼容的三个原型各自成功拼成“整体通过”。真实模型只使用正常输入；拒绝和非法响应等反例以确定性样本覆盖。当前已经取得实施授权，仍须逐项满足关卡，不能将授权等同于兼容性已成立。

**实验记录必须包含**：代码/配置/模型与依赖版本、预先固定的预期、实际路径、通过和失败次数、失败归因、所需改动、决定继续/修订/暂停。可复用现有测试和本机验收记录，不把真实聊天、密钥或整份私人预设提交仓库。一次真实成功只证明该样本，不升级为任意输入保证。

职责边界固定如下，具体字段名可随现有代码合理调整：

| 边界 | 负责 | 不负责 |
| --- | --- | --- |
| 客户端约定 | 记录原始可见工具约束、格式、历史及缺省用途 | 直接规定内部容器必须禁用 |
| 预设能力/编译 | 已支持接口、必要步骤范围、消息处理和版本 | 推测用户业务阶段、修改脚本源码以适配某预设名 |
| 单次处理决定 | 内部生成约定、允许响应分支、转换与交付验证 | 自己再执行一套脚本、正则或路由 |
| provider 最终检查 | 对照内部生成约定核对实际发送语义 | 将内部请求和原客户端字段机械比较 |
| 回复处理 | 单次还原、必需后处理、类型明确的规则与交付检查 | 执行业务工具、自动再生成、语义猜测修补 |
| 现有 UI/诊断 | 展示版本、实际处理和可操作原因 | 通过前端推测补齐服务端未实现的能力 |

移除旧执行路径要追踪调用点并替换其有效行为；不因文件名包含 preset 就整文件删掉。`nativeDelivery` 不能继续作为“所有内部回复处理均不运行”的笼统开关。旧配置只为当前已知渠道备份和显示差异，不新建复杂迁移平台，也不自动对线上渠道撤掉保护或开启工具。

已有业务渠道在新路径通过前不改。特别是当前变量渠道的禁用工具、关闭条目、结果来源需要一起重新检查，不能只删除 none 就声称修好。不得为改善含不安全内容的请求而调整预设绕过上游拒绝；工程验收使用正常任务资料。

小范围发布使用隔离模型别名/测试渠道及已确认配置，不把同一个真实请求额外发送两遍做影子比较。发布前保存代码版本和完整适配版本；部署失败或关键正向路径退化时停止扩大范围，恢复已确认回退点。回退只能恢复此前行为，不能声称此前已有缺陷也被治好。原型通过后清理重复控制分支，不能把临时路径长期并存称为重构完成。

### N. 真正的验收与停止条件

必须分清三项独立结论：**必要功能实际参与、交付格式合格、样本业务结果正确。** 没有业务验证条件的普通文本只报告前两项及未检查项。

| 样本 | 必须观察的结果 |
| --- | --- |
| 真实预设核心脚本 + 正常用户任务 | 容器完成回复时，请求脚本、实际回复工具、原 formatter 及必需规则均参与；业务调用分支按 D2 验收，不硬调用无关 formatter；不能换简化脚本替代 |
| 变量更新 | 测试客户端从已知初始状态应用返回操作，达到预期状态；不是只检查存在 JSONPatch 标签 |
| 仅提示词 JSON 与显式 Schema | 前者在配置了结果约定时验证；后者验证完整支持的 Schema，并保留所声明的必要预设步骤 |
| 普通文字、表格、自定义标签 | 当前任务被完成，无历史信封冒充答案，无不相关预设开场；未配置泛化验证时不宣称所有提示词均保证 |
| 客户端 auto/none/required/指定名称 | none 下内部容器正常生成、还原且无客户端工具调用；auto/required/指定名称的业务分支真实工作；分别有非法泄漏反例，不依靠上游全局 none 让文字测试通过 |
| 多轮工具、并行倒序结果、无 tools 的续传 | 同一测试客户端使用上一轮真实调用 ID 和结果；历史顺序和当前任务保持正确 |
| 同名工具、仅思考字段、多字段回复来源 | 无所有权猜测、无字段补造；未知用途必须清楚失败 |
| 世界书前后/深度/用户前 | 预设脚本前命中和插入，实际结果使用只在世界书出现的正常事实；关闭项不出现 |
| JSON 转义、Windows 路径、引号、数字和 null、多模态 | 解析后的实际值正确，不全局反转义、不丢字段、不重复图片 |
| SSE 分片、截断、超限、取消、混合调用、多 choice | 不交付半个内部容器；结束状态正确；缓冲资源释放 |
| 最终发送前的参数覆盖冲突 | 对照内部生成约定阻止非法覆盖，不误报合法客户端 none→内部容器转换；预览不能与实发各说一套 |
| 可选失败和必需失败 | 前者仅返回合格检查点，后者不被 passthrough 吞掉 |
| 两个渠道、多个同时请求、重试 | 配置与临时状态隔离，脚本/规则不重复，没有额外生成请求 |
| 新导入→配置→本地预览→真实测试→保存→新会话 | 桌面及窄屏实际操作通过，条目/高级 JSON 不撑宽页面，状态和当前版本相符 |
| 更新依赖/保存失败/回退/并发编辑 | 当前版本不受失败候选污染，运行请求不混用版本，过期结果不覆盖新编辑 |
| 同一客户端交替聊天、变量、总结 | 按显式字段/已配置用途处理，不猜测任务，不要求每轮开关脚本；未声明格式不伪称验证 |

用户实际预设只在本机授权环境测试，使用正常、无敏感的验收输入；核心脚本不换成简化脚本充当它。其源码与启用功能指纹要记录在本地证据，必要功能不能关闭后又报告通过。若预设其他内容使测试本身不适合发送，核心脚本仅作离线验收，完整真实验收必须标未完成，不能隐瞒替换测试材料的差异。

真实模型验收至少覆盖普通两轮、正常变量更新、结构化输出、业务工具续传、世界书参与和 SSE。P1–P4 各预先选定至少三个有不同实质输入的正常场景，可复用同一端到端会话覆盖多项，不机械相乘增加调用。该固定场景组必须全部满足功能、格式和业务断言；出现失败保留记录、分析归因，修复后重跑受影响场景，不能丢弃失败样本只保留重试成功。有限样本不是生产成功率/SLA 证明，不把 3/3 写成长期 100%。

每次验收分别报告：正向任务成功/总数、错误响应被正确拒绝/总数、上游拒绝/服务故障、未支持/未验证项，以及实际模型调用数。协议反例、非法 JSON、超时等用确定性 fixture 检查，不为了数字好看重复付费调用。确定性路径回归必须全部通过；真实上游故障不伪装代码成功，无法完成时标为未完成。

验收必须先固定预期，不能看到模型结果后修改标准。四个最小业务样本如下：

- **变量样本**：测试客户端持有 `{"credits":10,"items":[]}`，任务是花费 2 点并加入一件明确定义的物品。应用返回操作后必须得到 `credits=8` 和指定物品；只有说明、仅思考、返回原状态、无约定的空补丁均失败。另设真实“无需更改”的样本，防止把合法空补丁一概当错。
- **预设作用样本**：固定实际脚本本来具有的可观察作用，例如请求结构转换和 formatter 的包装/提取，再提供只存在于预设/世界书的正常事实。运行记录与结果共同证明这些作用。实际 formatter 若是恒等操作，核对它的输入和执行证据，不为了制造变化去修改真实脚本。另用确定性测试脚本验证宿主调用次序，但该测试不替代真实预设验收。不能将事实重复写进用户请求来让裸模型也能通过。
- **业务工具样本**：客户端声明正常查询工具，模型返回实际调用；测试客户端提供结果后发起下一轮，再要求严格 JSON。调用 ID、结果字段、JSON 值及预设事实同时正确；不是每轮独立制造假历史。
- **拒绝/不兼容样本**：模拟标准拒绝、仅普通拒绝文字、截断、none 时泄漏业务工具、容器无法还原、覆盖阶段改变内部工具选择。验证没有伪造业务结果，没有额外模型请求，错误或未完成状态符合本次约定；另有 none + 内部容器成功的正向样本，不能把它当作冲突。不得使用真实不安全内容来反复触发或绕过安全拒绝。

停止/不发布条件：P1–P4 主要正向目标不能成立且未获范围调整确认；任何必要功能被静默跳过；客户端实际结果不满足已声明约定；只有替代预设测试通过；处理错误触发额外生成；仍需每轮手动切换核心脚本；最终发送与内部计划不一致；新旧配置混用；必要客户端等待/性能界线未验收。不得把这些列为“已知小问题”后宣称整体完成。

开发完成报告按 G0–G5 列出已完成、未完成和证据，不能把“代码已写”“可行性通过”“真实客户端验收”“已部署”合为一个完成状态。实施中发现本设计不成立时，先记录反例并修正相关决策，不以新开关或晚期覆盖绕过验收。

## 1. 真正要解决的问题

用户在一个渠道导入预设，可能同时启用世界书、脚本和正则。日常请求只需要文字，部分请求需要 JSON，另一些请求需要客户端自己的工具调用。

目标是：

> 尽量保留预设、世界书和已支持脚本的作用，同时保护本次客户端明确要求的输出格式。不能兼容时准确说明冲突，不以静默跳过预设或伪造结果冒充兼容。

管理员需一次性明确适配范围：只加工普通文字对话，或要求所有适用请求均运行适配。前者在发送前就将范围外请求交给原生中转，不是运行失败后偷偷取消预设。两者的保证不能混称为“全部兼容”，详见第 19 节。

New API 仍是中转站：

- 输入是客户端提交的完整请求，不是只有最后一句用户消息。
- 不建立新的聊天会话库，不维护客户端身份表。
- 不替客户端编排“先辅助工具、后最终工具”的业务流程。
- 不执行模型产生的外部动作工具，不假定客户端能执行预设新增工具。
- 不以预设名称、工具名称、自然语言提示词猜测格式。
- 不承诺完整复刻酒馆浏览器、插件、世界书状态机。
- 未配置适配的渠道保持现有中转行为。

### 1.1 必须区分“格式兼容”和“内容正确”

合法 JSON 不等于符合客户端字段要求；符合字段要求不等于模型内容正确。

- 客户端要求 `json_object`：至少保证返回对象，不接受数组、数字、字符串或 null 作为对象。
- 客户端提供 JSON Schema：只有经过相应结构校验，才能声称符合该 Schema。
- 客户端只在提示词里描述字段：不能靠猜字段名做可靠转换。
- 工具参数转换成正文需要明确来源；多个字段组合需要明确转换规则。
- 对模型生成内容本身，不承诺通过网关转换就能保证语义完全一致。

### 1.2 不能同时满足的要求必须被承认

例如：客户端指定调用自己的工具，预设脚本又强制调用另一个工具，且两者参数语义不同。

这不是再增加一个“自动协调”开关就能解决的。可行结果只有：

1. 预设支持输出方式调整，保留提示词等能力，并遵守客户端指定工具；
2. 有明确且可验证的转换约定；
3. 返回具体的兼容性错误，让用户选择调整预设或另建渠道。

不能给工具改名、删除未知参数或假定客户端会执行另一工具。

## 2. 对旧设计的纠正

| 旧假设 | 修订后的原则 |
| --- | --- |
| 客户端指定工具就是业务“最终工具” | 只说明本次请求要求调用它，不推断整个业务流程 |
| 出现一个工具结果就进入最终阶段 | 工具历史只用于保留与校验，不用来安排下一步业务 |
| 有工具就忽略 JSON 要求 | 工具可用性与文字输出格式分别保存、分别约束 |
| 预设新增辅助工具可以交给客户端 | 只有客户端声明或明确接入约定的工具才可对客户端可见 |
| 模糊时直接原样返回一定安全 | 原样返回也必须满足客户端要求，且不得包含内部工具 |
| 恢复 JSON 后随意执行正文正则 | 结构化数据与普通正文分开处理，最后再次校验 |
| 有请求计划与指纹就代表执行一致 | 执行层必须实际读取同一份决定；摘要对象不等于执行约束 |
| 配置界面能显示最终结果类型 | 无请求时只能显示配置意图；真实结果属于请求预览和日志 |
| 全部条目有开关就代表世界书完整 | 还需统一触发源、插入锚点、排序、简化记录和预览口径 |

## 3. 最小的职责划分

不再扩展“多角色、多阶段、多套推断器”。保留四个清楚的职责：

1. **客户端要求**：从本次原始请求读取，后续不能被预设或渠道默认值覆盖。
2. **请求加工**：发送规则、世界书、预设组装与允许的脚本处理。
3. **响应适配**：明确的内部内容恢复、正文处理与最终结构校验。
4. **执行记录**：只记录实际发生的步骤和结果，不能反过来参与业务推断。

运行时对象可以持有请求副本；持久化日志对象必须是独立的摘要类型。不能把整个运行时对象直接放入审计 JSON。

### 3.1 客户端要求不是一个互斥枚举

至少分开保存：

| 维度 | 必须保护的内容 |
| --- | --- |
| 工具 | 原始工具集合、定义、调用选择、并行调用约束 |
| 文字格式 | 未指定／明确文本／JSON 对象／JSON Schema |
| 历史 | 消息顺序、工具调用 ID、工具结果、原始不透明字段 |
| 交付 | 请求协议、流式要求、choice 分组 |

`text/json/tool` 可作为用户摘要，但不能替代以上信息。

渠道格式设置只补充客户端未明确指定的部分。采样参数的“预设优先”不适用于客户端工具及输出格式。

### 3.2 工具只按所有权与明确用途区分

- **客户端工具**：保持定义和调用约束，返回客户端，由客户端决定如何执行。
- **已声明的内容容器**：只承载正文或结构化结果，网关依据明确规则恢复。
- **其他预设工具**：不能自动认定是可交给客户端执行的工具。

仅有“脚本新增了工具”不足以证明它是内容容器。工具数量为一、Schema 只有一个字符串字段、字段名叫 content，都不是通用语义证明。

旧 `client_final`、`auxiliary`、`action`、`phase_policy` 不继续作为默认业务编排基础。后续迁移需保留原配置备份、列出行为变化，并要求确认；不能无提示忽略旧设置。

## 4. 请求处理顺序

```text
原始客户端请求与要求
  → 按已保存的适配范围决定本次是否加工
  → 选择有效聊天记录（含显式替代历史）
  → 发送文本规则
  → 世界书匹配一次
  → 预设骨架与世界书插入
  → 允许的消息后处理与脚本
  → 客户端字段保护及兼容性检查
  → 现有上游转换
  → 发送
```

范围外请求直接进入原生中转，不经过下面的适配阶段。阶段失败回退与范围选择是不同机制。

### 4.1 原始请求和匹配用请求

- 原始请求只读，用于客户端要求与失败回退。
- 匹配用请求是发送规则处理后的、尚未混入预设的聊天记录。
- 显式 `_sillytavern_context.chat_history` 若替代普通 messages，发送规则与预览必须处理同一份替代历史。
- 不扫描后来加入的预设文本，以免它自动触发所有世界书条目。
- 重试复用同一份加工结果，不重复执行脚本或追加世界书。
- 每次真正调用上游使用独立工作副本，防止模型映射等后续处理污染冻结输入。

### 4.2 脚本与后处理

保留已有宏、消息合并、工具绑定等可用能力，但校验范围要覆盖：

- 客户端工具定义、调用选择与工具历史；
- `response_format` 及其他明确的结构要求；
- 路由、协议和流式相关字段；
- 内容大小、执行时间和不支持能力。

脚本需要读取原始客户端输出要求时，通过明确的只读上下文提供；不能在多个地方各自重新分类。

预设可以提出上游输出方式，但不因此获得覆盖客户端约束的权限。冲突在发送前处理，不能等模型返回之后再随机裁剪。

### 4.3 请求失败

错误必须携带真实阶段，不能用字符串猜阶段，也不能把任意编译错误都归给世界书。

- 世界书匹配失败：只按世界书策略决定跳过或终止。
- 预设失败：只读取预设策略。
- 脚本失败：只读取脚本策略，不去掉世界书后重跑一遍脚本碰运气。
- “原始请求中转”必须恢复原始快照，并停用与本次已取消适配相关的响应恢复器。
- 已经过发送规则的请求不能被称为“完全原样”。
- 不因一个阶段默认允许回退，就覆盖另一个阶段显式的 fail。

## 5. 工具和格式冲突的处理

| 当前请求 | 允许的行为 | 不允许的行为 |
| --- | --- | --- |
| 普通文字，无客户端工具 | 预设正常运行；明确的内容容器可恢复为文字 | 把未知动作工具当正文 |
| 明确禁止调用工具 | 保留禁止要求；不擅自强制内部或客户端工具 | 因预设 required 激活强制调用 |
| 工具 auto | 保留可调用集合和选择权 | 强制先调用某个辅助工具 |
| 工具 required／指定工具 | 保留本次调用约束 | 按历史推断业务已结束或替换工具 |
| JSON 对象 | 保留结构要求；明确转换后必须是对象 | 渠道默认 text 覆盖它 |
| JSON Schema | 原样保留约束；转换需支持对应校验 | 只解析 JSON 就声称满足 Schema |
| 工具 + JSON | 工具路径保护工具，文字路径保护 JSON；冲突明确报错 | 用互斥分类直接丢弃其中一个要求 |
| 旧式函数或其他未支持协议 | 不引入未知转换；注明支持边界 | 当普通文本随意处理 |

支持能力必须按端点区分。Chat Completions 的适配通过，不等于 Responses、Claude、Gemini 原生协议也通过。

## 6. 响应处理与最终校验

```text
上游响应
  → 协议完整性检查
  → 识别客户端工具／明确的内部内容容器
  → 恢复内容
  → 对允许的正文执行输出脚本与正则
  → 按客户端要求完成交付结构
  → 最终校验
  → 原子写回或明确错误
```

### 6.1 正文与结构化数据不能混用

- 普通文字：按已有顺序执行输出预处理、接收正则。
- 工具调用：保留调用名、ID、参数和协议字段；普通正文正则不碰 arguments。
- JSON 对象／Schema：默认不对序列化后的整个对象执行普通正文正则。
- 确实需要处理 JSON 内的正文时，只处理显式指定的字符串字段，再序列化并验证完整结构。
- 多字段组合由显式转换器负责，不扫描所有字符串或按字段顺序猜“正文”。
- 对 JSON 字符串只在已知编码边界解码；不无限递归解码，不全局替换反斜杠。
- 单独的 `\u003c` 等合法 JSON 转义不是损坏；可读展示与真实传输内容分开。

这需要一个清楚的文本处理目标，不需要再造完整模板语言。采用字段路径时必须定义路径语法、缺失字段行为和类型限制，不默默把对象转成字符串。

### 6.2 写回前的硬检查

需要适配的请求，在写回前至少验证：

- 没有内部工具泄漏；
- 对客户端可见的工具确实属于允许集合；
- 本次指定／禁止工具的要求未被违反；
- 恢复后的 JSON 满足对象类型或已支持的 Schema；
- 输出脚本及正则没有破坏上述要求；
- choice 之间未串内容；
- 完整恢复后，`finish_reason` 与实际内容类型一致；
- 不误改 reasoning、usage、工具 ID 和非目标字段。

完整转换并删除内部工具调用时，必要的结束原因调整必须显式记录；不能机械保留与正文矛盾的 `tool_calls`。

拒绝、截断、缺少终止事件、上游错误都要保留真实语义，不能伪装成完整的正常 JSON。

### 6.3 失败回退保留哪一份数据

每个阶段有明确的输入和成功输出：

| 失败位置 | 可考虑保留的结果 |
| --- | --- |
| 协议解析／内容恢复 | 只有满足客户端要求且无内部工具的原始结果才可保留，否则报错 |
| 输出预处理 | 已成功恢复、且仍符合客户端要求的上一阶段结果 |
| 接收规则 | 规则链开始前的有效结果；不回滚到上游内部工具 |
| 最终交付校验 | 只可使用已验证的兼容候选；没有则报错 |

`preserve` 不是“随时发送最初的 body”。`empty` 也不能把客户端要求的对象变成空字符串。

记录确实执行过的阶段；失败、跳过、回退和成功分别标识。不能在解析前先记“校验成功”。

### 6.4 流式

- 需要完整工具参数、整段正则或结构校验时可以缓冲，并提示首字延迟变化。
- 缓冲有大小与时间限制；不能超限后直接泄漏未转换的内部调用。
- SSE 按 choice、工具 index/ID 汇集，兼容切分事件，不按单个网络块推断。
- 写出任何字节后，不再切换输出协议或重发另一份正常结果。
- 没有适配要求的原生流式不因新模块默认全部缓冲。

## 7. 世界书：触发、位置、顺序与可见性

### 7.1 现有基础可以保留

常驻、关键词、次级关键词、大小写、全词、受限正则、预算、有限递归、条目总览和基本插入器都有价值，不应整体删除。

“启用”仅表示允许参与匹配，不等于本次命中。界面需同时区分总开关、书开关、条目开关、是否需要确认、本次为何未插入。

### 7.2 统一位置的锚点

位置先表示为稳定锚点，插入后再计算数字索引。不能让额外加入的预设 user 消息悄悄变成“最后一条用户输入”。

新位置语义版本的选项确定为：

| 选项 | 目标语义 |
| --- | --- |
| 跟随全局 | 使用全局配置，界面显示解析后的目标 |
| 跟随预设世界书插槽 | 选择存在且启用的插槽；记录具体插槽名称 |
| 系统背景区 | 紧接开头 system/developer 区块之后 |
| 最新用户输入前 | 以匹配用聊天记录的最后一个 user 为锚点，而非后来生成的预设消息 |
| 聊天深度 | 以有效聊天记录为基准，0 在最后一条后、1 在最后一条前；不计入后来生成的预设提示 |

**历史基线提示：** 审查时 before_last_user 和 at_depth 在组装后的消息序列上定位。后续实施已增加第 15 节的 v2 聊天锚点；旧 v1 配置仍保留旧语义。不能把这里的历史缺陷描述理解为当前 v2 尚未实现。

新版本增加显式的“预设定义前／预设定义后”，分别使用 `worldInfoBefore` / `worldInfoAfter`，不再用“先遇到哪个就放哪个”代替独立映射。已核对的导入映射与缺失插槽处理见第 15 节；这两个独立目标已在 v2 实施，v1 的继承行为不能当成 v2 的限制。

回退需说明原因，例如“预设没有该插槽，改放系统背景区”。保护现代工具交换；旧式函数交换如果未支持，也必须显示边界，不能宣称所有工具交换均安全。

### 7.3 同位置排序与预算

将三个概念分开：

1. 预算选择：优先选高优先级条目；
2. 同一插入位置的文本顺序：低优先级在前、高优先级在后；相同优先级稳定使用书顺序和条目顺序；
3. 最终消息顺序：先看插入位置，再看区块内顺序。

不能用一个全局 `Order` 同时代表三者。用户选择不同位置后，不应被全局优先级重新挪回一个位置。

去重也要考虑书与目标位置；内容相同但有意放在不同位置，不应仅按字符串判为重复。既有重复内容规则变更同样需要迁移说明。

新版本预算明确为展开后的条目正文字符数，具体选择步骤见第 15 节。宏及后续脚本资源限额单独执行；超限原因不可伪装成未命中。

### 7.4 预览与实发

预览必须使用与实发相同的：

- 配置和有效模型；
- 发送规则；
- `_sillytavern_context`；
- 匹配历史；
- 条目选择与插入逻辑。

预览至少分别展示：

- 匹配结果与未插入原因；
- 插入后的实际区块顺序；
- 预设后处理前的位置；
- 若执行了脚本，处理后的最终请求或“脚本可能重排、当前位置仅代表插入时”。

脚本是任意受限程序时，不能凭字符串搜索保证追踪每段世界书最终位置。保留插入时位置和最终请求即可，不伪造追踪精度。

预览中显示的正文需注明是否已展开宏、是否经过脚本，不能将原始条目拼接文本标成最终将发送的背景。

### 7.5 导入与简化确认

- 纯展示字段不应被误判为运行风险。
- 确实影响触发、位置或范围的未支持字段，需要用户确认。
- 原始导入数据保留；确认另存，不删除风险说明。
- 总览、详情、批量操作和服务器使用同一套确认状态。
- 确认后显示“已按简化方式启用”及差异，而非变成“完全兼容”。
- `issues` 修正后需要重新校验，不能留下无法解除的永久阻塞标记。
- 不一次性自动启用未知效果的所有脚本或所有世界书高级行为。

## 8. 能力报告和界面

能力报告回答三个不同问题：

1. **文件里有什么**：静态识别；
2. **这次样本运行了什么**：说明模型、样本、配置版本；
3. **线上这次请求发生了什么**：来自真实执行记录。

不得混成“已支持／已执行”的一个绿色状态。

模型范围不匹配时显示未探测，不能把跳过执行当成成功。影响加工行为的草稿变化标记相关报告过期；纯展示变化不要求重做检查。无法确定影响时先标待重新检查，服务端规范化后确认有效设置相同才可复用报告。旧异步请求结果不能覆盖新草稿。

渠道主页面只保留：

- 当前预设、世界书名称及启用情况；
- 需要处理的问题数量；
- “管理世界书”“编辑预设”“回复处理”“用样本预览”入口。

输出方式默认显示“按本次客户端请求决定”，而非凭渠道配置断言“最终回复是文本”。

失败策略显示实际有效值和明确后果。前端默认与服务端默认只能有一个依据。高级名词放入技术详情，普通用户不用理解 final/auxiliary/visibility。

世界书总览显示名称、有效启用状态、触发方式、解析后位置、优先级、简化状态。详情用于编辑，总览用于判断全局状态。

## 9. 日志、缓存、重试及性能

### 9.1 日志边界

- 配置快照只存安全配置摘要、指纹、数量和结论。
- 原始／发送／接收正文走专门的正文采集存储和访问限制。
- 不序列化 `RequestPlan.Base.Original`、`Matched` 或完整 Profile 到配置快照。
- 脚本错误可能带入内容，诊断摘要需要界定长度与敏感数据处理。
- 世界书统计使用执行层真实状态；不让 included 与 matched 各说各话。
- 每次重试的 attempt 有独立结果；共享请求摘要不等于混用尝试日志。
- 诊断里的 HTTP 成功不能代替输出契约校验成功。

### 9.2 缓存

优先缓存稳定的解析／编译结果。轻量请求分类通常直接计算，不为缓存几项分类结果而反复序列化整段聊天。

能力探测缓存注明样本与生成时间，返回独立副本。当前容量限制有保留价值，但“有限容量”不证明实时性与命中价值。

渠道保存只做必要解析与校验。远程脚本准备、样本执行、整段请求哈希不应未经性能测量就混入同步保存链。保存慢的根因本轮尚未测量，不归因于某一个缓存。

### 9.3 重试

- 不重复应用发送正则、世界书和脚本。
- 同一加工语义才允许复用结果；不同语义应在选路时处理或明确拒绝。
- 现有指纹保护值得保留，但不能把“有指纹”称为所有后续参数都冻结。
- 本轮仅接收规则不同也不跨渠道复用冻结结果；完整语义相同才可重试，见第 13.3 节。
- 收到不兼容的上游响应后，不为获得“看起来成功”的格式擅自增加模型请求次数。
- 对重复请求的线上来源，需要请求 ID／attempt／接入日志证据，不能由本次静态审查下结论。

## 12. 实施边界与冲突决策（确定规则）

### 12.1 本轮交付范围

本轮针对现有 **Chat Completions 请求链**，包括非流式及 SSE。沿用原生 provider 转换，不另写一个中转服务。

- 支持文字回复、客户端工具调用、JSON 对象、明确的内部内容容器恢复，以及现有世界书与受限脚本。
- JSON Schema 请求可以保持其原生输出方式；本轮**不实现 Schema 回复的内容改写或内部工具转 Schema 回复**。不新增一个只验证 JSON 语法的“Schema 校验器”。
- Responses、Claude/Gemini 原生入口、旧式 `functions/function_call` 不新增此转换能力；在“仅普通文字对话”范围下走原生链，记录不应用预设；在“所有适用请求”范围下，若启用的适配需要未支持的转换，发送前报明确错误，不悄悄退化为文字。
- 不新增会话存储、客户端识别、业务工具执行、模型二次生成、外部插件浏览器环境。
- 不调整计费、鉴权和上游重试次数；适配产生的错误不触发新的自动生成请求。

“不改写 Schema 回复”不等于禁止使用预设：提示词、世界书仍可生效，前提是脚本不改写客户端格式和工具要求。原生 Schema 由原生 provider 链处理，本模块不得把它标成“已通过本地 Schema 校验”。

第 12–17 节的加工和冲突规则只对已进入适配范围的请求生效；第 19.3 节确定范围选择。范围外仍执行原生请求校验，不因跳过预设就跳过网关校验。

### 12.2 客户端约束提取与优先级

在任何规则或脚本运行之前提取只读 `ClientRequirements`。只读取本次协议字段，不解析提示词含义。字段的“缺省”与“明确给定”分开保存。

1. 工具定义保留原始名称和定义；名称冲突、客户端工具与容器同名属于配置冲突，不做改名。
2. `tool_choice` 缺省不等于 `none`；缺省值不由本模块补写。显式 `none/auto/required/指定工具` 保留。
3. `response_format` 缺省时可使用渠道的文字／JSON 默认；显式 text、json_object、json_schema 优先于渠道。Schema 原文不由脚本重写。
4. 保护客户端提供的工具调用选择、并行调用约束、历史调用 ID 与结果关联。消息正文可以按已授权规则加工，关联关系不能改变。
5. 模型路由和采样参数继续沿用原生与现有预设参数策略；本设计不把输出格式混入采样参数优先级。
6. 只读要求提供给已支持的脚本上下文；脚本是否利用它由脚本决定。旧脚本不能因此自动获得兼容性。

### 12.3 工具冲突的精确处理

| 本次条件 | 上游工具处理 | 回复处理 |
| --- | --- | --- |
| 无客户端工具、没有显式禁止工具 | 可以使用已声明的内部内容容器作为传输方式 | 恢复容器内容，不向客户端暴露容器 |
| 显式 `tool_choice:none` | 不允许新增可调用容器或脚本强制工具 | 正常文字／JSON；上游仍调用工具则不作为成功结果交付 |
| 客户端工具可用，choice 缺省或 auto | 保留客户端工具及选择方式；本轮不混入内部内容容器 | 客户端工具原样交付；有文字时按文字格式处理 |
| 客户端 required／指定工具 | 不删除、替换或强制另一工具；不采用容器传输 | 校验调用属于客户端集合且符合指定要求 |
| 客户端工具 + JSON 对象／Schema | 同时保存两种约束，不推断流程阶段 | 有调用的 choice 校验工具；无调用的完成回复校验文字格式 |
| 脚本新增未知用途工具 | 发送前报配置冲突 | 不尝试将它交给客户端，也不猜测为正文 |

“不混入内部容器”只影响**本次实际启用的传输方式**，不是禁止渠道保存容器配置。对于已启用受限脚本、并明确配置了 v2 `reply_adapter` 的预设，采用下述“脚本整理上下文、客户端决定交付协议”的边界；未声明该边界的配置仍按严格冲突检查执行，不猜测哪些新增工具可以删除。

- 先建立脚本专用的请求视图：保留消息内容与常规参数；客户端工具定义、选择要求、Schema 不交给脚本改写。客户端工具历史在该视图中以完整 JSON 记录作为上下文数据呈现，不执行工具。
- 在这个视图上实际完成预设组装、世界书插入和请求脚本，保留脚本生成的完整上下文。不是出错后退回原请求，也不是只保留静态提示词。
- 脚本生成的私有调用／结果记录只作为上下文数据，不作为另一套待执行的工具协议。发送阶段使用客户端原有工具、选择要求、Schema 和并行要求，并明确告知模型当前交付规则。
- 存在客户端工具历史时，从第一条协议记录开始的原生历史后缀（含后续用户消息）逐对象原样附回。它与脚本的上下文视图作用不同；前者保持协议和时间顺序，后者供预设整理设定。不能改写工具参数、结果字符串、ID 或签名。显式 `chat_history` 和原请求的保护要求不一致时不能假装兼容。
- 客户端工具名即使与预设容器同名，所有权仍属于客户端，不能套用预设 formatter 把该调用变成正文；不得根据同名猜测客户端已经运行了相同预设。
- 普通文字聊天不经过这条交付分支，继续使用预设原有工具容器、formatter 和接收正则。原生客户端工具调用不进入文字处理脚本；原生 JSON／Schema 不经过整段正文 formatter 或普通正文正则，仍遵循既有 JSON 字段加工限制。
- 该方式保留核心上下文脚本能力，**不承诺同时执行两套相互矛盾的最终格式指令**。强制格式由客户端拥有；依赖浏览器、外部动作、额外模型生成的脚本功能不因此获得支持。客户端只声明了思考字段而未声明正文字段时，不能擅自补充其业务工具 Schema。
- 诊断使用 `client_delivery`，必须同时能够证明预设／脚本已运行和客户端协议已保留；不得把 `plain_chat_only` 的绕过计为同一能力。实际模型输出仍须单独验收，尤其不能将原生 Schema 保留标为本地完整 Schema 校验。

客户端工具回复中的旁白 `content` 不作为普通回复执行正则；本轮完整保留包含客户端调用的 choice，避免破坏工具与旁白共同表达的语义。工具路径上的 JSON 格式不用于校验 `arguments`；参数和输出文字是两个不同对象。本轮校验工具参数是合法 JSON 对象，但不新增完整工具参数 Schema 校验。

### 12.4 内容容器恢复约定

恢复来源必须二选一：现有已声明 formatter，或显式的参数字段路径。不能先猜字段、失败后再猜另一字段。一个 choice 本轮只允许一个容器调用，不支持把多个容器结果任意拼成一个结果。

- formatter 输出必须是字符串，不接受隐式 `String(object)`。
- 新字段路径用 JSON Pointer 的受限形式：`/content`、`/result/body`、`/items/0/text`；空路径代表根。支持 `~0/~1`，不支持通配符、递归查询或执行表达式；最大 32 段，禁止原型访问。
- 路径不存在或类型不符是恢复失败，不填空、不遍历寻找替代字段。
- 文字目标要求选中值为字符串。
- JSON 对象目标：选中对象则保持对象；选中字符串则按 JSON 解析一次，并要求为非 null 对象。数组、数字、普通 prose 均失败。若来源带额外包装，必须由已明确声明的 formatter 负责恢复为 JSON，不为此再增加一套“JSON 解析前正则”。
- formatter 返回的 JSON 字符串同样只解析一次。不会替客户端自动包成 `{"text":...}`，也不做模型补写。
- 上游同时返回容器调用和非空普通正文、客户端调用、其他调用时，报混合内容冲突，不静默丢弃其中任何一项。独立 reasoning 字段保留，不算普通正文。
- 完整恢复成功时将仅表示内部调用结束的 `tool_calls` 改成 `stop`；`length`、拒绝和上游错误不改成成功。

旧点路径仅在迁移时转换为明确 Pointer；含歧义键名、隐含数组规则的配置必须让管理员重新选择，不能按猜测迁移。

## 13. 单次请求的执行边界

下表是逻辑边界，不要求给每行建立类、接口或新文件。禁止为“架构完整”再造通用工作流框架。

| 阶段 | 输入 | 成功输出 | 不得执行的操作 |
| --- | --- | --- | --- |
| capture | 原始请求、选中渠道配置快照 | 只读原请求、客户端要求、有效设置 | 序列化完整请求到配置日志 |
| applicability | 原始协议特征、已保存的适配范围 | 进入适配或进入原生链及原因 | 用客户端名称、提示词关键词或运行失败猜测是否跳过 |
| send | 有效聊天记录、发送规则 | 加工后的聊天记录 | 改工具参数、工具结果关联、结构要求 |
| match | 加工后的历史、世界书 | 命中决定、待插入条目 | 扫描预设文本、发网络请求、修改历史 |
| assemble | 历史、预设、插入决定 | 带来源标记的消息序列 | 用生成的 user 消息替代聊天锚点 |
| script | 组装结果、受限运行时 | 加工请求、明确回复处理约定 | 覆盖客户端硬约束、持久化跨请求状态 |
| seal | 加工请求、只读客户端要求 | 冻结请求、回复规则、有限诊断摘要 | 推断业务下一阶段 |
| attempt | 冻结请求的工作副本 | 单次上游结果 | 再运行发送规则／世界书／脚本 |
| finalize | 完整响应、冻结回复规则 | 验证后的客户端交付结果 | 追加模型请求、未经检查释放缓冲 |

### 13.1 替代历史与文本规则

- 先选择有效历史，再执行发送规则。有显式 `context.chat_history` 时，它是历史唯一来源；原请求 messages 不再另走一遍发送规则。
- 原始快照始终是客户端实际提交内容，不被替代历史覆盖。
- 发送规则仅处理授权的文本块；多模态非文本块、不透明字段及工具参数不做字符串化。
- 渠道规则先于预设内置规则，与现有顺序一致。已经复制到渠道并具有来源关联的内置规则只执行一次；不能只按规则名称去重。来源身份为预设稳定导入 ID + 原脚本 ID + 方向，与内容版本指纹分开。只修改提示词不生成新来源身份；已关联的渠道副本优先，不同时执行内置原件。源规则变化时提示关联副本待检查，不自动覆盖用户修改或重新启用原件。
- 无来源关联的独立规则不因内容相似自动删除；迁移无法确定是否重复时给出提示，不猜测。
- 宏使用本次冻结的时间、已解析变量和随机种子；预览可重用同一上下文。此处不新增跨请求会话变量。

### 13.2 运行对象与审计对象

保留三个持久生命周期明确的概念，避免两套互相矛盾的 Plan：

- `ClientRequirements`：只读、请求内使用；包含必要协议字段，不带整份配置。
- `PreparedAdaptation`：冻结请求、回复规则、脚本资源句柄、配置指纹。由 controller 真正使用，不只作为日志附件。禁止 JSON 序列化；结束、失败、取消都关闭资源。
- `AdaptationSummary`：专门构造的可序列化摘要。只允许阶段、状态、ID、计数、有效策略、有限错误码、配置指纹；不接收任意 `map[string]any` 的运行对象。

正文和世界书插入文本留在现有受控正文审计／预览返回中；摘要不保存请求、源代码、工具参数或 Schema 全文。错误摘要最多 512 个字符，名称等展示字段最多 256 个字符；未知脚本异常默认显示稳定错误码，原始异常不能直接进入公共错误消息。

### 13.3 重试与冻结

- 同渠道重试复用冻结请求，每次深拷贝供 provider 修改；每个 attempt 的响应缓冲和诊断独立。
- 指纹覆盖请求加工、容器恢复、输出脚本、接收规则及模型适用范围。暂不支持“请求相同但响应规则不同”的跨渠道复用，避免绑定旧运行时却使用新规则。
- 使用有效加工设置的规范化指纹，不混入渠道数据库 ID、仅展示用备注、JSON 排版或缓存生成时间。原始提示词／正则／脚本等有语义的字符串不随意去空白；确实参与脚本或宏读取的名称也必须计入。避免仅仅复制到另一个渠道就被误判为不兼容。
- 候选渠道语义不相同则跳过该候选，走现有选路失败出口；不重新编译，不额外尝试模型。
- 上述限制只约束进入适配的请求；范围外的原生中转不因其他渠道的预设配置不同而失去原生重试机会。界面需提示适配请求是否有加工规则相同的备用渠道，不能只以物理渠道数量暗示可以故障切换。
- 冻结对象只在本请求中存在，不用整段聊天哈希建立跨请求 Plan 缓存。保留按配置版本缓存静态解析／编译产物。
- 回复格式错误为确定的适配错误，不进入上游重试分支；网络错误仍由原生策略决定，本文不改其次数。

## 14. 响应检查点、失败与流式

### 14.1 处理顺序

`decode → restore → output_script → receive_rules → validate → emit`

每一步返回独立结果，不原地污染上一步。文字转换完成后再组装协议信封；协议解析只负责标准字段，未知字段按现有原生行为保留。

| 检查点 | 含义 | 是否一定可发给客户端 |
| --- | --- | --- |
| U | 原生协议层收到的响应 | 否，可能含内部工具 |
| R | 容器恢复后的候选，JSON 来源已完成一次解析 | 否，仍需检查本次工具／文字交付要求 |
| P | 输出脚本成功后的候选 | 否 |
| F | 正则链成功后的候选 | 否 |
| V | 满足本次交付要求的候选 | 是，但尚未写出 |

只有通过同一终态检查器且未违反已声明必需处理的候选才能成为回退结果。合法 API 文字不是“已满足裁剪要求”的证明。保留点与转换结果分离；**不存在“最后有数据就能发”的后门**。

文字接收规则沿用“输出脚本→渠道规则→未重复的内置规则”的顺序。允许回退时退到整条链之前，不保留半条链的成功部分。选用回退后直接终态检查并交付，不继续后续处理；没有合格候选或会跳过必需处理则报错。避免对回退结果又执行半套不同的加工链。

“必需处理”只指本次已进入有效处理链、适用目标上声明必须完成的步骤。普通文本正则在 JSON 对象路径上按设计不适用，不因为它配置了失败即终止就将正常 JSON 请求判失败。先确定本次有效步骤，再检查这些步骤是否完成。

### 14.2 结构化内容的文字处理

- 无容器的 JSON 对象回复默认跳过普通正文脚本和正则，记录 `skipped: structured_output`；不是把 JSON 作为字符串裁剪。
- 需要用接收正则修改 JSON 内文字时，在“回复处理”显式选择字段。复用第 12.4 节 Pointer 语法，只修改存在的字符串值；缺失／非字符串按该处理阶段失败，不创建字段。普通输出脚本不逐字段重复调用，JSON 字段清单仅授权接收正则。
- 对象结构保留，字符串修改后重新序列化并验证对象类型。一次请求只使用一套显式字段清单，不隐式遍历全部字符串。
- Schema 回复禁止此字段改写；配置了结构化改写且本次要求 Schema，则发送前报 `unsupported_schema_transform`。未配置改写时保留原生 Schema 路径。
- 非流式多个 choice 独立处理；任一 choice 无法安全交付则整个适配响应失败，不删掉失败 choice 假装完整。
- `length`/拒绝/上游 error 的原生可见结果保留其状态，标为未完成或拒绝，不宣称格式校验成功。如果含隐藏容器而不能无损恢复，则返回适配错误，不输出半个对象。

### 14.3 失败策略及默认值

| 失败阶段 | 新配置默认 | 可选行为及边界 |
| --- | --- | --- |
| 配置解析、客户端约束冲突 | 终止 | 不提供自动猜测或改协议的回退 |
| 世界书匹配／插入 | 终止 | 显式“跳过世界书”；在运行脚本前恢复无世界书的组装基线，脚本只运行一次 |
| 预设组装、请求脚本 | 终止 | 显式“取消本次全部适配，转发原请求”；关闭运行时及本次适配响应链 |
| 响应解码／容器恢复 | 终止 | 可请求保留 U，但必须通过终态检查且无隐藏调用，否则仍终止 |
| 输出脚本 | 终止 | 显式保留 R，必须通过终态检查 |
| 接收正则 | 新配置默认终止；可选修饰可显式保留 | 复用现有失败及未匹配策略；保留原文不代表满足用户的裁剪要求，见第 19.4 节 |
| 最终检查、缓冲超限 | 终止 | 不放宽约束，不临时改成直通 |

旧 `empty` 对文字可迁移为“返回空文字”，但仍受工具要求约束；对 JSON／Schema／required 工具不适用，报错而不返回空字符串。新界面不继续推荐这个策略。

“取消全部适配”包括发送规则、世界书、预设脚本、容器恢复及相关接收规则；原生路由、鉴权和计费照常。日志必须显示已取消及原因，不能仍显示预设已生效。这不是重新运行预设，也不是重新发送已发过的上游请求；仅允许在首次上游发送前发生。

此选项不能绕过本次声明必须完成的加工。配置检查和样本报告应指出不相容的策略组合；运行时仍以必需处理为准终止。只有本次加工允许整体取消时才可转发原请求，不因原生 API 格式合法而忽略必需的正文整理。

错误携带确定的 `stage/code`，不靠字符串归类：配置及不兼容请求为 400；内部实现异常为 500；不合法上游交付结果为 502；上游超时沿用原生超时处理。提供 request ID 和普通语言摘要，不返回堆栈、脚本源码或正文。HTTP 错误只允许在尚未开始响应时写出。

### 14.4 SSE 的确定行为

- 只要启用需要完整响应的容器恢复、输出脚本、接收规则、本模块 JSON 对象终态检查，或本次适配要求检查客户端工具集合／禁止调用／指定调用，就在首次写回前缓冲；不把部分事件提前交给客户端。
- 复用已有 8 MiB 响应缓冲上限、2 秒后处理限额；网络等待使用原生请求超时，不将 2 秒误用成模型生成超时。超过上限报错，不转为泄漏原文的直通。
- 按 SSE 事件边界解码，网络块切分不影响解析；按 choice index、tool index 汇集，校验后出现的 ID／名称不与先前片段矛盾。arguments 片段按到达顺序拼接，不按每片 JSON 解析。
- 全部通过后输出合法 SSE：role、按 choice 的正文或客户端工具、真实 finish、现有用量事件、终止事件。转换文本不伪装成模型逐 token 实时生成；界面注明“处理完成后返回”。
- 客户端取消立即停止并释放缓冲，不继续提交另一次请求。已开始写出时的网络失败走原生断流处理，不追加第二份 JSON 错误或成功内容。
- 无上述处理的原生 SSE 不新增完整缓冲，也不标为“已经过完整终态检查”。

## 15. 世界书实施细则

### 15.1 两种位置版本，不静默改变已有渠道

世界书配置增加 `semantics_version`。缺省或 1 表示现有组装后定位行为；2 表示本节的稳定聊天锚点。新建配置使用 2；打开或保存旧配置不自动升级。旧版本仍修复错误统计、风险确认绕过和预览失真，不保留这些安全／正确性缺陷。

升级前显示旧位置与新位置的样本对照。确认升级一次保存完整配置，不逐条自动写回。旧原文保留在迁移备份中；位置升级可撤回，不要求还原整个应用版本。

新版本位置值：

| 配置值 | 界面名称 | 确定含义 |
| --- | --- | --- |
| `follow_global` | 跟随世界书设置 | 条目使用全局目标；全局不能再次 follow_global |
| `inherit` | 使用预设默认插槽 | 优先启用的 worldInfoBefore，否则 worldInfoAfter，否则系统背景区 |
| `before_definition` | 预设定义前 | 仅使用启用的 worldInfoBefore |
| `after_definition` | 预设定义后 | 仅使用启用的 worldInfoAfter |
| `system_prelude` | 系统背景区 | 组装时开头连续 system/developer 区块之后 |
| `before_last_user` | 最新用户输入前 | 加工后有效历史中最后一个 user 的来源锚点 |
| `at_depth` | 聊天中的指定深度 | 有效历史末尾倒数；0 在末尾之后，1 在末条之前 |

新配置全局默认 `system_prelude`；继承选项仅在管理员选择或旧配置迁移时使用。深度有效范围保持 0–20，配置超范围拒绝保存，不能在运行时无声截成 20。

有效历史用于深度计数的消息是 user/assistant/tool/function，不含 system/developer 和后来生成的预设提示。深度超过历史长度时放在第一条有效历史前；没有可定位历史时回退系统背景区并说明原因。

缺失指定插槽、预设未启用或模型范围不匹配时，默认回退系统背景区；诊断同时记录“指定目标”和“实际目标”。不把“定义前”假装成已准确实现。插槽标识重复属于预设配置错误，不复制注入。

### 15.2 保留工具交换与插入顺序

- 在组装前给有效历史消息分配请求内来源 ID，预设骨架保存来源映射；ID 只在内存使用，不能发给上游。
- 现代 assistant.tool_calls 与其对应 tool 结果构成不可插开的区块。深度命中区块内部时移到整个区块之前，记录“为保持工具调用完整，位置已前移”。
- 旧式 assistant.function_call 与 function 结果同样作为完整区块保护；这里只保护顺序，不新增旧式回复转换。
- 有结果却无可关联调用等非法历史交原生校验处理，世界书不能通过挪动消息“修复”它。
- 世界书在宏展开和预设骨架组装过程中放入锚点，在消息合并及请求脚本之前完成。后续脚本可改写文字；最终客户端关联保护仍执行。
- 同锚点按 priority 升序、书的显示顺序、条目的显示顺序排列；不依赖 map 遍历或 UUID 字典序。
- 最终位置由锚点决定，不做全局 priority 排序。不同逻辑目标恰好落到同一物理边界时按上述同锚点顺序合并；不得因此再次删除同内容条目。

### 15.3 触发、去重和预算

1. 本次使用发送规则处理后的有效历史；scan_depth 沿用已有有效范围及默认值。扫描字段与范围在预览中展示，非文本字段不序列化参与关键词匹配。
2. 跳过关闭、待确认、配置无效的条目，各有独立原因；常驻条目不需要关键词，其他条目按现有关键词规则判断。
3. 候选按 priority 降序、书顺序、条目顺序选择。每个候选使用本次冻结宏上下文展开；按展开后的 Unicode 字符数计算预算，不按 JSON 字节数或模型 token 数。
4. 预算计入正文及实际区块内条目分隔符；预设固定包装模板不计入世界书正文预算，仍受现有总请求大小限制。整条放入或跳过，不截断条目。一个过大条目跳过后继续检查较小条目。
5. 仅预算内已接纳条目可参与递归扫描；扫描其展开后内容。保留已有最多 3 轮、现有扫描工作量限制；不扫描预设或脚本改写内容。PreventRecursion 的条目可以被选中，但其内容不触发下一轮。
6. 每个条目只选一次；递归后续轮次使用剩余预算，不挤掉之前已接纳条目。记录触发轮次，避免声称是对所有递归候选作全局最优排序。
7. v2 不按正文字符串去重。重复身份 `(book_id, entry_id)` 配置拒绝保存；同内容不同条目视为管理员有意配置，均可插入。关闭重复条目由管理员决定，不让内容去重抵消不同位置的用途。
8. 宏展开失败归到世界书阶段；不以空字符串掩盖。条目全部关闭／未命中不是异常，不触发失败回退。

### 15.4 原生导入映射与简化确认

2026-11-09 查阅 SillyTavern 官方文档与 `release/public/scripts/world-info.js`，核对位置编号和“优先级／深度／插槽”是不同概念。本轮采用以下**有边界的导入映射**，不宣称完全复刻酒馆：

| 来源 position | 本项目 v2 目标 | 限制 |
| --- | --- | --- |
| 0（before） | before_definition | 依赖对应预设插槽；缺失时明确回退 |
| 1（after） | after_definition | 同上 |
| 4（atDepth） | at_depth + depth | 本项目按有效历史锚点定位；不支持的 role、深度范围需确认／修改 |
| 2、3（作者注释前／后） | 不自动替代 | 本项目没有等价作者注释锚点，管理员选择替代位置 |
| 5、6（示例消息前／后） | 不自动替代 | 本轮不新增示例消息独立锚点 |
| 7（outlet）或未知值 | 不自动替代 | 保留来源字段，要求选择受支持目标 |

来源参考（核对时点，不代表未来版本保证）：

- 官方源码：`https://raw.githubusercontent.com/SillyTavern/SillyTavern/release/public/scripts/world-info.js`
- 官方说明：`https://docs.sillytavern.app/usage/core-concepts/worldinfo/`

导入器明确区分顶层 Tavern 格式和嵌套 extensions 格式；同一字段两处冲突时列为待处理，不凭属性遍历顺序决定。`displayIndex/display_index` 是展示排序信息，不当成触发风险；`depth` 只在深度位置生效。深度处缺省角色按 system；明确的非 system 角色本轮需要确认简化为 system。其余未实现的行为字段保持待确认，不因“看起来是默认值”一律放行。

风险记录使用结构化 issue code + 来源字段 + 实际替代行为，原英文导入警告保留为技术详情，不直接堆给用户。增加 `accepted_risks`，保存该确认项所依赖的来源字段、替代行为和解释版本指纹；这些内容改变后恢复待确认。无关的展示修改不使所有条目失去确认；确实影响匹配或位置的变化不能当展示修改略过。

服务器统一计算有效启用状态：总开关、书开关、条目开关均开启，配置有效，风险均已确认。详情开关、批量启用与 API 直接写配置都不能绕过。修复条目后重新生成 issues；接受简化不删除原风险记录。

### 15.5 预览接口与状态口径

扩展现有预览入口，不新增另一套匹配器。输入包含 `config`、`sillytavern_preset`、`request`、适用的渠道发送规则、显式上下文及 `draft_revision`。服务器根据输入生成有效配置指纹；不能把前端 revision 当作可信配置证明。

两种明确操作：

- **检查触发与位置**：运行同一 send/match/assemble 逻辑，不执行任意请求脚本，不调用模型、不下载脚本；显示“脚本处理前”。脚本专有的后处理不会在该预览中假装完成。
- **预览最终发送内容**：显式执行已准备且已授权的受限脚本，使用真实请求加工入口，不调用模型、不执行模型工具；运行环境一次性销毁。资源未准备显示“需先准备”，不混入渠道保存。

条目输出分开表示 `eligible`、`triggered`、`selected`、`inserted`，附 reason、trigger_round、resolved_target、local_order、inserted_message_index。例如命中但预算不足：triggered=true、selected=false。汇总直接从这些字段计算，不再混用 matched/included 的字符串。

插入后索引明确标注是“脚本前消息序号”；脚本后另给最终请求，不用文本搜索伪造条目位置。切换渠道、模型、有效加工配置或请求样本时核对报告关联，不沿用不相符的结果；迟到请求返回不得覆盖新状态。纯展示修改按第 8 节处理。预览结果相同的保证仅限相同输入和冻结宏上下文，不能保证有时钟／随机行为的脚本跨次结果完全相同。

## 16. 配置、迁移与界面

### 16.1 最小配置变化

不新增数据库表。继续使用现有渠道配置载体；实现时不顺带升级 ORM 或改变数据库字段类型。

- 新回复恢复配置放在预设配置的 `reply_adapter`，含 `version:2` 和 `containers`。每项仅有工具 `name`、来源 `argument_pointer` 或 `formatter`、`output_kind:text/json_object`。两种来源互斥，formatter 只能引用现有受支持运行时的已声明回复处理器，不引入动态模块执行入口。
- 渠道现有适配设置增加 `adaptation_scope: plain_chat_only | all_supported`，统一约束本模块发送规则、世界书、预设与回复处理。新建时明确选择，旧配置缺省按 all_supported 读取，不能升级后自动跳过已有预设。范围外保留原生链；范围选择不是运行错误的回退策略，详见第 19.3 节。
- 输出目标依旧先由客户端要求确定；缺省时以显式恢复声明为准。声明 text 与客户端 json_object 不一致时不能无声包装，发送前报冲突，管理员可明确配置 JSON 恢复。
- JSON 字段文字处理清单 `json_text_pointers` 放在现有接收规则配置，缺省为空；普通文本无需填写。它不是工具参数编辑器。字段清单最多 32 项，路径不得重复或互为父子，避免重复加工；每个字段执行同一套适用接收规则，整组失败一起回退。
- 世界书新增 `semantics_version`、两个定义插槽枚举和风险确认记录；保留原 Source。
- 新配置默认值由服务端规范化后返回；前端使用同一有效值，不另写 `safe_raw` 等不同默认。
- 保存只校验形状、语法、引用、资源大小及明确的静态冲突；不拉网络模块、不跑样本、不进行模型调用。保存成功只表示配置已保存，不能显示“全部兼容”。

`reply_adapter` 是替换旧协调配置，不是让 `tool_text/tool_protocol/formatter/reply_adapter` 四套并列争夺输出。规范化层将可确认的旧配置转成同一运行约定；若出现两个恢复来源，必须报冲突，不按先后顺序选择。

### 16.2 旧配置迁移表

| 旧情况 | 读取时处理 | 管理员保存／升级时处理 |
| --- | --- | --- |
| 未指定适配范围 | 按 all_supported，保持原加工意图 | 可一次选择仅普通对话；必须说明范围外不运行预设 |
| 普通预设、无工具协调 | 保持可用；应用硬约束保护 | 无额外迁移确认 |
| tool_text 指定工具及字符串字段 | 可无歧义归一成单一容器约定 | 展示等价映射后保存 v2 |
| 已声明且唯一的 formatter | 复用其恢复能力，不推断其他工具 | 保存显式 formatter 来源 |
| tool_protocol 含阶段推断、辅助／动作可见设置 | 标记 requires_review；相关适配请求发送前 400 | 确认移除业务编排或重新声明容器；不继续执行旧推断 |
| 旧 response_argument 点路径 | 仅无歧义路径可归一 | 歧义路径要求手动选择；不自动递归提取 |

移除内部工具泄漏、保护客户端字段、禁止审计存完整 Plan 是强制正确性修复，不提供回退到错误行为的开关。旧危险配置阻止执行时必须在渠道列表／编辑页给出可操作提示；不能部署后只让请求持续报一个神秘 runtime 错误。

迁移不在读取渠道时写数据库；只形成规范化结果和警告。保存时生成可下载的旧配置备份及差异，由现有一次渠道更新原子写入。界面不得把“下载了备份”描述为服务器已自动备份。

## 17. 可执行的验收样本设计（尚未运行）

以下样本定义实施后的期望，不是本轮测试报告。`model:"test-model"` 是测试占位符，不表示真实模型能力。除明确修改的正文／内部调用 finish 外，外层 ID、model、created、choice index 和非目标字段沿用输入；不根据样例重算用量。

### 17.1 文字容器与回退

配置：容器 internal_reply，`argument_pointer:/content`，`output_kind:text`；无客户端工具。请求：

```json
{"model":"test-model","messages":[{"role":"user","content":"你好"}]}
```

预设生成的上游工具允许包含 internal_reply；客户端原请求不被改写。上游 choice：

```json
{"index":0,"message":{"role":"assistant","tool_calls":[{"id":"call_i","type":"function","function":{"name":"internal_reply","arguments":"{\"content\":\"<thinking>检查</thinking>你好\"}"}}]},"finish_reason":"tool_calls"}
```

接收规则删除 `<thinking>...</thinking>`，期望客户端 choice：

```json
{"index":0,"message":{"role":"assistant","content":"你好"},"finish_reason":"stop"}
```

将输出脚本改为抛错并选择“保留上一步有效结果”时，期望 content 是 `<thinking>检查</thinking>你好`，**不是**原来的 internal_reply；本轮处理在回退处结束，不再继续正则，日志明确显示回退。选择终止则 502 且无任何成功 choice 写出。

上述回退夹具明确允许跳过后续文字修饰；若该正则被配置为必须完成的提取／整理，则不能绕过它返回 R，应终止。本例不证明未处理文字可满足固定格式用途。

### 17.2 JSON 字符串恢复与正文规则隔离

请求：

```json
{"model":"test-model","messages":[{"role":"user","content":"返回结果"}],"response_format":{"type":"json_object"}}
```

配置容器 output_kind=json_object；选中的参数字符串为 `{"body":"hello"}`。没有字符串清理规则时，期望：

```json
{"index":0,"message":{"role":"assistant","content":"{\"body\":\"hello\"}"},"finish_reason":"stop"}
```

对同一 JSON **对象候选**配置普通接收正则，试图把整份 JSON 提取为 hello：规则必须跳过，结果仍为对象，日志说明 structured_output。没有“先把整个 JSON 当正文裁剪，再试试看能不能解析”的隐含处理路径。

将容器字符串改成 `[1,2]`，期望 502 `response_contract_violation`；改成普通 `hello` 同样失败。不自动包装对象。若对象字段清单明确为 `/body` 且规则 hello→你好，则期望 content 为 `{"body":"你好"}` 的合法 JSON 字符串。

### 17.3 客户端工具与预设冲突

客户端工具请求：

```json
{"model":"test-model","messages":[{"role":"user","content":"查询天气"}],"tools":[{"type":"function","function":{"name":"weather","parameters":{"type":"object","properties":{"city":{"type":"string"}},"required":["city"]}}}],"tool_choice":"auto"}
```

仅提示词／世界书预设：上游 weather 定义与 auto 保持不变。上游返回的下列 choice 交付给客户端时保持相同：

```json
{"index":0,"message":{"role":"assistant","content":null,"tool_calls":[{"id":"call_w","type":"function","function":{"name":"weather","arguments":"{\"city\":\"北京\"}"}}]},"finish_reason":"tool_calls"}
```

预设脚本另加 internal_reply 并强制调用时：**上游调用数为 0**，400 `preset_client_contract_conflict`，指出预设工具要求与客户端工具要求冲突。不能先替换 weather 发出去再期待恢复。

将原请求 tool_choice 改成 none、required、指定 weather：分别断言禁止调用被保留、要求至少一个客户端调用被保留、指定名称被保留。原 none 绝不能被脚本 required 覆盖。

### 17.4 世界书锚点与顺序

有效历史为 `U1, A1, U2`，预设追加 `P(user)`。开启 v2，条目：

| 条目 | 内容 | priority | 位置 |
| --- | --- | --- | --- |
| A | 背景A | 100 | 最新用户前 |
| B | 背景B | 10 | 系统背景区 |
| C | 背景C | 20 | 最新用户前 |
| D | 背景A | 5 | 深度0 |

在无消息合并和脚本改写的夹具中，期望消息次序：

```text
预设开头系统区 → B → U1 → A1 → [C, A] → U2 → D → P
```

断言：

- A/C 在真实 U2 前，不是 P 前；D 在历史末尾后、追加提示 P 前。
- A 不因优先级高被排到 B 之前；C/A 同位置按优先级排列。
- D 与 A 内容相同仍保留；预览显示真实区块次序。
- 历史改为 `U1, assistant(tool_calls:x), tool(x)`，depth=1 必须移到 assistant 调用之前，不插入调用与结果之间。
- 旧 semantics_version=1 对照样本保持旧定位，升级预览能显示差异。

## 18. 实施放行、交付顺序与剩余边界

### 18.1 设计放行结论

本设计已经确定了实施所需的核心行为：冲突决策、来源声明、阶段输入输出、回退数据、流式边界、世界书位置与顺序、配置迁移、模块替换范围以及可观察样本。最终复审结论见第 19.9 节。**不再需要先创建第二份宏观设计或重复收集同一需求。**

用户视角复审补充了第 19 节：原方案只能说明工程边界较清楚，不能直接推出“配置一次即可广泛稳定使用”。实施须同时包含适配范围、必需整理保护、版本稳定性和使用旅程验收；不可只完成第 17 节的错误拦截就宣布产品可用。

实施前仍需读取最新工作树，确认没有其他窗口改动这些边界；若出现新改动，核对受影响的具体条款，不推倒整份方案。局部函数拆分、命名和组件组合在编码时按项目规范决定，不把它们伪装成尚缺的业务设计。

明确不在本轮承诺中的能力：Schema 内容转换、客户端工具与内部容器并行混用、任意多容器归并、完整酒馆世界书状态机、所有原生 API 入口、脚本改写后的逐段来源追踪。这些限制已有确定的保留原生／拒绝／提示行为，不是实施中再临时决定的空白。

### 18.2 实施与必要验证

1. **契约与回复正确性**：先把已复现反例转成断言，再替换阶段推断和回退核心；通过 17.1–17.3、C01–C10。不得仅靠新接口存在就宣称完成。
2. **请求与世界书一致性**：统一历史、组装、v2 插入和预览，验证 17.4、C11–C18；保留版本1迁移对照。
3. **配置与展示**：迁移、摘要、前端有效值、过期结果、问题提示落地，验证 C15/C17/C19/C20；执行基础浏览器验收。
4. **收尾**：检查旧推断调用点已清除、历史计划不再误导；验证 C21/C22 和现有相关回归。修改 relaykit 时按仓库要求独立构建；数据库行为如有实际变化再执行仓库要求的数据库验证，不能用本文“不改表”规避真实变更验证。

保存性能先记录一次真实保存链的请求耗时与阶段耗时，再处理被证实的阻塞。移除同步远程工作是确定边界，但不预设它就是现网慢的唯一原因；不写未经测量的性能提升百分比。

### 18.3 本轮工作纪律

本轮仅完成实施前设计和文档一致性检查。没有修复业务代码、没有部署、没有运行上述新验收。开始编码须下一次明确授权；推送与部署也按当时授权执行，不沿用历史消息中已经过期的“自动推送”要求。

## 19. 用户视角复审：配置一次之后能否长期使用

### 19.1 复审结论

**原计划可以减少错误加工，但还不足以满足“多客户端、低维护”的完整预期。** 它偏重遇到冲突就阻止，却没有充分处理“用户其实只想给普通聊天加预设，其他功能照常中转”的使用方式，也把 API 格式合法过多地等同于交付正确。

本次修订不降低格式保护来换取成功率，而是补齐适配范围、明确承诺、一次配置、多次验证和版本稳定性。它是现有加工链前的一次范围选择，不是新的客户端识别器、自动业务编排或多层降级框架。

“一劳永逸”的合理承诺：

> 在同一配置版本、受支持的请求类型和已验证的用途内，无需因换了客户端品牌反复调规则；超出范围的请求按已选择的原生中转或严格处理方式执行。更换预设、格式要求、脚本版本或加工语义时，明确提示需要重新检查。

不能承诺任意客户端、任意预设、任意工具组合都同时保持全部预设效果；不能用绕过预设后的请求成功，统计成预设适配成功。“能发出请求”“保留预设”“客户端能使用结果”必须分别验收。

### 19.2 用户需求与原计划缺口

| 用户期待 | 原计划已有价值 | 原计划不足／本轮补充 |
| --- | --- | --- |
| 换客户端仍能用，不研究底层协议 | 从本次请求保护工具和格式 | 缺适配范围；同一渠道的工具／JSON 请求容易被预设冲突挡住 |
| 预设说启用就真的有效 | 不静默取消脚本，记录阶段 | 必须直接显示哪些请求会用、哪些不会用；原生中转不标为预设生效 |
| 返回的是我需要的正文 | 避免 JSON 破坏和内部工具泄漏 | 普通文本合法不等于裁剪成功；必需规则不能被其他阶段回退绕过 |
| 不丢内容，不重复生成 | 冻结请求、原子写回、禁止补生成 | 必须覆盖实际客户端工具往返、取消、流式与完整正文，而非只测解析 |
| 流式不突然“卡住” | 区分需要缓冲的链路 | 配置前显示等待影响；原生请求不为无关预设缓冲 |
| 上游故障能换备用渠道 | 防止重试重复加工 | 严格语义指纹可能缩小备用范围；需提示并提供同配置复用方式 |
| 今天好用，明天仍一样 | 请求内配置冻结 | 还需固定脚本依赖、更新前检查、保存原子性和明确恢复办法 |
| 一次设置即可，别反复填技术字段 | 摘要卡片与样本预览 | 恢复字段需可视选择；一次检查多个请求场景，不能一条 hi 就亮绿灯 |
| 错了知道怎么改 | 有阶段错误和诊断 | 要说明责任来源、影响范围及可执行修复动作，而非只给 stage/code |
| 并发、长文本下也可用 | 单请求缓冲和时间限制 | 单请求有限不代表整体资源稳定；需并发与超时的必要验收 |

以上是根据本项目用途建立的产品要求，不是用户访谈统计；目前没有数据可以给出“适配了百分之多少客户端”的结论。

### 19.3 一次选择加工范围，不按客户端维护特例

导入并准备预设后，使用一个清楚的设置回答“哪些请求需要运行这套加工”：

| 设置 | 普通文字请求 | 工具、JSON、其他协议请求 | 适合的用途 |
| --- | --- | --- | --- |
| **仅普通文字对话** | 按已配置预设／世界书／规则处理 | 不运行本模块加工，走原生中转 | 明确接受特殊请求不使用预设的用途 |
| **普通与特殊请求都应用** | 运行加工 | 按第 12 节兼容；冲突则明确失败 | 结构化输出也需要同一预设的用途 |

这不是默认替用户放弃预设。新建时展示后果并明确选择；强依赖上下文脚本、希望多客户端持续保留预设能力的用途应使用后者，并按第 12 节检查已声明的回复适配边界。前者是主动接受特殊请求绕过预设的选择，不是完整兼容方案。旧配置不能通过软件升级自动改选。

范围决定“哪些请求进入加工”，已有失败策略决定“加工失败怎么办”。要保证预设和固定格式必须生效，就使用终止策略；显式允许取消加工时，摘要必须写明“不保证失败时仍保留预设效果”。不把“普通与特殊请求都应用”这个范围名称当作无条件成功承诺，也不再增加一套与已有失败策略重叠的模式。

`plain_chat_only` 的确定判定：

- 仅限本轮支持的 Chat Completions 纯文本消息请求。
- 请求未声明非空工具／旧式函数、工具调用选择或工具历史；未声明 JSON／Schema 或其他结构输出；不含未支持的非文本消息块。显式 tool_choice:none 也走原生链，避免预设暗中改为工具传输。
- 缺省或明确 text 可进入普通对话范围；空 tools 数组本身不等于有工具，但独立声明的调用选择仍按前项处理。
- 只看已解析的协议字段，不看客户端名称、User-Agent、提示词是否写了“JSON”、工具叫什么或正文是否包含某个标签。
- 非标准格式只藏在自然语言中的请求无法可靠识别。界面明确说明这一限制，建议该用途使用不加工的渠道／模型入口，或由客户端声明标准输出要求，不能声称自动覆盖。
- 范围外一次性跳过本模块整套加工，避免只停脚本却保留依赖该脚本的正则。原生模型映射、参数覆盖、路由等仍遵循既有配置，所以 UI 写“不应用预设加工”，不写“网络字节完全原样”。
- 范围选择先于任何脚本运行，不在失败之后重跑一遍。日志记录 reason：工具请求／结构化输出／其他协议／非文本内容。

无论哪个范围，都不根据“这个客户端带了工具但这次大概不会用”做猜测。客户端每轮均携带工具时，plain_chat_only 会持续不应用预设；这是明确限制，必须在样本报告中提示。若该客户端也必须保留预设，应选严格用途并检查预设是否支持客户端工具，不能把范围设置当作全部问题已解决。

即使都属于纯文字，角色扮演、代码生成、摘要等任务也不一定适合同一预设。协议分类不解决业务意图冲突；不得按提示词关键词自动切换人格或编写业务分类器。需要不同加工效果时，利用现有独立渠道／模型入口保存各自用途，客户端只需选一次相应入口，不反复修改共享渠道。该方案降低维护成本，不承诺一个角色扮演配置可以不加区分地适合所有纯文字任务。

切换备用渠道时，本次范围决定也冻结：原生请求只能切到对本次请求同样不进行加工的候选；适配请求只能切到加工语义兼容的候选。不因换渠道半路打开另一套预设。

### 19.4 “有回复”不等于“可靠完成”

不新增另一套失败开关，复用已有失败与未匹配设置，但调整新配置默认和解释：

- 新建接收规则链默认处理失败报错；新建“提取正文”规则默认未匹配报错。用户可显式选保留原文，但界面说明这可能返回未裁剪的文字。
- 原有显式保留策略不静默修改；显示“此设置在整理失败时可能返回完整原文”，由管理员决定是否调整。
- 规则声明失败即终止／未匹配即终止时，输出脚本回退等较早阶段不得跳过该必需规则后返回成功。
- 普通替换的零匹配本身不必是错误；只有用户声明必须匹配时才据此失败。不能用“有正则”推断它一定命中，也不能自行判断某段文字符合角色扮演正文。
- API 协议验证、回复整理完成、采取允许的回退分别显示。回退成功只是符合已选策略，不宣称模型语义正确或所有预设要求满足。

结构化路径不能为了通过接口而随意包一层对象。工具调用不能为了避免错误而改名。真正无法同时满足的要求仍应拒绝；本轮新增范围只减少不该进入适配链的请求，不伪造兼容性。

### 19.5 减少一次配置的技术负担

设置流程保持四步：**导入 → 看清可用范围 → 检查代表性样本 → 保存**。不强制每次保存都跑脚本或调用模型。

- 已有明确恢复声明时自动填入并展示来源；无声明时不得猜工具的业务含义。
- 需要选择正文来源时，从管理员提供的工具参数样本中展示字段树、类型、内容预览。用户点选字段，系统保存 Pointer；高级编辑仍保留。不得把选择前的试运行包装成已验证兼容。
- 没有样本、多个可能来源、字段类型不符时，指出具体缺少什么；不要求用户先理解容器、JSON Pointer、phase 等名词。
- 提供一组可复用的检查场景：普通对话、工具调用、工具结果续接、JSON、Schema、流式、其他入口。先检查会走哪条路径；需要判断模型实际输出时另行明确运行真实请求，不能把不调用模型的预览当端到端成功。
- 报告逐项显示“会使用预设／按配置原生中转／有冲突／未验证”，绑定配置、模型和样本。不生成一个含糊的“全部支持”绿色徽章。
- 允许沿用已经检查的相同配置到备用渠道；改变了预设、规则、依赖或模型能力后标记相关结果过期，不要求用户手工重新录入所有字段。

### 19.6 长期运行的稳定性要求

**配置稳定：** 请求开始后使用同一配置快照，处理中保存新配置不得混用新规则。保存失败保留旧配置；表单保留草稿。检测编辑期间配置已被其他窗口更新时提示重新载入／对比，不静默覆盖。具体并发保存措施沿用或补齐现有渠道更新机制，不为此新增会话数据库。

**依赖稳定：** 已准备脚本和模块按解析内容版本固定，不在每次请求中重新拉取远程最新脚本。更新依赖是显式动作；失败保留上一个可用版本。首次未准备不能标“可用”。这保持现有脚本权限边界，不扩大远程执行能力。

**延迟可预期：** 保存前展示本套配置是否需要完整等待，以及原因；样本报告分别展示上游等待和本地处理耗时。纯原生请求不因为配置里存在一个未启用／不适用的正则而缓冲。必须整段处理的路径不承诺实时逐字输出，也不能用伪造 SSE 内容掩盖等待。

**资源可控：** 除单请求限额外，还需检查并发缓冲、脚本实例和取消后的资源释放。不能把每请求 8 MiB 当成整个服务只占 8 MiB。实际并发预算按部署容量测定；实现使用有界准入，超过容量明确返回临时资源错误，不无上限排队或转为不安全直通。准入失败在上游调用前发生。

资源准入优先复用宿主已有的并发限制与超时机制；只在现有机制无法约束适配缓冲／脚本实例时增加适配资源上限，不新建独立队列服务。开启缓冲前需要能给出单请求预算与并发上限的组合边界；具体数值由部署验收决定，不把未经测量的常量当作稳定性保证。

**备用可用：** 使用相同加工配置的备用渠道可复用冻结结果；不同语义不偷偷切换。配置检查区显示是否存在适用备用，而非自动复制覆盖其他渠道。没有备用时用户应提前知道，不在故障发生后才发现路由被收窄。

**问题可处理：** 每条问题提供“哪里出了问题／哪些请求受影响／下一步怎么处理”。例如“预设强制使用自己的回复工具，与本次客户端工具冲突。普通聊天仍可用；若此客户端必须用预设，请调整预设工具模式”。不要把渠道配置错误统称为“用户消息无效”，不要要求用户盲目重试。不能保证所有第三方客户端会遵从错误码或不自行重试。

**升级可恢复：** 发布前对现有配置做只读兼容检查，列出会被阻止的渠道、原因及迁移动作；准备旧配置备份。需要迁移的业务先迁移或由管理员接受影响，再发布。不得把批量请求报错当作升级后的正常发现流程；已知错误行为不因此继续保留。

### 19.7 必须补充的使用旅程验收

以下是第 17 节之外的产品放行条件，不是已通过的测试：

| 场景 | 必须达到的体验 |
| --- | --- |
| 一次配置，同渠道依次发送普通聊天、工具、JSON、Schema | 依保存的范围稳定分流；不要求每次改设置；明确哪些没有使用预设 |
| 换客户端但协议要求相同 | 无需新建客户端特例；相同输入要求采用相同处理决定 |
| 客户端每轮都携带工具 | 样本明确指出 plain_chat_only 不运行预设，不能虚报该客户端预设适配成功 |
| 严格用途下工具和预设冲突 | 在上游调用前说明冲突；不增加模型调用；给出可执行调整建议 |
| 必需提取未命中／输出脚本出错 | 不能返回未经必需整理的文字并显示完全成功 |
| 保存新配置时旧请求仍在进行 | 旧请求完成原版本，新请求使用新版本；无跨渠道／跨版本混用 |
| 远程模块更新失败 | 已有可用版本继续使用；未准备的新版本不覆盖线上配置 |
| 上游故障，存在相同加工语义的备用 | 原生次数限制内切换；不重复加工；无兼容备用则准确说明 |
| 流式、长回复、客户端取消、代表性并发 | 等待原因可知、无跨请求串内容、资源受限且会释放；无适配不额外缓冲 |
| 旧配置升级 | 发布前即可知道受影响渠道，迁移前后可比较，有恢复配置的方法 |
| 新模型／新格式／只有提示词约束的客户端 | 标出未经验证或无法可靠识别的部分，不声称已经通用兼容 |

先覆盖实际使用的客户端请求样本，再添加协议级边界样本；不以客户端品牌数量代替覆盖。真实模型结果仍需观察，不能用固定 mock 证明任意模型都能遵守预设。

### 19.8 最终产品判断

按修订方案实现并通过上述验收，可以形成“在明确范围内配置一次、长期复用；特殊需求一次调整”的产品，而不是每个客户端打补丁。

但目前只能给出**设计上的条件性判断**，不能确认现有代码已稳定、已可靠，也不能证明覆盖大多数实际流量。上线前须用现有代表性请求和真实运行结果检验成功、原生中转、冲突、允许回退、超时各自占比，并分别解释原因；不能把所有 HTTP 200 统算为预设兼容成功。

### 19.9 最终复审与设计冻结

最终结论：**对本文件声明的支持范围，设计可放行实施；不需要继续增加新的适配层或重复宏观设计。** “使用舒服、低维护、稳定可靠”已经有明确行为和验收条件，但只有实施后的结果才能证明兑现。

最后收口的维护细节：

| 情况 | 用户不应被迫做的事 | 确定行为 |
| --- | --- | --- |
| 仅改渠道展示备注、界面排版 | 重新准备脚本、重做全部兼容检查 | 有效加工设置不变则保留关联结果 |
| 调整预设提示词，正则来源未变 | 排查同一正则为什么执行两遍 | 稳定来源身份与内容版本分离，关联规则只执行一次 |
| 已接受的世界书简化，修改无关展示信息 | 再确认全书条目 | 确认仅在相关风险及替代行为变化时失效 |
| 同配置复制到备用渠道 | 手改配置使数据库 ID 相同 | 以有效加工语义判兼容，不以渠道 ID 判兼容 |
| 文本规则存在，但本次走 JSON 路径 | 为 JSON 请求临时关闭文本规则 | 不适用步骤不执行，不被误判成必需步骤失败 |
| 选择较宽适配范围，同时设置失败回退 | 猜测“必须生效”和“可取消”谁优先 | 范围与失败后果分别显示，必需加工不可被回退绕过 |

这些行为纳入现有对应的回归及使用旅程，不单独建立另一套测试工程。首次配置提供推荐值和解释；普通用户无需逐阶段选择全部失败策略。高级设置保留，但不作为正常使用的必经步骤。

最终验收通过标准是：使用选定的代表性样本组，保存一次配置后连续运行，不需要为每次请求改设置；在范围内完成约定加工，范围外遵循已选择行为；失败可解释、不串内容、不重复加工；更新与回滚可控，资源与等待时间在部署实测的限制内。

仍需重新检查的变化仅包括实际用途／输出约束变化、预设或规则行为变化、依赖版本变化、上游模型能力变化。报告过期是提醒，不自动触发付费请求；普通保存也不强制跑完整样本组。

设计冻结不禁止修复实现时发现的真实缺口；但不得以“更通用”为由再引入客户端识别、隐式工具编排或未获授权的自动生成。下一阶段应以实现与上述验收获取证据，而不是继续用文档长度证明可靠性。

### 19.10 可用性优先的默认失败策略（2026-11-09 讨论记录）

用户要求先记录，尚未授权据此更改代码默认值或已保存配置。此项作为后续默认值调整依据；与前文新配置默认终止的建议不同时，按本节重新评估，不能声称已经生效。

回退意味着相应功能本次可能没有生效，不代表等价完成预设；日志须明确显示跳过世界书、取消适配或保留上一阶段的实际结果。“有效”指通过对应结构及必要处理检查，不保证模型语义质量。世界书承载必需规则、正则承载必需清理等严格用途，仍允许管理员选择终止。

## 20. 最新预设的可用体验与通用兼容设计

### 20.1 交付目标和非目标

本节对应用户最新要求：以 `Meowssiah-2.0.0.json` 为代表性样本，让普通用户能够使用其应有的请求加工与回复能力，不要求复刻酒馆所有功能。样本用于暴露能力缺口和验收，不作为生产代码分支条件。

“正常使用”的具体含义：导入并完成一次可信脚本确认和样本检查后，客户端继续发送完整聊天请求；中转站处理世界书、预设、数据脚本和已选择的文字规则；上游返回后，客户端收到符合原 API 协议的文字或其明确要求的格式。用户不必每次粘贴脚本、手改工具名、清除残留 HTML，或因普通多轮聊天反复调整配置。

以下不是交付目标：浏览器菜单、按钮、页面美化、浏览器本地存储、酒馆聊天存档写回、前端组件渲染、外部日志上传、脚本主动发起模型调用、没有完整客户端上下文时重建丢失历史。基础文字功能不应依赖执行这些附加功能。

保证的是可验证的加工、协议和隔离行为，不保证模型一定遵循提示词、一定输出高质量故事，也不保证任意未知脚本都可运行。下述方案是待实施设计，不能据此将当前版本标为已兼容该样本。

### 20.3 用户操作流程：一次配置，日常不干预

1. 用户选择渠道、模型，导入预设。导入只解析，不执行任意脚本、不上传日志、不改变其他渠道。
2. 展示一张“此预设可以如何使用”的摘要：请求整理、回复还原、世界书接入、文字清理；另列“已略过的界面功能”和“影响使用的待处理项”。不将几十条 API 名称作为主界面说明。
3. 保留手动控制。已有启用偏好不被导入或重新分析覆盖；未授权运行的脚本显示“尚未开启”，不是“已生效”。用户确认可信并开启数据处理后，才执行对应钩子。
4. 从明确插件配置生成可检查的回复来源建议；无歧义的同类声明可一次确认应用，不能每换预设都手填工具名。存在歧义时只让用户选择具体用途，不要求编写高级 JSON。
5. 默认使用文字交付：沿用预设 formatter，跳过仅界面展示的正则，不输出由中转站额外生成的面板或网页。需要进一步裁剪内容时，在现有回复清理入口设置并预览；不默认丢弃预设自带的摘要、选项或其他文字段落。
6. 用户可选导入世界书，在总览看到有效开关、触发方式、位置和顺序。没有世界书不妨碍预设本身工作。
7. “检查并预览”运行本地处理，不调用模型。用户另点“发送一次测试请求”时才发起一次可计费模型请求；不在导入、保存或后台自动发送。
8. 确认结果并保存渠道。此后普通多轮调用复用已保存配置和固定依赖；只有预设、用途、模型能力或依赖版本发生实质变化时重新提醒检查。

成功提示分三档：“配置已识别”“本地处理已通过”“模型测试已通过”。不能用第一档绿色提示暗示最后一档已完成。模型测试结论绑定输入场景、模型和配置指纹，不宣称覆盖所有客户端。

### 20.4 数据来源：一个事实来源，两种读取方式

客户端本次提交的有效历史仍是唯一聊天事实来源；显式替代历史仍按第 13.1 节选择，不合并两份历史。预设条目和世界书是加工配置，不是从服务器另找出的聊天记忆。

脚本收到的 `request` 是当前已组装请求的可修改副本；数据读取接口提供同次请求的清晰视图，不能指向其他会话、数据库里最近一次聊天或上一次预览。

| 数据 | 提供方式与权限 |
| --- | --- |
| 已组装 messages、工具与允许的请求字段 | 沿用请求钩子参数，修改后仍经过现有字段和客户端约束校验 |
| 客户端有效历史 | 沿用已有消息读取接口的有限投影；保留角色、顺序、非文本块和工具关联，不声称是酒馆原生存档 |
| 当前预设条目、顺序及启用状态 | 只读有效配置副本；包含渠道条目覆盖后的结果，不能再从原 JSON 读回已关闭条目 |
| 宏、时间和已授权变量 | 本请求冻结上下文；预览与正式处理使用同一口径 |
| 临时 metadata / 脚本状态 | 本请求独享、有大小限制；只在本次处理阶段之间传递，完成即释放 |
| 酒馆 raw chat、历史 extra、浏览器 localStorage、真实酒馆 chat ID | 没有数据就明确不提供，不返回伪造存档、空代理或冒充真实 ID 的 request ID |

不把标准 messages 无条件投影成 `ctx.chat`：两者结构及 metadata 含义不同，可能反而使脚本放弃其正确的 messages 后备路径。`getContext()` 中不具备的可选字段保持缺省；需要这些字段且没有后备路径的脚本报告缺少能力。

本次允许的兼容外观为一个普通、请求隔离的数据对象：`window` 的 `parent/top` 指向自身，只提供 `SillyTavern.getContext()` 等已明确支持的数据接口；不是浏览器窗口，没有 DOM、iframe、网络或后台任务。对象上临时属性只属于当前隔离环境。`getContext()` 的预设配置只读，metadata 为本请求临时对象；不把修改 metadata 解释为存档成功。

不存在 `localStorage` 时保持缺省，使用可选链的脚本可自行走默认分支；直接依赖其读写的必需处理明确失败。未知宿主调用不能靠“返回空对象”假装成功。不按特定 storage key 提供值，不注入预设专有控制台状态。菜单模式、深度思考等可由预设本身已有条目控制时，用户仍在预设编辑中操作。

SPreset 钩子与酒馆助手数据脚本共享这份数据语义和资源约束；保留各自已存在的钩子形式，不新建第三种预设运行模式。有限数据接口不等于开放整个 window，更不等于运行浏览器脚本。

请求临时状态用明确的序列化输入／输出在钩子间传递，不缓存加载后的 JS 环境或 Go 可变对象；状态总量上限 256 KiB，超限按脚本阶段失败，不能为了继续运行截掉一半。只读配置副本与可修改 metadata 分开。沿用现有 8 MiB 钩子输入输出、64 MiB 隔离环境及执行超时限制；新增接口不得绕过已有并发准入或让每次状态访问重置执行时限。涉及完整响应的运行资源从准备到释放均有请求所有者，结束、失败、取消都释放。具体部署承载量仍需实测，不把这些边界常量当作性能结论。

### 20.5 脚本识别、依赖和不支持功能

识别依据为文件格式、启用条目、声明的钩子和受支持 API，不依据预设名称、作者、工具名称或某段故事文字。生产代码禁止出现 `if preset == Meowssiah`、专用控制台 key、固定思考标签等分支。

- 已有 `extensions.SPreset` 数据处理声明时，直接走该配置契约；浏览器加载器不因启用就成为执行数据钩子的前置条件。
- 独立的 DOM 菜单、美化脚本可整项略过并说明原因；混合脚本既处理正文又调用不支持能力时，不能通过字符串删除、改写函数体或捕获全部异常来“裁掉界面部分”。没有脚本自身的后备路径，就标出实际缺失能力。
- 现有远程依赖准备能力只拉取受支持的数据模块，保留地址校验、大小、超时、依赖图限制及内容指纹。可信确认后准备，保存版本化快照；正式请求不临时上网拉代码。
- 依赖加载不等于脚本执行，语法准备通过不等于业务兼容；不执行 DOM 注入加载器来间接追踪其任意 URL，不开放任意 import、eval、文件或网络访问。
- 外部日志上传始终不执行。浏览器状态及跨轮归档不伪造；完整历史由客户端继续提交，受支持脚本可基于本次历史重建其文字结构。客户端删去的摘要或旧轮次无法凭空恢复。
- 对 MacroNest、MessageInjections、ForcedPostProcessing 等其他声明逐项标注“已映射到现有能力／此功能未开启／尚不支持”。与核心请求整理相互依赖的未支持功能不能混在“仅界面功能已略过”里。

### 20.6 工具用途：修正所有新增工具都被当作回复来源的错误

保留第 12 节“显式回复来源、不猜业务阶段、不执行客户端工具”的原则。修订点是：**新增工具不一定是回复来源，历史里出现工具也不表示需要再执行一次工具。**

三种用途及来源必须在请求内确定：

| 用途 | 判断和处理 |
| --- | --- |
| 客户端自己的工具 | 只根据原始请求识别，定义、选择约束和历史受保护；不能隐藏成预设回复 |
| 预设回复工具 | 来自管理员已确认的回复来源声明，或明确插件契约生成并确认的建议；使用已声明 formatter / Pointer 还原文字 |
| 预设创建的已完成历史调用 | 必须证明调用及结果全由本次脚本新增、ID 成对且无冲突、没有待执行调用；只是发送给模型的上下文，不是实际执行结果的声明，也不是回复来源 |

回复来源建议仅在存在明确启用的 consumeToolCalls + formatter 声明、且对应有效 ToolBindings 只有一个候选时生成。该建议仍是界面明确列出的配置，不从工具名、schema 字段或近期响应猜测。候选多个或契约不足时要求选择，不能给所有工具套上 formatter。

ToolBindings 的定义本身是代码时，导入阶段只显示存在声明；须在用户授权后的本地检查中执行、校验并取得真实工具名，才能形成待确认建议。保存的来源绑定到预设导入身份、条目 ID 和有效定义指纹；运行时工具名或定义变化必须重新校验，不继续沿用过期建议。

“已完成历史调用”先做差分与关联校验，并且不能通过修改客户端原有工具历史来制造证明。该用途由插件适配入口声明并绑定本次生成的来源；仅仅在上游响应中看到同名调用不能认定用途。其他脚本入口没有足够证据时要求明确配置，不自动推断。

不增加跨请求业务状态、不识别“现在是 context 阶段还是故事阶段”、不自动补工具结果，也不为了拿最终文字多请求一次模型。历史调用记录与正在请求执行工具在界面中分别命名。

#### 工具选择的可表示转换

当前脚本字段 `toolConfig` 不应靠“allowed 必须等于全部 tools”判断支持程度，改成有穷、可证明的语义归一化：

1. `ANY + allowed 唯一工具` 可转换成标准的指定工具选择；不要求其他合法历史定义也能在本次被选择。
2. `ANY + allowed 等于全部可选工具` 对应标准 required；`AUTO`、`NONE` 仅在能保持候选集合和是否允许普通文字的含义时归一化。
3. 子集含多个候选而目标协议不能等价表达时明确不支持，不扩大候选集，也不擅自改成随便选一个。
4. 历史工具定义可按上游协议需要保留，但不得因此变成本次允许的回复调用。目标 provider 无法同时表达历史和选择限制时，在发送前报清楚，不删除历史来蒙混。
5. auto 模式允许普通正文，不能强改为指定调用；如果当前 provider 无法把仅供历史使用的工具排除出可调用集合，该组合不标为支持。后续不得以“提高成功率”为由偷偷收窄 auto 的正文选择。

工具定义、schema 属性顺序及历史中的原生签名字段必须经过现有协议承载能力检查；能无损保留的保留，不能承载的准确报告。禁止为了通过当前 DTO 校验泛化删除未知嵌套字段；也不由中转站主动生成签名或验证绕过标记。样本脚本自身生成的非标准元数据需要在实际目标渠道验收，不能因字符串长得像合法字段就宣称跨 provider 支持。

因此样本默认 `ANY + 唯一允许回复工具` 有明确的通用解决路径；其可选 auto 分支需单独检查，不以默认分支通过代替。`context` 和 `soliumbra_reply` 只出现在样本说明和 fixture 中，不作为生产分类常量。

若模型实际返回历史用途工具、未声明调用、混合正文与回复容器，继续按冲突处理，不能把任意 arguments 展示为成功回复。没有“没看懂就透传内部调用”的后门。

### 20.7 世界书：匹配先于脚本，位置完整进入组装，再由脚本加工

沿用已经实施的 v2 稳定锚点、同位置排序、完整工具区块和预算，不再创建另一套世界书流程。这里的“世界书在预设之前”准确表示：**触发只看加工后的客户端历史，内容在预设骨架中按目标位置插入，插入完成后才调用请求脚本。** 不是先把所有条目硬塞到 messages 最前面，再希望预设识别。

确定的顺序为：

`原请求快照 → 适用范围 → 有效历史与发送规则 → 预设骨架/世界书匹配及定位/宏展开 → 消息合并 → 请求脚本 → 工具及客户端约束检查 → 冻结 → 上游`

逻辑上匹配与组装分离；为准确计算展开预算和实际边界，可以共享编译上下文。不得扫描已加入的预设提示词来补触发，不重复发送规则，也不在脚本后补插世界书来掩盖脚本吞掉内容。

- “预设定义前／后”继续定位独立 `worldInfoBefore/worldInfoAfter`，保留预设自己定义的外围边界提示条目；中转站不注入样本专有 catgodml 标记。
- “最新用户前／聊天深度”使用真实历史来源锚点；同物理位置保持既定稳定顺序；不把脚本重写后的合成工具消息用于重新计算深度。
- 对样本需验证定义前、定义后、最新用户前和聊天深度，检查脚本是否将内容带入其生成的历史／上下文；不能只验证一个手工包装的 system 消息。
- 脚本把世界书重组到工具结果中可以是正常处理，不要求最终保持相同消息索引。预览同时提供插入时位置与脚本后的请求；不能凭字符串搜索声称普遍精确追踪。
- 用验收哨兵验证代表性样本的保留、次数和顺序；哨兵不进入真实用户请求。任意脚本主动删除或摘要化内容，运行时不擅自重新追加，也不宣称语义保真。
- 旧配置仍需看实际 semantics_version。当前只有一个用户，不新建复杂迁移平台；实施时只检查、备份、按明确选择调整当前渠道，不能因“兼容旧配置”继续保留已知错误。

### 20.8 回复、正则与转义：一条交付链，不再叠补丁

继续使用 `完整协议解析 → 回复来源恢复 → 输出脚本 → 接收文字规则 → 客户端约束检查 → 交付`。每个阶段运行一次；冻结其配置，同渠道重试不重复请求侧脚本或世界书。

1. 仅对已声明的回复工具调用 formatter。上游 arguments 必须是完整合法 JSON 对象，恢复前先校验；不能让样本自带的 partial-args 后备逻辑把截断对象伪装成成功。
2. formatter 负责字段顺序和业务标签。中转站不硬编码 game_content、think_nya、summary 等段落，也不默认只取正文而丢掉动态段落。可选 Pointer 来源仍保留，二者不串成“猜第一个字段，不行再用 formatter”。
3. 默认保留预设原有文字；用户需要隐藏思考、仅保留正文或保留状态标签时，用现有明确规则／回复来源选择并预览。独立 reasoning 字段不自动拼进正文，也不能仅凭 `<thinking>` 等文字就断言是协议推理字段。
4. JSON 解码一次得到真实字符串；仅在工具 arguments、工具结果等有明确协议类型的字段解析其 JSON。禁止全局 replace `\\n`、`\\"`、HTML 实体解码，或对“看起来像 JSON”的正文循环解析。普通代码、路径、字面反斜杠必须保留。
5. 顶层与 SPreset 绑定规则按稳定来源 ID 统一。相同 ID 且内容相同只保留一份有效来源；相同 ID 不同内容提示冲突并要求选定，不能按名称、发现先后或跨渠道全局 map 去重。独立不同 ID 不因相似文本被自动删除。
6. `promptOnly` 规则按原声明处理再次发给模型的历史文字；`markdownOnly` 且非 promptOnly 的规则默认属于展示用途，不自动用于 API 接收正文。需要改为 API 清理时，用户在外部规则编辑中明确选择，并保留来源和方向。不能为了隐藏思考顺便启用整个 HTML 美化链。
7. 外部规则和内置规则的已关联副本仍只执行一次，关闭外部副本不会偷偷重新启用内置原件；模型范围、角色和深度继续生效。
8. 不创建通用“删掉全部 HTML”过滤器。用户正文可以合法包含 HTML、XML、自定义标签；跳过界面生成规则与删除用户正文是两回事。

有回复加工时 SSE 仍完整收集、验证后交付；明确展示“处理完成后返回”，不承诺逐 token 实时速度。没有加工的原生请求不增加这份缓冲。保留上游真实未完成／拒绝状态，不将内部调用泄露或截断内容包装成成功。

### 20.9 客户端特殊格式与可用性优先

不以“完美使用”为理由破坏客户端工具、JSON 或 Schema。继续沿用现有适用范围和第 19.10 节的失败底线，不新增按客户端品牌分支。

| 情况 | 对用户的确定承诺 |
| --- | --- |
| 普通文字聊天，处于适配范围 | 执行预设核心请求／回复链及已开启世界书 |
| 仅普通文字范围，客户端带工具或结构化要求 | 走原生中转，明确提示本次没有使用预设；不能显示已生效 |
| 客户端每次都附带 tools 或 tool_choice | 首次检查即提示该客户端大部分请求可能不使用预设，不让用户到上线后才发现 |
| 宽范围、只有提示词且不改写客户端协议 | 继续保护原工具及结构要求；不是遇到 JSON 就一概禁止预设 |
| 宽范围、预设内部回复工具与客户端工具／Schema 冲突 | 发送前说明冲突；不自动丢弃客户端工具，不猜哪个优先 |
| 请求脚本失败，允许整次取消且无不可跳过的加工约束 | 首次上游发送前回到原请求，只发一次，记录“本次未使用预设”；配置无效或协议冲突不靠此掩盖 |
| 世界书、可选回复修饰失败 | 按已选策略退回完整检查点；必需提取与客户端格式不能被跳过 |

初次配置展示推荐方案和影响范围，而不是要求用户先理解全部失败策略。手动控制仍有价值，但主要用于改变用途和解决真实歧义，不应成为每次请求的工作。

跨轮摘要归档、浏览器面板交互等未支持能力，在导入时就说明其用户影响；“可以正常文字对话”不应被误读为“酒馆中的所有记忆和菜单均被复制”。换客户端后仍需重新检查该客户端的实际协议要求，这是一次配置检查，不是逐条消息调参。

### 20.10 界面与诊断：用户只需要回答三件事

主页面只回答：“现在启用了什么”“还差哪一步”“测试后客户端会收到什么”。复用现有摘要卡片和二级编辑对话框，不再铺开脚本 API 清单，也不另外重构整套正文审计页面。

- **请求整理**：说明会把聊天历史、预设和世界书交给数据脚本处理；展示开启状态。未开启时提示该预设是否依赖它，不允许“总状态已就绪”掩盖核心关闭。
- **回复还原**：展示已确认回复工具及“使用预设自带的回复整理方式”；参数路径等收进高级设置。历史用途工具显示为“仅用于组织发送内容，不会真的执行”，不能和回复来源混排成让用户全选的列表。
- **文字清理**：分发送与接收，清楚标出仅酒馆展示、可能生成网页、已启用清理、已关闭；支持样本查看。预设更新导致来源变化时提示具体项，不重启用户关闭项。
- **世界书**：总览有效开关、触发和目标位置；样本报告逐项给出“未开启／未命中／预算未纳入／已插入／目标缺失改放某处”。脚本后只展示实际最终请求，不伪造逐条最终位置。
- **附加功能**：默认一行“未运行菜单、美化与外部日志上传，不影响已验证的基础文字功能”；展开可看具体脚本。独立略过不等于所有依赖关系都已证明无影响。

错误使用普通语言，并附稳定阶段码和请求 ID，例如“预设需要浏览器聊天存档，目前只能读取本次请求，且脚本没有提供后备处理”“预设整理完成，但回复工具的选择限制无法由此渠道表达”。内部保留 API 级诊断，不能把 `{phase, capability:script-failed}` 当作唯一用户说明。

日志区分三件事：上游实际返回、New API 实际交付、可读解释；前两者相同时提示“未改动”，不复制一堆看似不同的数据。原文保留 JSON 转义是正常序列化，可读视图按字段解码；展示层不得改变真实交付内容。复制原文与复制文字分别命名。

### 20.19 脚本成果与客户端交付的单一所有权（2026-11-10，已部署，通用链路验收通过）

20.18 的“编译后重贴本轮原始消息”方案撤销。它虽然在部分样本中改善了任务遵循，但会重新引入脚本已经清理、改写、归档的内容；以最后一个 assistant 划分当前任务，也无法区别客户端尾部的系统背景与真正的新任务。这是通用实现错误，不应靠为某个预设增加例外解决。

本轮实施边界：

1. **消息内容只有一个编译结果。** 世界书、预设条目和请求脚本按既定顺序处理消息；脚本输出是最终上下文，不再追加原始 system/developer/user 后缀，也不从自然语言猜测任务、格式或“最后一个正文”。脚本主动删除、替换的内容不会被网关复活。普通预设交付仍使用其回复来源和 formatter。
2. **原生协议单独保护。** 客户端声明 tools/functions、tool_choice 或 response_format 时，仍运行请求脚本，但客户端拥有这些原生协议字段。实际客户端工具调用／结果消息按原顺序原样保留在编译上下文之前；只保留协议消息，不复制普通历史、尾部系统提示或图片。预设内部工具示例仅作为上下文资料，不混入客户端可调用工具。
3. **任务提醒不重放内容。** 需要交付协调时只添加无用户正文的通用说明，要求完成编译上下文所表达的最新任务；不能通过重新追加未处理消息来“修复”任务遵循。模型是否真正完成任务必须独立检查，不能用一个提示语承诺任意脚本／模型永久正确。
4. **回复处理保持职责边界。** 普通文字继续执行已启用的输出脚本和接收正则；私有回复容器先由原 formatter 还原。客户端业务工具参数和明确结构化 JSON 不交给任意文字脚本改写。不能把 formatter 未适用误报为整个预设关闭。
5. **诊断提供事实而非成功暗示。** 记录请求钩子是否实际运行、消息是否改变、编译前后消息数量和本次交付方式；不保存额外正文，不将“处理完成”当作业务任务完成。

验收必须覆盖：脚本删除／替换的普通消息不再出现；当前任务保留在脚本输出中；普通及显式历史一致；原生与旧式工具历史不丢失、不重复、不拆散；无工具定义的工具结果续传；同名工具所有权；多模态内容不被重复注入；普通输出钩子、私有 formatter 和接收正则真实改变结果；JSON／工具返回仍满足客户端协议。使用无敏感内容的确定性样本，真实模型验收也只使用正常任务，不重放含未成年人性内容的历史请求，不以改变模型安全拒绝作为验收目标。

此方案保证网关不再覆盖脚本成果，并守住客户端协议；不能保证任意不兼容脚本都能自动理解完整客户端语义。预设内部硬编码的故事开场、浏览器状态依赖、主动丢弃用户任务等属于脚本能力边界，不能由网关盲目恢复整段输入掩盖。线上配置中主动关闭的条目也不会因代码修复自动恢复。
