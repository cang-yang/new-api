# New API 客户端与预设工具协议协调设计

> 状态：待用户复审。本文是实现前规格，不授权直接修改代码。
>
> 本文替代同目录下由 `085952033` 提交的旧版设计。旧版问题不是缺少一个工具名判断，而是推断输入、阶段输入和启用边界都不完整。

## 1. 背景

New API 的首要职责仍然是中转站：

- 接收客户端请求。
- 完成鉴权、路由、渠道选择、计费、日志和上游协议转换。
- 在世界书和预设能力存在时，按已配置顺序处理请求。
- 把上游结果按客户端可理解的协议返回。

世界书和预设属于中转链路上的条件处理，不应把 New API 改造成 SillyTavern 客户端，也不应持久化聊天状态、自动执行工具或自行推进多轮对话。

当前需要解决的是一个真实存在的协议冲突：

1. 客户端带着自己的工具契约或结构化输出要求发送请求。
2. 世界书在客户端消息上完成关键词匹配和信息插入。
3. 预设脚本在编译后的客户端消息上增加自己的工具。
4. 预设脚本可能要求本轮必须调用工具。
5. 如果客户端要求最终调用 A，预设脚本又要求调用 B，一个上游请求里就会出现两个“最终回复协议”。
6. 模型无法从协议上判断当前应调用 A 还是 B。

这不是单纯的提示词问题。一个模型调用只能有一个明确的最终协议。需要解决的是“辅助工具阶段”和“最终回复阶段”的分离，以及最终响应对外部客户端契约的恢复。

## 2. 已确认的故障与根因

### 2.1 真实请求现象

已观察到的处理后请求具有以下结构：

```json
{
  "model": "gemini-3.8-flash",
  "tools": [
    { "function": { "name": "soliumbra_reply" } },
    { "function": { "name": "context" } }
  ],
  "tool_choice": "required",
  "messages": [
    { "role": "user" },
    { "role": "assistant", "tool_calls": ["soliumbra_reply"] },
    { "role": "tool", "tool_call_id": "call_init_00" },
    { "role": "user" },
    { "role": "assistant", "tool_calls": ["context"] },
    { "role": "tool", "tool_call_id": "call_sync_01" }
  ]
}
```

该请求中：

- `soliumbra_reply` 是客户端最终需要的回复工具。
- `context` 是预设脚本增加的辅助工具。
- 当前已经存在 `context` 的完整调用和结果。
- 下一阶段本应只暴露并强制调用 `soliumbra_reply`。
- 实际 `tools` 同时保留了二者，`tool_choice` 只是笼统的 `required`。

因此模型仍可能再次调用 `context`，客户端也无法获得稳定、唯一的最终回复协议。

### 2.2 代码层根因

现有实现主要存在四个缺口：

1. 协议计划默认使用原始客户端请求判断客户端最终工具，但请求阶段和消息阶段判断又必须参考预设脚本编译后的请求。原始请求和编译后请求没有被清晰地区分为两个输入。
2. 预设脚本把 `tool_choice` 改成 `required` 后，旧逻辑只看到“编译请求中有多个工具”，容易落入 `ambiguous_preset_final_tool`，随后整个协调层不激活。
3. 当前没有“跟随预设保存”的显式开关。协议层可能在一套本来不需要协调的预设上尝试推断。
4. 阶段判断没有把“最后一条辅助工具结果”作为最终阶段的主要证据，因此处理后的真实请求没有得到应有的最终工具投影。

### 2.3 不能通过猜工具名解决

不能根据以下内容判断工具角色：

- 名字中包含 `reply`、`answer`、`context`、`game`。
- 工具参数较多或较少。
- 工具是否由某个当前已知预设生成。
- 工具在数组中的固定位置。

这类规则换个预设就会失效。角色必须来自客户端契约、脚本所有权、辅助工具调用结果或显式配置。

## 3. 目标与非目标

### 3.1 目标

- 每个预设独立决定是否启用工具协议协调，默认关闭。
- 开关随预设配置一起导入、编辑和保存，不使用全局状态。
- 开关关闭时，`tools`、`tool_choice`、`response_format` 和响应完全沿用现有中转行为。
- 开关开启时，允许最多一个客户端最终协议和一个预设最终协议参与当前调用。
- 保留预设脚本的提示词、消息注入、辅助工具和动作工具能力。
- 当已经出现辅助工具结果时，自动进入最终阶段，而不是再次暴露辅助工具。
- 客户端要求工具回复时，保留客户端的工具定义和工具调用历史，最终返回客户端工具调用。
- 客户端要求 JSON 或文本时，允许把安全的预设终止工具结果恢复为 `message.content`。
- 无法唯一判断角色或无法安全恢复格式时，不猜测、不改名、不伪造客户端工具，保持正常中转并记录诊断。
- 兼容流式、非流式、多 choice、reasoning、usage 和工具参数分片。
- 协调层只存在于 Chat Completions、已启用预设、脚本运行和非 Passthrough 的链路上。

### 3.2 非目标

- 不复刻完整 SillyTavern 状态机。
- 不保存会话级 `sticky`、`cooldown`、递归状态或工具阶段状态。
- 不自动执行客户端工具、预设工具或动作工具。
- 不根据工具名做隐式适配。
- 不把一个工具的 schema 强行改名为另一个工具来冒充兼容。
- 不修改路由、模型选择、渠道亲和、计费、鉴权、日志和重试次数。
- 不为该功能增加独立客户端式页面或导航。
- 不修改世界书在预设之前执行的既有边界。

## 4. 总体架构

协议协调层位于以下链路之后：

1. 请求读取和鉴权。
2. 渠道、模型和 Passthrough 判定。
3. 世界书处理。
4. 预设提示词编译。
5. 预设脚本执行和工具注入。

协议协调层只负责：

1. 保存原始客户端协议快照。
2. 读取预设脚本执行后的编译请求。
3. 判断是否允许激活。
4. 识别客户端最终工具、预设最终工具和预设辅助工具。
5. 根据当前消息阶段裁剪上游可见的 `tools` 和 `tool_choice`。
6. 在需要时把预设终止工具结果恢复为客户端文本或 JSON 内容。
7. 生成不带正文和 schema 的安全审计信息。

协议协调层不得重排消息、删除历史工具调用、更改工具 ID、替换客户端工具定义或执行工具。

## 5. 启用边界与配置

### 5.1 预设级开关

在现有 `SillyTavernToolProtocol` 中增加：

```go
type SillyTavernToolProtocol struct {
    Enabled        bool     `json:"enabled"`
    ClientFinal    string   `json:"client_final,omitempty"`
    PresetFinal    string   `json:"preset_final,omitempty"`
    Auxiliary      []string `json:"auxiliary,omitempty"`
    ResponseTarget string   `json:"response_target,omitempty"`
}
```

配置示例：

```json
{
  "sillytavern_preset": {
    "script_runtime": "spreset-v1",
    "tool_protocol": {
      "enabled": true,
      "response_target": "auto"
    }
  }
}
```

规则：

- `tool_protocol` 缺失或 `enabled=false` 时，协议协调层完全不参与请求或响应处理。
- `enabled=true` 只表示允许评估，不代表一定激活。
- `client_final`、`preset_final`、`auxiliary` 只作为高级显式覆盖，不是必需项。
- `response_target` 支持 `auto`、`text`、`json`、`tool`，默认 `auto`。
- `response_target=tool` 只有在存在明确的 `client_final` 时才有效。
- 该配置保存在渠道预设配置内，随预设导入、编辑器草稿和渠道保存一起持久化。
- 不增加全局开关，不增加服务端会话状态。

### 5.2 自动激活条件

只有同时满足以下条件才允许建立协议计划：

- 端点为 Chat Completions。
- 渠道配置了预设。
- 预设的 `Models` 为空或包含当前模型。
- `script_runtime` 非空。
- 请求未启用 Passthrough。
- `tool_protocol.enabled=true`。
- 脚本执行成功并返回当前请求的工具所有权信息。
- 原始客户端请求存在现代工具契约、结构化输出要求，或编译后请求存在可识别的预设工具。
- 至少能够唯一识别一个最终协议和一个辅助/终止角色关系。

以下情况不得激活：

- 没有预设、没有脚本、脚本未运行或脚本执行失败。
- 没有工具，也没有文本/JSON 最终格式需要恢复。
- 只使用旧式 `functions`/`function_call`，且无法无损映射到现代工具契约。
- 预设工具所有权报告不可信或与客户端工具定义冲突。
- 工具角色不唯一。
- 渠道或模型不匹配。

### 5.3 与现有功能的关系

- `Passthrough`：跳过世界书、预设和协议协调。
- `tool_text`：继续要求 `script_runtime` 关闭；两者不能同时启用。
- 世界书：仍然在预设编译前执行。
- 预设文本、ChatSquash、FinalRequestProcessing、Regex 和 OutputPreprocessing：仍按现有顺序执行。
- 渠道测试和真实 relay：使用同一编译链，避免测试结果与实际请求不一致。

## 6. 工具角色模型

### 6.1 客户端最终协议

`client_final` 表示客户端最终希望收到的协议。它可以是：

- 一个明确的函数工具及其工具调用结果。
- JSON 内容契约。
- 普通文本内容契约。

客户端原始请求是客户端契约的唯一权威来源。预设处理后的请求不能凭空创造新的客户端工具定义。

### 6.2 预设辅助工具

`preset_auxiliary` 是预设脚本为了补充上下文、同步信息或完成中间步骤而增加的工具。

辅助工具响应仍以 `tool_calls` 返回，由客户端按自身能力处理并将结果放回后续请求。New API 不执行辅助工具。

### 6.3 预设终止工具

`preset_terminal` 是预设用于承载最终可见回复的内部工具。只有在以下条件之一成立时才能确定：

- 预设显式配置了 `preset_final`。
- 没有客户端最终工具，且编译请求中只有一个预设自有工具。
- 编译请求的函数级 `tool_choice` 明确指向一个预设自有工具，且没有客户端最终工具冲突。

预设终止工具不能在客户端明确要求另一个最终工具时被当作最终工具。

### 6.4 动作工具

动作工具是预设脚本要求客户端执行外部动作的工具。

本设计不尝试仅凭 schema 区分“动作工具”和“终止内容工具”。如果工具需要执行动作，必须保持在辅助/动作阶段，不能被响应投影吞掉。

如果无法确认一个预设工具是终止内容工具还是动作工具，默认不得把它转换为正文或 JSON，也不得伪造为客户端工具。

## 7. 工具角色推断

推断必须同时使用两个快照：

- `original`：世界书和预设脚本执行前的客户端请求。
- `compiled`：预设脚本执行后的上游请求。

### 7.1 客户端最终工具

按以下顺序推断：

1. 如果配置了 `client_final`，且该工具存在于原始客户端请求中，使用该工具。
2. 如果原始客户端的 `tool_choice` 是函数级选择，且工具存在，使用该工具。
3. 如果原始客户端 `tool_choice=required` 且原始请求只有一个工具，使用该工具。
4. 如果原始客户端有多个工具，且最近一个当前周期内的工具结果对应其中一个工具，且排除该工具后只剩一个未完成候选，该候选为 `client_final`。
5. 否则客户端最终工具未知。

重要修正：

- 编译后请求因为预设脚本追加工具而变成多个工具，不能反过来否定原始客户端已经明确的最终工具。
- 编译后 `tool_choice=required` 只说明“需要工具”，不说明“任意新增工具都是最终工具”。
- 只要原始客户端存在唯一、明确的最终工具，预设新增工具默认归入辅助/动作集合。

### 7.2 预设辅助工具

默认规则：

- 如果已经确定 `client_final`，所有预设自有且不等于 `client_final` 的工具归入辅助/动作集合。
- 如果没有 `client_final`，但确定了预设终止工具，其余预设自有工具归入辅助集合。
- 显式配置的 `auxiliary` 优先于默认分类。
- 显式配置的辅助工具必须存在于编译后请求中。
- `auxiliary` 不能包含最终工具。
- 显式 `preset_final` 不能覆盖一个已经明确存在的 `client_final`；这种配置不激活并记录 `client_and_preset_final_conflict`。

### 7.3 预设终止工具

按以下顺序推断：

1. 显式 `preset_final`。
2. 没有客户端最终工具时，编译请求函数级 `tool_choice` 指向的预设自有工具。
3. 没有客户端最终工具、原始请求没有工具，且编译请求只有一个预设自有工具。
4. 显式辅助列表之外只剩一个预设自有工具。
5. 否则不激活：客户端请求没有任何工具契约时记录 `no_client_tool_contract`，其余情况记录 `ambiguous_preset_final_tool`。

### 7.4 不允许的推断

- 不按名称关键词判断。
- 不把原始客户端所有非最终工具自动当作辅助工具，除非其角色已经由函数级选择或历史结果证明。
- 不把预设新增的多个工具全部视为同一阶段可安全调用，除非显式配置或唯一推断成立。
- 不在存在两个不同最终工具时任意选择其中一个。
- 不从提示词正文推断客户端回包格式。客户端没有通过 `tools`、`tool_choice` 或旧式函数控件声明任何工具时，视为不存在可协调的客户端契约，预设工具保持原样。

## 8. 当前阶段判定

阶段是请求级结果，不保存到服务端。

只使用编译后消息序列判断阶段，因为预设脚本可能注入辅助工具调用、工具结果和额外消息。

### 8.1 辅助阶段

满足以下条件时进入 `auxiliary`：

- 存在辅助工具。
- 当前周期内没有已完成的辅助工具结果。
- 最后一个辅助工具调用还没有对应结果，或尚未调用辅助工具。

上游只暴露辅助工具。若辅助工具只有一个，使用函数级 `tool_choice`；若有多个，`tool_choice=required`，但可见工具集合只能包含辅助工具。

### 8.2 最终阶段

满足以下条件之一时进入 `final`：

- 当前周期内存在至少一个已完成辅助工具结果。
- 没有辅助工具。

上游只暴露最终工具，并使用函数级 `tool_choice` 强制该工具。

### 8.3 当前周期边界

当前周期边界是消息序列中最后一条有效 user 消息。

阶段判断只查看该 user 消息之后的消息：

1. 从消息尾部向前扫描。
2. 找到最后一条 user 消息。
3. 建立工具调用 ID 到工具名的映射。
4. 查找该 user 消息之后已完成的辅助工具结果。
5. 找到则进入最终阶段。
6. 未找到且存在辅助工具则进入辅助阶段。
7. 没有 user 边界时，只有在尾部存在已完成辅助工具结果时才进入最终阶段；否则进入辅助阶段。

如果辅助工具调用缺少结果，按 fail-safe 保持在辅助阶段，不提前暴露最终工具。

## 9. 请求投影

只有协议计划激活时才允许修改以下字段：

- `tools`
- `tool_choice`

以下字段必须保持不变：

- `messages`
- `functions`
- `function_call`
- `response_format`
- `model`
- `stream`
- 计费、路由和渠道相关字段
- 上游私有字段和请求元数据

### 9.1 保留客户端历史

以下内容必须逐项保留：

- 原始客户端工具定义。
- 工具调用 ID。
- 工具结果 ID。
- 工具调用和工具结果的顺序。
- 多模态内容。
- reasoning 或 provider-specific 元数据。

请求投影只隐藏当前上游调用不应看到的工具定义，不删除消息历史。

### 9.2 辅助阶段投影

辅助阶段只暴露辅助工具：

```json
{
  "tools": ["preset_auxiliary_only"],
  "tool_choice": {
    "type": "function",
    "function": {
      "name": "preset_auxiliary"
    }
  }
}
```

如果存在多个已验证可并列的辅助工具：

```json
{
  "tools": ["aux_a", "aux_b"],
  "tool_choice": "required"
}
```

客户端最终工具不得出现在辅助阶段。

### 9.3 最终阶段投影

最终阶段只暴露最终工具：

```json
{
  "tools": ["final_tool"],
  "tool_choice": {
    "type": "function",
    "function": {
      "name": "final_tool"
    }
  }
}
```

最终工具属于客户端时，上游实际调用客户端工具。
最终工具属于预设时，上游调用预设终止工具，响应后再执行合同恢复。

### 9.4 合同约束

- 客户端最终工具不能被预设终止工具替换。
- 预设终止工具不能在没有客户端工具定义的情况下伪装成客户端工具调用。
- 原始客户端工具定义不能被修改。
- 旧式 `functions`/`function_call` 不参与投影。

## 10. 响应恢复

响应恢复只处理最终阶段，并且只处理当前计划中唯一确定的最终工具。

### 10.1 客户端最终工具

如果最终工具属于客户端：

- 保持上游 `tool_calls` 原样。
- 保留参数 JSON、ID、finish reason、usage 和 reasoning。
- 不做文本或 JSON 投影。

### 10.2 客户端要求文本

如果客户端最终协议是普通文本，且最终工具属于预设：

1. 如果预设配置了 `toolCallFormatter`，使用其输出。
2. 如果参数只有一个字符串字段，直接使用该字符串。
3. 如果 schema 的 `required` 有多个字段，按 required 顺序选择最后一个可用的字符串字段。
4. 否则按 `propertyOrdering` 从后向前选择唯一字符串字段。
5. 只有唯一字符串字段时直接使用该字符串。
6. 仍无法唯一提取时，写入完整 JSON 字符串，不丢数据。

### 10.3 客户端要求 JSON

当客户端明确要求 `response_format.type=json_object` 且最终工具属于预设时：

- 参数必须是合法 JSON。
- 对象、数组、数字、布尔和 null 按原结构序列化到 `message.content`。
- 字符串参数以 JSON 字符串编码写入，保证 `message.content` 本身仍是合法 JSON。
- 无法解析时不得输出半转换结果。
- 第一版只支持 `json_object` 语义。
- `json_schema` 不进入自动协议投影；开关开启但客户端只要求 `json_schema` 且不存在客户端最终工具时，协议计划不激活并记录 `response_projection_unsafe`。

### 10.4 辅助阶段响应

辅助阶段响应保持标准工具调用：

- 不移除 `tool_calls`。
- 不改写为正文。
- 不把 `finish_reason=tool_calls` 改成 `stop`。

### 10.5 流式响应

流式处理必须：

- 完整拼装最终工具参数后再投影。
- 保留非文本 SSE 事件、注释、`retry` 和未知字段。
- 保留 `usage`、`reasoning_content`、`system_fingerprint` 和 choice 索引。
- 多 choice 按 choice 分组处理，不能串组。
- 只在必要时移除最终工具调用并写入 `content`。
- 仅当没有剩余客户端工具调用时才把 `finish_reason=tool_calls` 改为 `stop`。
- 请求投影本身不能强制响应缓冲；只有最终内容投影需要缓冲。

## 11. 预设能力与动作工具保留

### 11.1 必须保留

- 预设提示词和消息注入顺序。
- ChatSquash 和 FinalRequestProcessing 的既有行为。
- 预设辅助工具和动作工具。
- 辅助工具响应，让客户端可以按原流程执行并回传结果。
- OutputPreprocessing、tool formatter 和响应正则的既有顺序。

### 11.2 禁止的伪兼容

- 不能把 `context` 工具改名成 `soliumbra_reply`。
- 不能把动作工具响应吞掉后返回空正文。
- 不能因为工具名字像回复工具就跳过实际 schema。
- 不能在缺字段、缺历史或工具 ID 不一致时继续投影。

### 11.3 无法解决的组合

以下组合没有无损的单一模型调用方案：

- 客户端要求最终工具 A，预设也要求独立最终工具 B，且 B 不是可通过文本/JSON 恢复的内容容器。
- 客户端和预设同时要求不同且不可转换的 schema。
- 预设工具的真实用途是外部动作，但客户端只接受正文。

此时协议计划不得激活。请求和响应保持原样，审计记录明确原因。不能为了表面兼容而丢失预设动作或伪造客户端工具。

## 12. 审计与诊断

### 12.1 审计字段

审计只包含协议身份和安全结论：

```json
{
  "enabled": true,
  "eligible": true,
  "activated": true,
  "reason": "client_final_with_auxiliary_result",
  "phase": "final",
  "contract": "tool",
  "client_final": "soliumbra_reply",
  "preset_final": "",
  "final_tool": "soliumbra_reply",
  "auxiliary": ["context"],
  "diagnostics": [],
  "fingerprint": "..."
}
```

### 12.2 禁止记录

审计不得包含：

- 消息正文。
- 工具结果内容。
- 工具描述全文。
- JSON schema 全文。
- 密钥、Token 或上游私有字段。

### 12.3 诊断原因

至少需要稳定区分：

- `tool_protocol_disabled`
- `preset_not_active`
- `script_runtime_inactive`
- `no_client_or_preset_contract`
- `no_client_tool_contract`
- `legacy_tool_contract_unsupported`
- `client_final_ambiguous`
- `preset_final_ambiguous`
- `ambiguous_preset_final_tool`
- `client_and_preset_final_conflict`
- `tool_ownership_conflict`
- `phase_auxiliary`
- `phase_final`
- `projection_skipped_unsafe`
- `response_projection_unsafe`

诊断只用于本地观察、渠道测试和日志，不影响上游协议。

## 13. UI 与预设保存

### 13.1 位置

开关放在现有预设编辑器的“脚本兼容”区域，位于脚本运行方式选择之后。

### 13.2 展示

当脚本运行时未启用时：

- 显示为不可用。
- 提示需要先启用服务器可执行脚本。

当脚本运行时已启用时：

- 显示“协调客户端与预设工具调用”开关。
- 默认关闭。
- 说明只应在预设脚本会要求模型调用工具时开启。
- 说明只有客户端请求自己声明工具时才生效，没有客户端工具契约的请求保持原样。
- 展示检测到的预设工具名称。
- 展示当前推断状态：客户端最终工具、预设辅助工具或“暂无法安全判断”。

### 13.3 保存语义

- 开关修改先进入预设编辑草稿。
- 点击“应用到渠道”后写入 `tool_protocol.enabled`。
- 保存渠道后生效。
- 从预设 JSON 导入时保留该字段。
- 没有该字段时默认关闭。

### 13.4 不增加的 UI

- 不增加全局工具协调页面。
- 不增加工具调用历史管理页面。
- 不增加会执行辅助工具的按钮。
- 不展示上游密钥、完整消息或完整 schema。

## 14. 重试与并发

协议指纹至少包含：

- 开关状态。
- 响应目标。
- 客户端最终工具。
- 预设最终工具。
- 辅助工具列表。
- 最终工具。

跨渠道重试时，如果协议指纹或相关预设设置不同，不进入新的上游请求，返回可诊断错误。

同一请求内的重试必须复用同一个协议计划。重试不能：

- 重新推断出不同阶段。
- 累积辅助工具调用。
- 修改原始客户端历史。
- 因前一次上游失败而改变客户端合同。

## 15. 端到端场景

### 15.1 客户端要求工具回复，预设需要辅助上下文

第一次客户端请求：

1. 客户端工具：`soliumbra_reply`。
2. `tool_choice=required`。
3. 预设脚本增加 `context`。
4. 协议计划：客户端最终工具 `soliumbra_reply`，预设辅助工具 `context`。
5. 当前周期没有 `context` 结果。
6. 上游只看到 `context`，并强制调用。

客户端执行 `context` 后第二次请求：

1. 历史中存在 `context` 调用和结果。
2. 预设再次增加 `context`。
3. 协议计划识别当前周期已有辅助工具结果。
4. 上游只看到 `soliumbra_reply`，并强制调用。
5. 客户端收到标准 `soliumbra_reply` 工具调用。

### 15.2 客户端要求 JSON，预设使用终止工具

1. 客户端没有工具，但设置了 `response_format.type=json_object`。
2. 预设声明唯一终止工具 `answer`。
3. 开关开启且角色唯一。
4. 上游只看到 `answer`，并强制调用。
5. 上游参数为 `{"answer":"ok","score":7}`。
6. 响应恢复为 JSON 字符串写入 `message.content`。
7. 不向客户端暴露 `answer` 工具调用。

### 15.3 开关关闭

1. 请求包含客户端工具。
2. 预设脚本增加工具。
3. `tool_protocol.enabled=false` 或字段缺失。
4. New API 不做任何工具裁剪、阶段判断或响应投影。
5. 请求和响应保持现有中转行为。

### 15.4 角色不明确

1. 客户端没有最终工具。
2. 预设脚本增加两个自有工具。
3. 没有显式配置，也没有函数级选择。
4. 协议计划不激活。
5. 原请求和原响应路径保持不变。
6. 审计记录 `ambiguous_preset_final_tool`。

### 15.5 无预设或无脚本

1. 渠道没有预设，或预设没有 `script_runtime`。
2. 即使请求带工具，也不建立协议计划。
3. 请求按普通中转路径处理。

## 16. 用户视角复审

### 16.1 开启后用户应感受到的变化

- 带工具脚本的预设可以继续完成辅助工具阶段。
- 辅助工具完成后，模型只被要求调用客户端最终工具。
- 客户端不会再从两个“最终工具”中随机选择。
- 客户端要求文本或 JSON 时，预设终止工具可以透明地恢复成正文内容。
- 关闭开关后，行为回到普通中转，不需要修改其他渠道功能。

### 16.2 用户不应感受到的变化

- 路由和计费不变。
- 渠道测试仍能显示同一编译结果。
- 世界书仍在预设前完成。
- 预设提示词和动作工具不会被悄悄吞掉。
- 客户端工具历史和 ID 不会变化。

### 16.3 仍可能出现的限制

- 客户端和预设各自要求不同最终工具且无法转换时，系统会保持原行为，不会伪造兼容。
- New API 不会自动执行辅助或动作工具。
- 不认识的旧式工具输入不会自动升级。
- 预设脚本未运行时，开关不会让协议层单独工作。

这些限制是有意的安全边界，不是未实现的行为。

## 17. 测试与验收

### 17.1 请求角色和投影

- 开关关闭时，请求字段和语义保持不变。
- 原始一个客户端工具、编译后增加一个预设工具、编译后 `tool_choice=required` 时，客户端工具仍被识别为最终工具。
- 当前周期存在辅助工具结果时，上游只暴露最终工具。
- 当前周期没有辅助结果时，上游只暴露辅助工具。
- 辅助工具只有一个时使用函数级选择。
- 辅助工具为多个时只使用辅助集合和 `required`。
- 客户端工具历史、结果和 ID 保持不变。
- 预设不能删除或修改客户端工具。
- 旧式 `functions`/`function_call` 不触发投影。

### 17.2 响应恢复

- 客户端最终工具响应保持 `tool_calls`。
- 文本目标可以提取唯一字符串或最后一个 required 字符串字段。
- JSON 目标只在参数合法时写入 `content`。
- 辅助阶段响应不转换成正文。
- 流式和非流式结果语义一致。
- 多 choice 不串组。
- `usage`、reasoning、`finish_reason` 和 SSE 元数据保留。
- 不能安全提取时不输出半转换结果。

### 17.3 条件边界

- 没有预设、没有脚本、模型不匹配、Passthrough、非 Chat Completions 时不激活。
- 开关开启但角色不明确时不修改请求。
- 预设动作工具保持可执行阶段。
- 预设和客户端最终协议冲突时不猜测。
- 跨渠道重试指纹不一致时拒绝重试。

### 17.4 UI

- 脚本未启用时开关不可用并给出原因。
- 脚本启用后开关默认关闭。
- 修改开关进入草稿。
- 点击应用并保存渠道后配置持久化。
- 重新打开编辑器时开关状态保留。
- 导入带 `tool_protocol` 的预设时字段不丢失。
- 长文本和移动端布局不溢出。

### 17.5 真实请求回放

使用已确认的真实请求结构进行回放，必须得到：

- 原始工具定义仍为 `soliumbra_reply`。
- 预设工具为 `context`。
- 最新 user 消息之后已存在 `context` 工具结果。
- 最终阶段只暴露 `soliumbra_reply`。
- `tool_choice` 为函数级 `soliumbra_reply`。
- 所有原始消息、工具 ID 和工具结果保持不变。

### 17.6 完成标准

以下条件全部满足才视为完成：

- 旧版歧义停用问题被真实请求回放覆盖。
- 开关关闭路径无行为变化。
- 无法判定路径无请求变更且有诊断。
- 客户端工具合同、文本合同和 JSON 合同均有测试。
- 流式与非流式均有测试。
- 重试和渠道测试覆盖通过。
- 相关 Go 测试、构建检查和前端编辑器测试通过。
- 未破坏世界书、预设、路由、计费和 Passthrough 的既有测试。

## 19. 实施顺序

1. 先补规格对应的测试：启用开关、真实角色推断、编译消息阶段判断、歧义回退。
2. 再修改配置契约和协议计划输入，确保旧路径不激活。
3. 接入请求投影和响应恢复。
4. 接入审计、渠道测试和跨渠道重试指纹。
5. 最后接入前端开关和预设导入保存。
6. 执行真实请求回放、流式回放和全量相关测试。

在第 1 至第 5 步中，任何一步发现无法无损处理的情况，都必须回到本文第 11.3 节，而不是通过工具名或 schema 猜测补丁。

## 20. 最终结论

该方案不是“让预设工具和客户端工具同时成为最终工具”，而是：

- 辅助阶段只让预设工具工作。
- 最终阶段只让客户端要求的最终协议工作。
- 预设内容在安全可证明时恢复成客户端要求的文本、JSON 或工具结果。
- 不能证明时不改请求、不对响应做伪转换，并明确记录原因。

这样既保留中转站属性，也保留预设脚本的辅助能力，同时避免模型在两个最终协议之间随机选择。
