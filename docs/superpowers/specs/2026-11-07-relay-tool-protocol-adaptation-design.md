# New API 工具协议适配层设计

## 1. 背景

New API 是中转站，不是 SillyTavern 客户端。世界书和预设脚本都必须建立在中转能力之上，不能改变路由、计费、鉴权和上游协议转换的基本职责。

当前问题发生在一个具体的请求链路上：

1. 客户端发送聊天请求，其中可能带有自己的工具调用契约或结构化输出要求。
2. Worldbook 根据客户端原始消息匹配并插入世界信息。
3. SillyTavern 预设编译客户端消息。
4. 预设脚本可以注入辅助工具，也可以要求模型调用预设自己的终止回复工具。
5. 当客户端和预设同时要求“最终回复协议”时，上游请求可能出现两个以上 `tool_choice=required` 可选工具，模型只能随意选择。

已观察到的真实请求中，`tools` 同时包含 `soliumbra_reply` 和 `context`，`tool_choice` 为 `required`，最后一条消息是 `context` 的工具结果。模型下一步本应调用 `soliumbra_reply`，但协议没有表达这个阶段语义，因此可能再次调用 `context`。

这不是单纯的前端问题，也不能靠删除一个工具解决。两个不同的“最终传输协议”在同一个模型调用中确实不能同时成立；但客户端要求的结构可以作为正文或 JSON 内容被投影出来。

## 2. 目标

建立一个与预设名称、脚本名称、工具名称无关的条件协议适配层：

- 只在实际存在世界书、预设、脚本工具或输出契约时启用。
- 在不必要时完全不改变原中转路径。
- 一个模型调用只暴露一个最终回复协议。
- 辅助工具阶段和最终回复阶段分开，避免 `required` 下的随机选择。
- 保留客户端可观察的外部契约。
- 允许把预设终止工具的结果投影为普通文本或 JSON 内容。
- 流式、非流式、多 choice、usage、reasoning 和 finish reason 均不能损坏。
- 对无法安全判断的结构不猜测，保留现有行为并记录诊断。

## 3. 非目标

- 不复刻完整 SillyTavern 状态机。
- 不执行客户端工具或预设工具的动作。
- 不引入 `sticky`、`cooldown`、概率触发或会话存储。
- 不修改路由、模型选择、渠道计费、鉴权、重试次数和上游连接配置。
- 不把任意工具的请求和响应强行互相改名后冒充兼容。
- 不新增用户客户端式管理界面。

## 4. 能力边界

协议适配层是条件性的，只有满足相应条件才启用：

| 能力 | 激活条件 |
| --- | --- |
| Worldbook | 渠道配置了已启用的世界书 |
| 预设提示词 | 配置了预设、模型匹配且未启用 body passthrough |
| 脚本运行时 | `script_runtime` 非空且端点为 Chat Completions |
| 工具角色解析 | 请求中存在客户端工具契约，或预设脚本声明了工具 |
| 请求投影 | 存在明确最终工具，并且存在需要隔离的辅助工具 |
| 响应投影 | 上游最终工具需要转换为客户端要求的文本或 JSON 内容 |

以下情况不得触发新逻辑：

- 没有渠道级预设或世界书。
- 请求不是 Chat Completions。
- body passthrough 已启用。
- 没有工具、没有脚本工具、没有结构化输出要求。
- 无法安全识别工具角色。

## 5. 工具角色

角色是请求级数据，不写入全局状态：

- `client_action`：客户端工具，但无法确认它是最终回复协议。
- `client_response`：客户端明确要求的最终回复工具。
- `preset_auxiliary`：预设脚本用于补充上下文、同步信息或中间步骤的工具。
- `preset_terminal`：预设决定最终可见回复的工具。
- `internal_transport`：只负责运输最终文本或 JSON 的内部工具。

角色解析优先级：

1. 显式配置声明。
2. 客户端工具契约。
3. 预设脚本消费关系。
4. 如果仍无法唯一确定，则不猜测，保持原路径并在审计中记录原因。

第一版支持的安全推断：

- 客户端 `tool_choice` 指定函数名，且该工具存在于原始请求中，则该工具为 `client_response`。
- 客户端 `tool_choice=required` 且原始请求只有一个工具，则该工具为 `client_response`。
- 客户端 `tool_choice=required` 且有多个工具时，如果当前周期最后一条工具结果对应其中一个工具，且剩余工具恰好一个，则剩余工具为 `client_response`，被调用过的工具为辅助工具。
- 显式配置 `ClientFinal` 时使用配置值。
- 显式配置 `PresetFinal` 时使用配置值。
- 预设脚本新增且未被客户端声明的工具，默认为预设工具。
- 当客户端存在明确 `client_response`，预设新增工具默认全部为辅助工具。
- 当没有客户端最终工具，且预设新增工具只有一个时，该工具可作为 `preset_terminal`。
- 当没有客户端最终工具，且预设新增工具多于一个时，只有显式配置或明确的函数级 `tool_choice` 才允许确定终止工具。

不采用名称包含 `reply`、`context`、`answer` 等词来猜测角色。

## 6. 单轮状态机

每个模型调用只选择一个阶段：

### 辅助阶段

适用条件：当前生成周期还没有辅助工具结果，且存在预设辅助工具。

上游请求只暴露当前允许的辅助工具。`tool_choice` 必须精确指向一个辅助工具，或使用仅包含辅助工具的 `required`。

### 最终阶段

适用条件：最近一条用户消息之后已经出现辅助工具结果，或没有辅助工具。

上游请求只暴露唯一最终工具，并使用函数级 `tool_choice` 指向它。

状态依据当前请求中的消息顺序判断，不保存服务端会话状态：

1. 从消息尾部向前扫描。
2. 找到最近一条 user 消息作为当前生成周期边界。
3. 如果边界之后存在辅助工具结果，则进入最终阶段。
4. 如果最后一条消息本身就是辅助工具结果，也进入最终阶段。
5. 否则进入辅助阶段。

如果存在辅助工具调用但没有对应结果，按 fail-safe 进入辅助阶段，并记录诊断。

## 7. 请求投影

请求投影只改变允许修改的协议字段：

- `messages`
- `tools`
- `tool_choice`

其他字段必须保持原样。

投影步骤：

1. 保留客户端原始请求快照。
2. 执行 Worldbook 和预设编译。
3. 执行脚本和预设工具注入。
4. 解析工具角色。
5. 在不破坏客户端工具历史和 ID 的前提下验证客户端外部契约。
6. 按当前阶段裁剪上游可见工具。
7. 将 `tool_choice` 改为唯一最终工具或唯一辅助工具。
8. 生成不含工具描述正文、只含角色和诊断的审计信息。

客户端工具历史、工具结果和 ID 不能被投影删除或重写。隐藏只发生在上游可见的 `tools` 和 `tool_choice`。

## 8. 响应投影

上游响应在现有响应过滤器之前进入协议投影。

支持的目标：

### 纯文本

最终预设工具的参数转为客户端可见文本：

1. 如果预设配置了 `toolCallFormatter`，使用其输出。
2. 如果参数对象只有一个字符串字段，直接使用该字符串。
3. 如果工具 schema 的 `required` 中有多个字段，按 schema 顺序选择最后一个 required 字符串字段。
4. 如果没有 required 字符串字段，优先按 `propertyOrdering` 选择；仍无法唯一选择时，只有唯一字符串字段才直接使用。
5. 仍无法唯一选择时，返回完整 JSON 字符串，而不是丢数据。

### JSON 内容

当客户端使用 `response_format` 要求 JSON 时：

- 参数本身是 JSON 对象，写入 `content` 的对象序列化文本。
- 参数是字符串，写入字符串内容。
- 无法解析为合法 JSON 时按严格失败处理，不输出半转换结果。

### 客户端工具

如果客户端明确要求最终工具，客户端工具本身就是最终协议，不执行预设终止工具的改名投影。

### 辅助响应

辅助阶段返回辅助工具调用，保持工具调用结构，不把辅助工具转换为正文。

## 9. 流式响应

流式处理必须：

- 在最终 SSE frame 之前完成完整工具参数拼装。
- 保留非文本事件、注释、`retry` 和其他 SSE 字段。
- 保留 `usage`、`reasoning_content`、`system_fingerprint` 和 choice 索引。
- 将已完成内部工具调用从 `tool_calls` 中移除。
- 只有没有剩余客户端工具调用时才把 `finish_reason=tool_calls` 改为 `stop`。
- 只在确实需要响应投影时缓冲；请求侧投影不能单独导致响应缓冲。

## 10. 兼容与回归边界

- 旧 `tool_text` 行为保持可用，但不得与新的通用响应投影同时执行。
- Worldbook 继续在预设之前匹配。
- 渠道测试和 Worldbook 预览继续使用同一条编译链。
- 跨渠道重试必须确认协议配置一致；不一致时拒绝重试并返回可诊断错误。
- 非 Chat Completions 端点不启用脚本适配。
- Passthrough 继续跳过预设和世界书。
- 路由、计费、鉴权、日志和上游重试逻辑不变。

## 11. 审计

每次请求产生以下协议审计信息：

- 是否激活。
- 客户端外部契约类型。
- 客户端最终工具。
- 预设最终工具。
- 当前使用的最终工具。
- 辅助工具列表。
- 当前阶段。
- 诊断原因。
- 协议指纹。

审计不得包含工具描述全文、消息正文、密钥或上游私有字段。

## 12. 验收标准

必须通过以下行为测试：

- 没有预设和世界书时，请求和响应与当前路径一致。
- `tool_choice=required` 且存在客户端最终工具和预设辅助工具时，上游只暴露当前阶段的工具。
- 当前周期存在辅助工具结果时，上游只暴露最终工具。
- 当前周期没有辅助工具结果时，上游只暴露辅助工具。
- 客户端工具历史、结果和 ID 不变。
- 最终预设工具可投影为普通文本。
- 最终预设工具可投影为 JSON 内容。
- 流式和非流式结果一致。
- 多 choice 不串组。
- `usage`、`reasoning_content` 和 `finish_reason` 按协议保留。
- 无法识别角色时不猜测，并产生明确诊断。
- 渠道测试和实际 relay 使用相同的编译链。

## 13. 分阶段范围

第一阶段实现：

- 能力边界和协议计划。
- 工具角色推断和显式配置覆盖。
- 辅助阶段与最终阶段的请求投影。
- 纯文本和 JSON 内容响应投影。
- 审计、回归测试和推送。

第二阶段再评估：

- 客户端最终工具之间的复杂跨 schema 转换。
- 自动执行辅助工具。
- 跨多轮内部工具编排。
